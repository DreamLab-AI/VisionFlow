### F-01 — NIP-98 single-use replay enforcement permanently self-denies pod initialization
- Topics: VC-03.4, VC-03.15, VC-05.15
- Evidence: `validate_nip98_token` (`src/utils/nip98.rs:428`) claims the signed event ID in a singleton memory cache (`REPLAY_CACHE`, `nip98.rs:215`) to reject replays (`nip98.rs:178`). The route `POST /api/solid/pods/init-nip98` is mounted inside the `/api` scope (`src/main.rs:1181`, `src/handlers/solid_proxy_handler.rs:1790`), so it passes through `RbacGate`, which runs `verify_access` (`src/utils/auth.rs:174`) and claims the NIP-98 event ID in `REPLAY_CACHE`. Then `init_pod_nip98` (`solid_proxy_handler.rs:1331`) immediately runs a second, independent NIP-98 verification via `SolidPodState::extract_user_identity` (`solid_proxy_handler.rs:1332`), re-validating the exact same token.
- Failure: The second verification encounters the event ID already claimed by `RbacGate` in the same request, fails with `TokenReplayed`, causes `extract_user_identity` to return `None`, and returns HTTP `401 {"error":"NIP-98 authentication required"}` (`solid_proxy_handler.rs:1335-1338`). Legitimate clients attempting to provision a Solid pod with valid NIP-98 credentials are permanently locked out.
- Confidence: high
- Marked by authors: yes (Divergence noted in VC-05.15 and VC-03.15)

### F-02 — Release builds drop authenticated identity on the primary WebSocket stream

4. **Client WebWorker memory management and SharedArrayBuffer isolation:** While the protocol defines V5 binary layout and worker dispatch (`graph.worker.ts`), the material does not include browser-side allocation boundaries, backpressure handling for dropped WebGL animation frames, or behavior on platforms lacking `SharedArrayBuffer` support.
5. **Exact boundary behavior of external inference APIs:** Services like `RAGFlowService`, ComfyUI, and external LLM endpoints are documented as HTTP boundaries with API key authentication, but their retry policies, circuit breaker thresholds, and timeout degradation modes under network partitions cannot be verified from these summaries.

### R-1 — Unfiltered position broadcast leaks private multi-tenant graphs over WebSocket
- Topics: VC-13.3, VC-03.9, VC-03.2
- Chain of events:
  1. An enterprise tenant configured private graph data relying on `PUBKEY_VISIBILITY_FILTER` (enabled by default) to restrict confidential nodes to authorized keypairs.
  2. An unauthorized or anonymous external client connected to the `/wss` endpoint with a valid or empty session.
  3. In production release builds, the WebSocket upgrade handler (`http_handler.rs:328-341`) hardcodes query token extraction to `None` and verifies `Authorization: Bearer` headers without writing the extracted `NostrUser` into `ws_server.pubkey` (`http_handler.rs:186-258`), causing every connection to run with `pubkey: None`.
  4. On the GPU physics tick (25Hz/60Hz), `ForceComputeActor` executed physics integration and forwarded all node coordinates via `UpdateNodePositions` to `GraphServiceSupervisor`, which forwarded them to `PhysicsOrchestratorActor` and `ClientCoordinatorActor` (`force_compute_actor.rs:2430`, `graph_service_supervisor.rs:1996`, `client_coordinator_actor.rs:345`).
  5. `ClientCoordinatorActor::broadcast_with_filter` serialized all positions into V5 binary frames (tag `0x05`, 52 bytes per record). Because `client.filter.enabled` defaults to `false` for connecting clients, `ClientCoordinatorActor` took the `unfiltered_binary` branch (`client_coordinator_actor.rs:371`).
  6. The `PUBKEY_VISIBILITY_FILTER` drop-set filter (`compute_private_opaque_ids` / `apply_drop_set`) was executed solely on the periodic polling loop (`fetch_nodes` in `position_updates.rs:742-754`) and was completely bypassed by the real-time push pipeline (`ClientCoordinatorActor`).
  7. The unauthorized client received real-time 52-byte binary frames containing 3D coordinates, node IDs, cluster IDs, community IDs, and anomaly scores for all private nodes across all tenants, exfiltrating the client's proprietary graph topology.
- Evidence:
  - `src/gpu/broadcast_optimizer.rs:7-11`: Design doc states `BROADCAST-001` emits full snapshots only; visibility culling is disabled by default.
  - `src/actors/client_coordinator_actor.rs:368-378`: If `client.filter.enabled == false`, the actor sends `unfiltered_binary` directly via `SendToClientBinary`.
  - `src/handlers/socket_flow_handler/position_updates.rs:742-754`: Visibility filtering is only implemented inside `fetch_nodes`.
  - VC-13.3 explicitly records: "this per-client node-id filter is a SEPARATE mechanism from the pubkey visibility drop-set filter, which gates the polling path (fetch_nodes, see VC-13.6) and initial state sync, NOT this ClientCoordinatorActor broadcast".
  - `src/handlers/socket_flow_handler/http_handler.rs:341`: In release builds, `ws_server.pubkey` is never set during upgrade.
- Warning signs visible today:
  - Architecture documentation in VC-13.3 explicitly highlighting that the broadcast pipeline does not evaluate `PUBKEY_VISIBILITY_FILTER`.
  - Code divergence note in VC-03.2 documenting that `ws_server.pubkey` is never set from the `Authorization` header in release builds.
- Confidence: high

### R-2 — Role deletion preserves ambient write privileges, failing de-provisioning
- Topics: VC-03.8, VC-05.1, VC-03.7
- Chain of events:
  1. An enterprise administrator detected a compromised key or offboarded a contractor and executed `DELETE /api/admin/rbac/users/{pubkey}/role` to revoke access.
  2. `admin_rbac_handler::handle_delete_user_role` invoked `RoleStore::remove_checked` within an atomic SQLite transaction (`admin_rbac_handler.rs:181`, `role_store.rs:500`).
  3. `remove_checked` successfully executed `DELETE FROM roles WHERE pubkey = ?` and committed the transaction.
  4. The client was informed that the role was deleted, but under ADR-2010 design, deleting a role row does not create a denial tombstone; it drops the user to ambient default authority (`role_store.rs:359`).
  5. When the offboarded contractor subsequently submitted mutating requests, `RoleStore::effective_role` resolved their access. Finding no explicit database row, it fell back to `configured_default` (`role_store.rs:195, 359`), which defaults to `UserRole::Editor` if `RBAC_DEFAULT_ROLE_ENV` is unset or empty.
  6. `UserRole::Editor` mapped to `AccessLevel::Authenticated` (`rbac.rs:83`), which permits `WriteGraph` and `WriteSettings` operations (`rbac_gate.rs:147`).
  7. The contractor retained full mutation access and used their existing Nostr private key to overwrite ontology definitions, modify graph structures, and exfiltrate data after revocation was reported successful.
- Evidence:
  - `src/services/role_store.rs:500`: `remove_checked` deletes the target's explicit row without revoking ambient authority.
  - `src/services/role_store.rs:195-218`: `parse_default_role` defaults unset or empty configurations to `UserRole::Editor`.
  - `src/services/role_store.rs:359`: `effective_role` precedence falls back to `configured_default` when no explicit row exists.
  - `src/models/rbac.rs:83-89`: `UserRole::Editor` maps to `AccessLevel::Authenticated`, granting mutating permissions.
  - `src/handlers/admin_rbac_handler.rs:202`: Handlers explicitly acknowledge that removal does not revoke access and warn that ambient defaults apply.
- Warning signs visible today:
  - Explicit note in VC-03.8: "removal is NOT revocation: deleting the row drops the target to their AMBIENT authority (Admin if power-user, else configured_default), never denies outright. Genuine revocation requires an explicit Viewer assignment."
- Confidence: high

### R-2 — Double-spending and ledger drainage via process-local state locking across replicas
- Topics: SP-05.4, SP-07.14, SP-07.15, SP-10.4, SP-10.8
