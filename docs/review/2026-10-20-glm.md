## visionclaw#3 / critical

### F-01 — Codescape's main port runs with no authentication and is reachable from the LAN through nginx
- Topics: VC-39.2, VC-39.5, VC-39.7
- Evidence: The main listener on port 4100 (REST, /ws/positions, /ws/events, /wss, /ws/voice, /ws/presence, codescape-server/src/routes/mod.rs:403-415) "runs OpenAccess, reported honestly as auth open" (codescape-server/src/auth.rs:120-124), while nginx publishes `/codescape/` on port 3001 to the LAN "in dev by owner decision" (nginx.dev.conf:63-65, docker-compose.unified.yml:464). Voice on that port reaches `run_command` → `execute(Command)` on a blocking thread (codescape-server/src/routes/mod.rs:348-351) and egress to ASR/TTS (codescape-server/src/voice/asr.rs:261, voice/tts.rs:78).
- Failure: Anyone on the LAN opens the Codescape surface with no credential, issues grammar (and, if Loom is configured, LLM-mediated) commands, consumes ASR/TTS egress budget, and reads the code-graph views of mounted repositories.
- Confidence: high
- Severity: high
- Marked by authors: yes (OPEN, register R1 "until P6")

### F-02 — Auth bypass defaults to ARMED in compose; the only hard guard is which binary and which .env reach production
- Topics: VC-36.15, VC-36.3
- Evidence: `VISIONCLAW_DEV_MODE: "${VISIONCLAW_DEV_MODE:-1}"` — dev mode defaults ON (docker-compose.unified.yml:95, ADR-2108 flip described in the same note). When active, "Every request granted as DEV_MODE_PUBKEY = 'dev-mode-local-admin'" (src/utils/auth.rs:96, project/src/main.rs:299) as a "LAN-local FULL bypass, peer-agnostic: no NIP-98, no token, no peer check" (src/utils/auth.rs:203-218). Release builds refuse to boot if the var is present (project/src/main.rs:109, :136, :161), but the dev-auth build's hygiene hook is an empty stub (project/src/main.rs:169), the bypass is enforced at four independent sites (src/utils/auth.rs:191, src/settings/auth_extractor.rs:25, src/handlers/memory_cloud_handler.rs:66, src/handlers/speech_socket_handler.rs:165), and "both services load env_file .env, so the var must never sit in a .env shared with prod — sharper now that the compose default supplies it unasked" (docker-compose.unified.yml:92-94).
- Failure: A dev-auth artifact deployed to a prod-like host, or a shared .env carrying the now-defaulted var, yields a silently total auth bypass; if it reaches a release deploy instead, the service refuses to boot (exit 2) — either way an outage or a breach from one environment mistake.
- Confidence: high (mechanism); medium (likelihood, which depends on the deploy pipeline, not shown)
- Severity: high
- Marked by authors: partially (ADR-2108 records the default flip and the .env caveat; it is not registered as an open risk)

- Marked by authors: no

### F-08 — Memory-route ordering compares wall clocks across machines with no skew bound
- Topics: VC-38.8, VC-38.12

- Confidence: high
- Severity: medium
- Marked by authors: yes (OPEN, VC-38.8)

### R-1 — Armed-by-default VISIONCLAW_DEV_MODE full auth bypass reached a client-facing deployment
- Topics: VC-36.15, VC-36.11, VC-36.3
- Chain of events: ADR-2108 (2026-09-08) flipped the dev compose default from `:-0` to `:-1`, so `launch.sh up dev` boots an ARMED backend and the operator opts *out* rather than in. A dev-profile image or environment is promoted to, or run alongside, a client-facing LAN deployment. Because the dev-auth build's hygiene hook is an empty stub, nothing refuses the variable. Every request — REST write, drag, pin, layout, settings — is granted as `DEV_MODE_PUBKEY = "dev-mode-local-admin"`, peer-agnostic, with no NIP-98, no token, no peer check. Even an empty `XR_NOSTR_SECRET` with the ephemeral signer works friction-free. All write attribution collapses to one pseudo-user, so the audit trail cannot say who did what to the client's data.
- Evidence: `docker-compose.unified.yml:95` (`VISIONCLAW_DEV_MODE: "${VISIONCLAW_DEV_MODE:-1}"`, "DEV SERVICE ONLY"); the caveat that "both services load env_file .env, so the var must never sit in a .env shared with prod — sharper now that the compose default supplies it unasked" (`docker-compose.unified.yml:92-94`); release refusal only in release builds, exit code 2 (`project/src/main.rs:136`, `:161`, and `:109` "a release binary physically cannot honour" the vars); the dev/dev-auth stub (`project/src/main.rs:169`); the grant (`src/utils/auth.rs:116-121`, `:203-218`, `:96`); the banner (`project/src/main.rs:294-299`); ephemeral-signer friction-free path (`xr-client/scripts/graph_scene.gd:466-471`); other independent dev-bypass sites (`src/settings/auth_extractor.rs:25`, `src/handlers/memory_cloud_handler.rs:66`, `src/handlers/speech_socket_handler.rs:165`).
- Warning signs visible today: the default was deliberately inverted to opt-out; the `.env` sharing hazard is written down but unenforced; the hygiene guard exists only in the release binary; four separate server-side bypass sites each rely on their own gating.
- Confidence: high that the mechanism exists exactly as described; the promotion/`.env` path by which it reached production is inferred.
- Severity: high

### R-2 — The /wss graph data plane has no read authorization: subscribe precedes authenticate, rejection is never signalled, revoked peers keep streaming
- Topics: VC-36.3, VC-36.4, VC-36.15, VC-36.9
- Chain of events: The client connects, sends `requestInitialData` and the subscribe frame, and only then is `Connected` pushed — the optional NIP-98 `authenticate` is sent *after* the stream is live, and its acceptance is never read back. There is no Authenticated state anywhere in the client's machine. A client whose signature is rejected — or a revoked key, or a peer that never authenticates at all — simply remains an anonymous subscriber with no signal. On 401/403 the write is refused but "read stream still served". The stream carries node ids, positions, clusters, communities, anomaly/heat, and 0x23 agent-action frames fanned to *every* /wss client including task-line payloads. A revoked contractor or third party on the network keeps full read of the client's knowledge graph indefinitely.
- Evidence: control frames before `Connected` (`xr-client/rust/src/transport.rs:44-45`, `:100-104`); authenticate sent and ack never read (`transport.rs:108-115`); "the client has no Authenticated state" (VC-36.4 note); "read stream still served" on 401/403 (VC-36.15); `Connected` only after both frames on the wire (`graph_scene.gd:2858-2859`); 0x23 fan-out to every /wss client with task lines (VC-36.9, `binary_protocol.rs:801`).
- Warning signs visible today: the material's own Open item ("a rejected signature leaves the session anonymous with no signal"); ADR-2108 built a visible notice for *denied writes* but nothing covers reads; the diagrammed handshake order puts authorization strictly after data-plane admission.
- Confidence: high — the behavior is directly stated; the confidentiality loss to a client is the inferred impact.
- Severity: high

### R-3 — Codescape exposed on the LAN: OpenAccess command surface behind dev nginx plus an unverified presence identity
- Topics: VC-39.7, VC-39.2, VC-39.5, VC-39.6
- Chain of events: The `codescape` compose profile is enabled at a client site. Dev nginx publishes `^~ /codescape/` on port 3001 (an explicit owner waiver of A2 gap 4), proxying to the main listener on 4100, which runs OpenAccess — reported honestly as "auth open". Any LAN peer can open the voice or command channels. The presence shim accepts the Schnorr signature *unverified*, so the claimed DID is only a label: an outsider claims the operator's DID, is labelled as them in the room roster and on broadcast captions, takes the voice floor (claim per connection, 30 s cap), and issues typed/voice Commands — the command set includes Delete and Transform — against the shared code graph during a client session. NIP-98 verification exists on /wss, but the trust and origin machinery it depends on is only as good as the proxy-trust configuration (see F-03).
- Evidence: OpenAccess (`codescape-server/src/auth.rs:120-124`, `codescape-server/src/routes/mod.rs:69`); LAN-published dev path (`nginx.dev.conf:63-65`, cited as "the owner's dev-only waiver of A2 gap 4"); unverified signature, DID-as-label, 64 members / 256 rooms (`codescape-server/src/xr_presence.rs:20-23`, `:65-67`); typed-Command executor including Delete type 3 (`codescape-server/src/routes/mod.rs:289-351`, `codescape-model/src/wire.rs:119-131`); floor claim per connection (`codescape-server/src/state.rs:181`, `floor.rs:13`); ADR-2143 `implementation_status: partial`, `activation_status: inactive`, P2–P6 open (ADR-2143:6-7, :231).
- Warning signs visible today: the register's own OPEN entries R1/R2/X2, including the doc-drift that claims /ws/presence is unimplemented while the shim route is registered; the whole surface is pre-production auth-wise.
- Confidence: medium — every component is stated; the incident chain (profile enabled on a client LAN with an outsider present) is inferred.
- Severity: high
