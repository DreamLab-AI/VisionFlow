### R-1 — "Deleted" agent memory persists and stays searchable in RuVector; erasure is silently partial
- Topics: VC-22.6, VC-22.1, VC-22.10
- Chain of events: 1) Client demands erasure of their agent's memory. 2) Operator runs the only delete path: `SolidPodService.deleteAgentMemory` → `agentMemory.deleteAgentMemory` builds a container path and calls `deleteResource` (`client/src/services/SolidPodService.ts:366`, `agentMemory.ts:191-194`) → `ldpClient` issues DELETE (`ldpClient.ts:203`). 3) Pod answers 2xx or 404; both count as success (`ldpClient.ts:210-215`). 4) This path makes no RuVector call — "no delete-propagation hook exists in this path" (VC-22.6). 5) The embedding row in external Postgres "persists and stays searchable" (`docs/DATA-authority-erasure.md:87`). 6) The residue is not merely stored: the server now holds a direct read-only RuVector client (`RUVECTOR_PG_CONNINFO`, crate `visionclaw-memory-cloud`, `Cargo.toml:133-138`), "a second consumer" of that row. 7) Client discovers retrievable data after being told it was deleted.
- Evidence: VC-22.6's DIVERGENCE block (tombstone gap) and DRIFT note (second read consumer); VC-22.10's PROPOSED ADR-2102 note describing today's behaviour as "a partial erasure that is … a silent success"; agentbox ADR-2060 (the RuVector-side half) is "referenced, not superseded" — no implementation in this repo.
- Warning signs visible today: the red DIVERGENCE rect in VC-22.6; `deleteResource` treating 404 as success, masking the asymmetry between stores; DATA-authority-erasure.md:87 documents the gap; both remediation ADRs (2102/2060) unimplemented.
- Confidence: high.
- Severity: high.

### R-2 — A force-full sync destroys runtime-governed ontology writes, and Oxigraph has no backup to restore them from
- Topics: VC-22.10, VC-22.11, VC-22.7, VC-21.1
- Chain of events: 1) Over time, classes/axioms are added at runtime through the governed write door (`add_owl_class`/`add_axiom`, `application/ontology/directives.rs`) into the assert graph — they exist only there. 2) A full rebuild runs: `FORCE_FULL_SYNC=1`, `?force_full=true` on `POST /api/admin/sync`, or the boot sync task (VC-21.1). 3) `clear_graph()` wipes GRAPH_KNOWLEDGE (`github_sync_service.rs:384-389`) and `rebuild_assert_graph` replaces the whole assert graph via CLEAR+INSERT (`save_ontology_graph`, `github_sync_service.rs:1004`) — "this CLEAR wipes the ENTIRE assert graph including runtime OWL classes/axioms added via the governed write door (`github_sync_service.rs:930-932`)". 4) Those classes are not in the corpus, so they are not re-derived, and they are "NOT itself in GRAPH_PROVENANCE-protected history for the assert graph". 5) Recovery is impossible: `backup-sqlite.sh`'s required set is the SQLite DBs only (`backup-sqlite.sh:75`, abort semantics `:242-245`); "Oxigraph still has NO point-in-time backup — that bullet stands" (VC-22.11); ADR-2103 is proposed only. 6) The audit trail shares the exposure: GRAPH_PROVENANCE is "restore-only because it cannot be re-derived" (VC-22.7) and is not a backup member — any Oxigraph storage loss is permanent loss of the signed provenance record.
- Evidence: as cited above, all stated verbatim in VC-22.10/22.11/22.7; the destructive path is a documented, operator-reachable feature.
- Warning signs visible today: the VC-22.10 note that runtime writes are wiped by rebuild; the standing no-backup bullet; both remediation ADRs still PROPOSED.
- Confidence: high (the destructive behaviour and absent backup are stated; which trigger fired is inferred).
- Severity: high.
