### R-1 — Encrypted-zone history becomes permanently unreadable after a zone-key distribution failure, because no recovery mechanism exists on main

### R-1 — A rejected tier load leaves the worker publishing the previous scope's positions under the new generation
- Topics: VW-04.6, VW-04.2
- Chain of events: user opens scope B → main thread sends `loadScope` with B's bytes → the worker commits the new generation and node count **before** validating the bytes → `NggExplorer.loadCsr` rejects the tier (corrupt or incompatible bytes; the worker receives only a string error) → the previously loaded tier A stays live and the generation is not marked failed → a later Start message ticks A's simulation and publishes A's positions and count tagged with B's generation → the caller's `nodeCount` for B is never checked against the loaded tier, so the main thread zips B's node ids onto A's coordinates → the client is shown a materially wrong graph (entities at other entities' positions, wrong adjacency) with no error at any layer. Separately, `isMainToWorker` accepts any object with a string `type`, so malformed parameter messages pass unchecked into CSR configuration.
- Evidence: "`loadScope` changes generation/count before validating bytes (physics.worker.ts:271-295). After a rejected tier, a later Start can publish old positions under the new generation. Caller `nodeCount` is not checked against the loaded tier. `isMainToWorker` only checks an object with a string `type` (protocol.ts:195-200)" — labelled a failure boundary by the authors (VW-04.6). Positions are copied from the explorer view into the transport buffer at physics.worker.ts:164-192; `loadCsr` maps errors to a string (src/bindings/explorer.rs:41-45), giving the host no structured failure state. - Confidence: high that the defect exists as documented; inferred that it caused this incident.
- Severity: high

### R-2 — Ontologies larger than `ParserConfig.max_classes` are silently truncated at ingest and rendered as if complete

- Confidence: high that the defect exists; inferred that it caused this incident. The default cap value is not stated, so how easily it is hit is not judgeable.

## Evidence limits

- **Source vs package vs adoption vs deployment.** All defect claims above are claims about source, pinned to commits: vowl-wasm VW-01–VW-05 at `28af4365a68d9aacfd7c04f63299cc96ad717ce3`, VW-06 at `2aff199e2de06f4bba512301acf7023477c492ac`; the visionGraph worker at `7b0875f2c26b9e69dc5c97e9c88166acc14c47dc`. Published-package evidence: the npm registry held only 0.1.2 as of 2026-11-01; 0.2.2 exists as a GitHub release tarball whose npm publication failed and remained open at VW-06's stamp. Consumer adoption: visionGraph pins that **0.2.2 GitHub tarball** under `@dreamlab-ai/vowl-wasm` — a newer sibling repository is not adoption evidence, and no running deployment, traffic or client-facing runtime appears anywhere in this material. All production scenarios are inferred from code-level defects, not observed behaviour.
- **Severity vs reachability vs authority.** Severity grades above assume the defect fires in production; demonstrated reachability varies: R-1/F-14 are in the consumer's own source; R-2 fires whenever the cap is exceeded (cap value unstated); F-08 and F-09 are conditional on unresolved version/registry questions; the SVG renderer's hidden-node omission (VW-01) is explicitly not wired to any binding and is therefore excluded as unreachable through the published JS API.
- **Stateful-failure boundaries (falsification).** R-1's stale-generation state lives in the worker between messages: a worker restart, or a `loadScope` that validates before committing the generation, clears it — correct data after a reload would falsify R-1. R-2's truncation is deterministic per input; only a cap/config change or parser fix alters it.
