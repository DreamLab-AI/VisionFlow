## agentbox#2 / critical

### F-01 — A revoked mandate's WAC grant remains in force at the pod indefinitely
- Topics: AB-11.7, AB-11.8
- Evidence: `revokeMandate` re-signs the kind-30078 record and rewrites the local `registry.json`, but "nothing in agentbox removes or rewrites the `.acl`" (`management-api/routes/mandate.js:238-281`, `management-api/lib/mandate.js:129-152`). The revoking NIP-33 event is never published to any relay — it is only returned in `signed_event` (`routes/mandate.js:264-269`). The pod enforces the `.acl` the caller PUTs, and that ACL still names the revoked agent's DID with its original modes.
- Failure: An operator revokes a compromised agent's mandate. The agent's `Read Write Append Control` grant on the container remains fully live at the solid-pod-rs WAC layer. The agent continues reading and writing the delegated container until an operator manually PUTs a replacement `.acl`, which no code does.
- Confidence: high
- Severity: high
- Marked by authors: yes (Tension under AB-11.7) — but the marker understates that the revocation mechanism is structurally incomplete, not merely a gap: there is no code path that propagates a revocation to the enforcement layer.

### F-02 — JS relay consumer: empty allowlist admits every signed author on public relays
- Topics: AB-13.7
- Evidence: `mcp/nostr-bridge/relay-consumer.js:764-768` — with `ingressPolicy = allowlist`, an empty allowlist ADMITS all. The Rust boundary (`admission.rs:35-45`) treats an empty allowlist as deny-all. Nothing sets `AGENTBOX_RELAY_ALLOWED_PUBKEYS` (`server.js:1434`). The shipped manifest sets `external_fanout = "bidirectional"` (`agentbox.toml:175`), which adds `wss://relay.damus.io,wss://relay.primal.net` to the subscription (`relay-consumer.js:247-255`). Any signed author on those relays whose event p-tags a local npub passes into the governance, intent and payment handlers.
- Failure: A remote actor publishes a signed kind-31400 governance event or a kind-38000 agent-intent event on a public relay, p-tagging the container's npub. The JS consumer ingests it and dispatches it to the intent handler or writes a pod file. The authority gate's separate 31403 responder allowlist is not opened, but intent markers and pod writes are reachable.
- Confidence: high
- Severity: high
- Marked by authors: yes (Tension under AB-13.7)

### F-05 — With the shipped default, every process shares uid 1000 and can read every other's key material
- Topics: AB-16.1, AB-16.7

- Failure: A compromised MCP server, skill process, or agent subprocess reads the sovereign identity key, the bridge signing key, and the per-profile agent key. It can then sign Nostr events, write to pods, and inject commands into any tmux session — all while appearing to be the legitimate container identity.
- Confidence: high
- Severity: high
- Marked by authors: yes (DIVERGENCE under AB-16.1, AB-16.7)

### F-06 — The nostr-gateway daemon signs as the ROOT operator key by default
- Topics: AB-16.5

The attacker now holds the root operator key and can issue commands to any agentbox instance, sign mandates, and impersonate the operator on the relay — not just the gateway's derived child.
- Confidence: high
- Severity: high
- Marked by authors: yes (DIVERGENCE under AB-16.5)

### F-07 — Pod signer uses a one-shot loadFailed latch: a transient key-load failure permanently disables signing for the process lifetime
- Topics: AB-11.13
- Evidence: `getSigner() — lazy, cached, one-shot loadFailed latch (pod-signer.js:104-122)`. If the signer fails to load once (file absent during first boot, a race with another process writing the key file, a transient I/O error), the latch engages and never retries. With `requireSigned` on, every subsequent pod request throws `SigningUnavailable`. With it off, every request goes unsigned.
- Failure: During a container restart, the sovereign identity file is being written by bootstrap while management-api starts and attempts its first pod write. The load fails transiently, the latch engages, and for the entire remaining uptime of the management-api process (potentially weeks), no pod write can be signed. Nobody notices until a pod write fails WAC verification or goes out unsigned.
- Confidence: high
- Severity: medium
- Marked by authors: no

### F-08 — Pod writes are signed with the container's sovereign identity, not the mandate grantee's key
- Topics: AB-11.13

"The per-session mandate grantee is not the key the pods adapter signs with by default" (`AB-11.13 Tension`). The adapter's writes succeed or fail on "the ACL the bootstrap wrote for its own identity" rather than on a mandate.

The write is signed by the container DID, not the agent's DID. The WAC ACL check evaluates the container's identity (which has full access), so the mandate's scoped restrictions are never consulted. The mandate is decorative.
- Confidence: high
- Severity: high
- Marked by authors: yes (Tension under AB-11.13)

### F-11 — Content-addressed identifiers use different hashing on the two sides of the cross-repo bridge, with byte-parity asserted nowhere
- Topics: AB-11.5, AB-17.5
- Evidence: `_contentAddress` hashes a JS `stableStringify` string as UTF-8 (`uris.js:460`), with its own comment saying "deterministic enough beats exactly RFC 8785." VisionClaw `content_address` hashes bytes. "Byte-parity is asserted nowhere" (AB-11.5 DOC-DRIFT). The BC20 bridge computes `sha12(input)` as "SHA-256 over a UTF-8 string, first 12 hex" (`bc20-provenance-bridge.js:132-135`).
- Failure: The same logical payload produces a different 12-hex digest on each side. A `urn:visionclaw:execution:<sha256-12>` that agentbox mints does not match the one VisionClaw computes for the same content. Cross-repo provenance chains silently break: lookups by digest fail, and the injective mapping guarantee of B01 is violated without any error surfacing.
- Confidence: medium — the material states the mismatch exists but does not demonstrate a live collision because the forwarder is already broken (F-04), masking the symptom.
- Severity: medium
- Marked by authors: yes (DOC-DRIFT under AB-11.5, DIVERGENCE under AB-17.10)

### F-12 — CREATE INDEX CONCURRENTLY on the RuVector HNSW access method causes verified double-insertion corruption, but the prohibition is documentation-only
- Topics: AB-20.10

## Not judgeable from this material

1. **The events adapter implementations and their persistence targets.** The execution journal dispatches through the ADR-005 events adapter, and `action-plane.js` explicitly checks that it is not `'off'`. But the material never names which non-off implementations exist, where they persist envelopes, or whether `hydrate()` can actually rebuild state after a crash. Without seeing the adapter implementations, the journal's durability claim cannot be verified.

2. **Runtime deployment configuration versus source defaults.** Multiple findings (F-02, F-06, F-09) depend on whether the running deployment sets the allowlist, changes the gateway identity, or has a forum endpoint configured. The material is source-tracing only and states that runtime configuration "is not visible in source." A running container's actual env vars, manifest values, and supervisor blocks must be inspected.

3. **Whether the NIP-98 proxy's break-glass bearer is configured in the running deployment.** The code paths exist and are drawn (AB-16.6), but whether `NIP98_PROXY_ALLOW_BEARER` is set, what its expiry and scope are, and whether it has ever been used are runtime facts not derivable from source.

4. **The actual durability and recovery properties of the `registry.json` mandate store.** The material shows a read-modify-write pattern with `_saveRegistry` but does not state whether the file write is atomic (temp-then-rename), whether concurrent Fastify requests can interleave, or what happens on a partial write during a crash.

5. **Cross-repo integration testing between agentbox and VisionClaw at the pinned commits.** F-04 (malformed forwarder) and F-11 (byte-parity) are both about the agentbox-to-VisionClaw interface. Whether any contract test exercises the full path — forwarder to ingest to provenance chain — on the current commits, rather than each side in isolation, cannot be determined from the diagrams.

# Post-mortem — custody and authorization failure class

### R-1 — Same-UID custody: with the shipped `role_isolation = false`, every co-resident process can read every signing key and drive every control surface as the operator
- Topics: AB-16.1, AB-16.7, AB-16.13, AB-16.5, AB-11.16, AB-12.6, AB-14.14, AB-11.14
- Chain of events: (1) Any code-mode sub-call, MCP plugin tool, consultant CLI (`spawn-cli.js:47,51` spawns vendor CLIs as the same user, AB-15.12) or skill subprocess runs as `devuser` uid 1000. (2) It reads `/run/secrets/nostr.key` (the bridge/sovereign key, written 0400 devuser, `entrypoint-unified.sh:1121-1130`), any per-profile 0600 agent key (`agent-identity.js:165-166`), the mirror child key, and the ambient `AGENTBOX_PRIVKEY_HEX`/`AGENTBOX_BRIDGE_SK` class variables that stay in PID 1 and reach every child while the flag is off (`entrypoint-unified.sh:395,439`, AB-16.13 branch OFF). (3) Holding the root operator key, it can seal commands the nostr-gateway accepts, because the gateway's default identity is `'operator'` — "out of the box the gateway holds and signs with the ROOT operator key" (`gateway.cjs:154-155`, AB-16.5 DIVERGENCE) — and the sealed-sender check compares against that same pubkey (`gateway.cjs:151,157,673`). (4) It connects to the sessions socket: uid 1000 is in `allowed_uids` by design (`session-plane-acl.json:8-11`, `api.rs:70-76`), so it can send into any session slug, not just the coordinator (AB-12.6 note). (5) It reaches tab0-bridge over loopback, where an empty `BRIDGE_TOKEN` is an open gate (`server.mjs:581`), driving `/tab0/send` and `/nostr/send`. (6) It forges `X-Agentbox-Pubkey` over loopback — `peerIsProxy` accepts loopback peers (`agent-event-auth.js:98-105,117`) — stamping any `did:nostr` into journalled `agent_did` (AB-14.14 Debt) and into agent-event attribution (AB-11.14 Debt). (7) It edits `registry.json` (the mandate registry is a local file) and the BC20 mapping JSONL. Net effect: full identity, control-plane and audit compromise attributed to the operator, with no privilege boundary crossed anywhere.
- Evidence: `agentbox.toml:2543` ships `[security].role_isolation = false`; AB-16.1 N4 "every supervised program, MCP server, skill and agent runs as devuser, so each can read every other's 0600 key file and the mirror key, and uid 1000 is admitted to the session socket by design"; AB-16.7 sequence shows `PEER->KF: read — SUCCEEDS, same uid`, `PEER->BSK: read — SUCCEEDS`, `PEER->SOCK: connect — ADMITTED`; AB-11.16 "a 0600 file is a same-uid boundary only"; AB-16.5 gateway operator-default; AB-14.14 Debt "a same-container process still passes the loopback test and can stamp any pubkey into the journalled agent_did" (TODO-unified X-1); `compose:88-93` — no runtime sudo, root only at boot, i.e. nothing inside the container distinguishes these processes.
- Warning signs visible today: every one of these is already marked — AB-16.1 N4, AB-16.7 DIVERGENCE notes, AB-11.16 DIVERGENCE, AB-16.13 OFF branch, SECURITY-profiles staging role isolation as the remedy, ADR-2122 keeping the flag off until a boot rehearsal.
- Confidence: high
- Severity: high

### R-2 — Mandate revocation never reaches the enforcement point: the pod's WAC `.acl` keeps admitting a revoked delegate
- Topics: AB-11.7, AB-11.8, AB-11.9, AB-11.13
- Chain of events: (1) Operator issues a mandate; the caller — not management-api — PUTs the emitted `acl_turtle` to `<container>.acl`, granting the agent Read/Write/Append (Control is grantable, never default, `lib/mandate.js:39-40`). (2) The pod enforces only that ACL. (3) Operator revokes via `POST /v1/mandate/revoke`: the local registry entry is marked revoked and a kind-30078 with the same `d` tag is re-signed — but "nothing is sent" to any relay (`routes/mandate.js:264-269,280`) and nothing in agentbox removes or rewrites the `.acl` (`routes/mandate.js:238-281`, `lib/mandate.js:129-152`). (4) The revoked delegate's key continues to be admitted by the pod until someone manually replaces the ACL or `expires_at` passes; `isMandateActive` checks only `revoked` and `expires_at` (`lib/mandate.js:191`), and the registry it reads is a local same-uid-writable file (see R-1). (5) Durable effect: the grant lives on the pod's storage; an agentbox restart or rebuild does not touch it — only `expires_at` or manual ACL replacement falsifies the claim that access persists.
- Evidence: AB-11.7 Tension verbatim: "the pod enforces the `.acl` the caller PUTs, while revocation only rewrites the local registry and re-signs the record; nothing in agentbox removes or rewrites the `.acl`, so a revoked mandate's WAC grant stays in force at the pod until someone replaces it"; AB-11.7 Open: "no code in agentbox at this revision publishes a mandate event to a relay" (`routes/mandate.js:230`); AB-11.8: "There is no delete" under NIP-33 replaceable semantics; AB-11.13 Tension: the default pod signer is the container's sovereign identity, so mandates are not even the credential the write path uses.
- Warning signs visible today: the Tension and Open blocks themselves; the unsigned-mandate persistence in AB-11.9; the operator-only listing in AB-11.8 being the only inventory of delegations.
- Confidence: high
- Severity: high

- Marked by authors: yes (Tension in SP-04.8; Drift in SP-01.6)

### F-14 — Group, client and issuer conditions are accepted by the parser but can never grant on this server
- Topics: SP-04.13, SP-04.15, SP-04.1
- Evidence: Every admission context sets `client_id` and `issuer` to None (lib.rs:1093-1094, :1263-1264), so client/issuer conditions are satisfiable only via the `foaf:Agent` shortcut (client.rs:61-64) or never (issuer.rs:57-61). The group resolver is "an EMPTY StaticGroupMembership" (lib.rs:994, :1206; evaluator.rs:38), so "group grants are lost without any error" (SP-04.15 N1). SP-04.1 Tension states the admission context is narrower than the WAC 2.0 vocabulary the evaluator accepts.
- Failure: An operator authors a perfectly valid WAC ACL using `acl:agentGroup` (or a client-class condition) for a partner organisation. Access silently denies for every member; there is no error, no counter (SP-10.12: WAC denials are never counted or logged), and the documented workaround pressure is to replace the scoped grant with `foaf:Agent` — a public grant.
- Confidence: high
- Severity: medium
- Marked by authors: yes (Debt in SP-04.13 and SP-04.15; Tension in SP-04.1)

### F-15 — Replay, payment and trail state are process-local; restart and replicas reopen the windows, and a zero TTL disables replay checks entirely
- Topics: SP-05.5, SP-05.4, SP-10.4, SP-07.7
- Evidence: "Restart forgets ids, replicas do not share state. Reuse is possible while the token remains fresh" (replay_store.rs:115); TTL "is not validated against token freshness. Environment accepts any positive seconds. Constructor also permits zero" (replay.rs:133, :149) — with TTL 0 the seen-entry check `age < TTL` fails and the store takes the "overwrite same slot, accept" branch (replay.rs:260), i.e. every replay is admitted (this last step is inferred from the stated flow). Trail and epoch locks are "in-process and held across network calls — a known gap that a second replica does not share" (CHANGELOG.md:603; trail_store.rs:340); the freshness window alone is ±60 s (nip98.rs:28).
- Failure: A restart or a second replica lets a captured NIP-98 event be replayed for up to its freshness window on each instance; with a mis-set zero TTL, replay protection is off altogether. Two replicas paying out concurrently share no payment lock and can double-spend the ledger. The zero-TTL acceptance itself is unmarked.
- Confidence: high on the stated facts; the zero-TTL consequence is inferred
- Severity: medium (escalates to high the moment the deployment is replicated)
- Marked by authors: yes for the process-local limits (LIMIT notes, "known gap"); no for the zero-TTL admission

## solid-pod-rs / premortem

## Post-mortem — basis and evidence discipline

This analysis is bounded by the diagrams-as-code distillation and the commits it stamps (latest source evidence: `9b6143c` for most topics; `8f2df86` SP-11, `fcc624a` SP-12, `daff10d` SP-13, `c27cdfed` SP-15; consumer pins: VisionClaw `0.5.0-alpha.17`, forum `0.5.0-alpha.18` locked, agentbox rev `76ab7aab`). No release past `0.5.0-alpha.18` (2026-10-29) is recorded; the repairs at `8f2df86`/`fcc624a`/`daff10d`/`c27cdfed` sit under `[Unreleased]` (CHANGELOG.md:7) with no publication evidence. Consumers on published packages therefore predate several stated repairs. Three ranked candidate root causes follow; the material cannot identify which one fired.

### R-1 — Unauthenticated provenance-commit query discloses private resources on every published version
- Topics: SP-07.6, SP-15.3, SP-02.10, SP-09.7
- Chain of events: operator runs a server with the `git` feature (agentbox compiles `forge-full`, which implies `git`; VisionClaw takes `-server` optionally) built from a published `0.5.0-alpha.17`/`alpha.18` package or an earlier pin. Private resources are written and committed into the pod repository with `.prov.ttl` sidecars. An attacker hits the provenance commit endpoint: it resolves Git metadata and the first content path, then reads the resource's current sidecar directly from storage with no resource WAC gate and no check that the sidecar corresponds to the requested commit. The private resource's metadata and sidecar text are returned unauthenticated, while a direct read of the same resource 401s. The repair (caller identity, Read check on the resolved resource, single matching canonical activity) exists only at `c27cdfed`, which is unpublished.
- Evidence: "no resource WAC gate or sidecar commit check … `anchored` is a substring check for `bt:txid`" (`solid-pod-rs-server/src/handlers/prov.rs:413`), sidecar read direct from storage (`prov.rs:391`), commit resolution (`prov.rs:351`); the fixture observation "private resource and sidecar reads returned 401 in the audit fixture, while the unauthenticated commit query returned their metadata and sidecar text" (SP-07.6 Tension); routes registered before the LDP catch-all under `cfg(feature git)` (`solid-pod-rs-server/src/lib.rs:5412`); repair at `c27cdfed` adds Read on the resolved resource (`prov.rs:390`) and commit-matched activity (`prov.rs:409`) (SP-15.3); consumer pins VisionClaw `0.5.0-alpha.17` (`../project/Cargo.toml:246-249`), forum `0.5.0-alpha.18` locked (`../nostr-rust-forum/Cargo.lock:4225-4226`), agentbox rev `76ab7aab` (`../project/agentbox/lib/solid-pod-rs.nix:58`) — all predate `c27cdfed`, which is above the last published release.
- Warning signs visible today: the LEAK drift node in SP-07.6 names the missing gate outright; SP-15.3 exists precisely as the "scoped successor" to this counterexample; SP-09.7 records that the fixes after `76ab7aab` are under `[Unreleased]`.
- Confidence: high (defect demonstrated at fixture level in the material and present in every published package; whether a deployment serves these routes is a deployment fact outside the material)
- Severity: high

### R-2 — MRC20 deposit accepts a one-string trail, so credited balances are self-asserted
- Topics: SP-07.9, SP-07.17, SP-07.19, SP-07.13, SP-07.14, SP-15.5
- Chain of events: the attacker derives the deposit head address from the *configured issuer's public key* — derivation needs no issuer secret. They fund one UTXO at that address on the network the operator's mempool endpoint serves, then POST `/pay/.deposit` with a NIP-98 header, a state whose `ops` transfer a large ticker amount to their own address, and a one-element `stateStrings` proof. `verify_mrc20_anchor` walks "every earlier mark", but with one string mark 0's input is never examined and only the last stateString is compared with `JCS(state)` — the funded head satisfies the walk. `credit_by_outpoint` credits the self-asserted amount to the caller's ticker balance, bounded only by the 21-million-coin per-credit ceiling. The attacker converts through `/pay/.withdraw-sats`, `.swap`, `.buy`, `.sell` (all mounted unconditionally). This defect is open at the latest stamped source: SP-15 repairs payment-state authority and adds a DID-tweaked-beneficiary requirement, but its source list excludes `mrc20.rs` and `blocktrail.rs`, and no proof-length binding is claimed.
- Evidence: head address derived from the public issuer key alone (`solid-pod-rs/src/mrc20.rs:766`); mark 0's input never examined (`solid-pod-rs/src/blocktrail.rs:1114`), `BrokenLink` only for input-less marks (`:1116`); only the last string compared (`mrc20.rs:1061`); nothing on the deposit path rejects a one-string proof (`solid-pod-rs-server/src/handlers/pay.rs:603-620`); credit is whatever `state.ops` transfers (`mrc20.rs:253`) to the ticker balance (`pay.rs:655`) with the 21M ceiling the only bound (`solid-pod-rs/src/payments.rs:469`, `:622`); the whole `/pay/*` surface is registered with no feature flag (`solid-pod-rs-server/src/lib.rs:5282`); issuer/ticker binding (`pay.rs:549`) constrains the issuer key, which is public; SP-15.5's DID-tweak (`pay.rs:610`) constrains the beneficiary — the attacker is the beneficiary; SP-07.17 Tension states "Source tracing at 9b6143c only: no request was sent. Closure is the SP-07.9 binding plus a route test that refuses a one-string proof", and the route tests have no one-string negative case.
- Warning signs visible today: SP-07.9 Tension and N5 ("nothing requires … at least two strings"); SP-07.17 Tension names the missing negative test and the closure criteria; SP-15 does not list this among repairs.
- Confidence: high (source defect, open at `c27cdfed` per the successor's own scope); reachability is inferred — it requires an operator running payments against value on a network the attacker will fund
- Severity: high

### R-3 — agentbox's pinned build ships the pre-repair forge mirror, exposing held upstream objects once follow entries are configured
- Topics: SP-08.18, SP-14.3, SP-14.4, SP-06.12, SP-09.7, SP-01.8
- Chain of events: the operator deploys the agentbox pod tier, whose Nix build pins `solid-pod-rs-server` at `0.5.0-alpha.18` rev `76ab7aab` and adds `forge-full` by default. Following ADR-2010's staged activation, the operator configures `FORGE_MIRROR_RELAYS` and `FORGE_MIRROR_FOLLOW`. The mirror fetches upstream repositories into the store Forge serves — at this pin there is no candidate-store isolation (SP-GIT-02 commits A, B1, B2 are later), so held/unapproved objects sit in the served store hidden only behind ref advertisement. The CGI still runs with `allowTipSHA1InWant=true` (the `1a66c2d` change that sets the want-flags to `false` postdates the pin), and Forge's raw/HTML/JSON/archive readers accept any caller-supplied revision without consulting advertisement. Anyone who learns a commit SHA — from an upstream event, a public fork, or a guess — fetches held upstream content through the operator's forge. Durable effect: the served store's object contents persist until a post-SP-GIT-02 migration rebuilds it, which this pin does not contain; there is no self-healing.
- Evidence: agentbox pin `0.5.0-alpha.18` at `76ab7aab` (`../project/agentbox/lib/solid-pod-rs.nix:54-58`) with `forge-full` unless disabled (`../project/agentbox/flake.nix:1548`); "`76ab7aab` … predates both the hidden-tip repair and the SP-GIT-02 store isolation. A shipped agentbox build therefore carries the pre-repair mirror; it stays inert only while no follow entries are configured" (SP-08.18 Tension); pre-repair boundary was "hiding `refs/mirror` only changed what smart-HTTP advertised; Forge's raw, HTML, JSON and archive readers call local Git with a caller-supplied revision" (SP-14.3); the want-flag change is `1a66c2d`, 2026-11-01, after the alpha.18 release of 2026-10-29 (`solid-pod-rs-git/src/service.rs:425-432`, SP-06.12 Drift); boot migration of legacy stores exists only in the post-repair code (SP-14.4).
- Warning signs visible today: the SP-08.18 Tension paragraph and the SP-09.7 agentbox-pin debt state the lag explicitly; ADR-2010's own review qualification says compiling `forge-full` does not prove held objects cannot be served.
- Confidence: medium (the shipped-pin defect is stated with high confidence; the triggering configuration and the value of exposed content are deployment facts the material cannot show — inferred)
- Severity: high

## Further latent defects

### F-01 — Payment state read-failure fallback can overwrite the authoritative ledger with stale mirrors
- Topics: SP-07.15, SP-15.4
- Evidence: "any get error falls back to legacy files" (`solid-pod-rs-server/src/handlers/pay.rs:184`) and the next successful commit replaces canonical state (`pay.rs:198`), losing intents and resetting the version (SP-07.15). The repair — "only NotFound selects legacy migration" (`pay.rs:191`, `:196`) — exists only at `c27cdfed`, unpublished; published `alpha.17`/`alpha.18` carry the old behaviour.
- Failure: a transient storage read error during a payout window makes handlers operate on stale legacy mirrors; the next successful write commits those mirrors as canonical, erasing debit intents — already-broadcast payouts reappear as balances and can be withdrawn twice. Durable effect: the overwrite is the commit itself; a restart does not restore the lost intents, and no reconciliation path is described.
- Confidence: high (source; trigger requires a read error)
- Severity: high
- Marked by authors: yes (Drift node FALL in SP-07.15)

### F-02 — Whole-history Git export sits behind a root-Read gate, and the routing/authority halves of the fix are separable

- Chain of events: Curation corrects or removes content → visionGraph publishes and sends `corpus-sync` carrying source repo + source SHA only (`publish.yml:536`) → the VisionClaw workflow builds the pod bundle, recording `sourceSha` and `buildSha` = its own `GITHUB_SHA` (`pack-pod-resources.py:116`) → the rolling `ontology-latest` release is updated (`ontology-publish.yml:305`) → at boot/periodic pull, the server compares **only stored `buildSha`** (`ontology_pull.rs:312`) → VisionClaw's default-branch head is unchanged between the two corpus updates, so `buildSha` matches → the puller **skips before even downloading the checksum manifest** (`ontology_pull.rs:312`) → the pod keeps activating source A's generation while source B is live; the fire-and-forget event means no acknowledgement ever alerts anyone (`publish.yml:536`; `ontology_pull.rs:40`). **Durable effect / retry boundary:** the stored `buildSha` in the pod index is the persistent state; a server restart re-runs the identical comparison and skips again — restart does **not** heal this. Only a new VisionClaw commit, manual generation deletion, or a changed comparison would.
- Evidence: The material states the puller "compares stored buildSha only and requires an existing atomic generation" (`ontology_pull.rs:312`, `:320`, `:337`) and marks "same build SHA skips new source SHA before downloading checksum manifest" as DEBT; the current-source tests **reproduce** "source A active when source B arrives with the same build SHA" (`pack-pod-resources.py:117`, `ontology_pull.rs:312`) — source-level, visionclaw commit 75b7241. "Request delivery is not downstream completion" (`publish.yml:536`); pull wired into startup (`src/main.rs:917`, `ontology_pull.rs:295`, `:389`).
- Warning signs visible today: the freshness axis that is *recorded* (`sourceSha`) is not the axis that is *checked* (`buildSha`); the material's own tests already demonstrate the stale retention; the dispatch event carries the source commit, not the assembled corpus digest, so no downstream detector exists.
- Confidence: high — the defect is reproduced by the cited tests; only the assumption that no intervening VisionClaw commit occurred in the incident window is inferred.
- Severity: high
