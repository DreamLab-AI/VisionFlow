## Root causes, most likely first

### R-1 — The daemon never ran the extracted engine: the merge that fixed the rules was never deployed, so "guard before apply", the finished-night rule and the corrected dry streak were absent in production for the entire period
- Topics: DE-01.2, AB-23
- Chain of events:
  1. The extraction completes: five crates published at 0.1.0, adapter pins `dream-core`/`dream-gate` `=0.1.0` merged on agentbox `main` as PR 28 (aa9b094c3) on 2026-10-16.
  2. The image rebuild is left as "the operator's step" with no gate, deadline, or alert tying merge to deployment.
  3. The daemon keeps running the pre-extraction binary. Three behaviours are explicitly named as absent from the supervised engine: guard before apply, the finished-night rule, and the corrected dry streak.
  4. A nightly run eventually reaches the condition those rules were written for — most plausibly a finished night being re-entered and re-run/overwritten (finished-night rule absent), or an apply step executing without the new guard.
  5. The old binary takes the destructive action; client data is overwritten, duplicated or applied unguarded. Nothing in the system detects it, because the fix exists only in a merged-but-undeployed commit.
  6. The defect persists indefinitely: agentbox CI has been dead since 2026-10-08, so no pipeline ever fails on the deploy gap.
- Evidence: "NOT YET LIVE: the image rebuild is the operator's step, until then guard before apply, the finished-night rule and the corrected dry streak do not run in the supervised engine" (`../project/agentbox/docs/adr/ADR-2141-extract-the-dream-engine-core-into-a-standalone-permissive-repo.md:40`); "the running daemon is still the pre-extraction binary" (Open (activation), DE-01.2); "the agentbox repository's GitHub Actions have not run since 2026-10-08 … PR 28 merged with no CI gate" (Debt, DE-01.2).
- Warning signs visible today: the document itself says NOT YET LIVE and names three absent safety rules; the word "corrected" concedes the pre-extraction dry-streak logic was wrong, i.e. production was known to be computing streaks incorrectly; merge-to-deploy has no completion criterion.
- Confidence: high that the dormant deployment is real (stated flatly); the causal link to this specific incident is inferred
- Severity: high

### R-2 — Publish outcomes are at-most-once and never reconciled after a crash: a crash in the publish window leaves ledger and forge permanently divergent, losing or duplicating a client's deliverable
