## visionclaw#3 / critical

### F-01 — The graph position stream is served to clients without valid credentials, and an auth failure is silent
- Topics: VC-36.3, VC-36.4, VC-36.15
- Evidence: VC-36.15 states that with dev mode off, on "no or insufficient credential" the server answers "401 or 403 - drag/pin refused, **read stream still served**" (`src/utils/auth.rs:191`, `graph_scene.gd:1253`, `hud.gd:1436`). VC-36.3's diagram asserts the order: `requestInitialData` and `GRAPH_SUBSCRIBE` are sent immediately on connect (`transport.rs:44-45`), `Connected` is pushed after those control frames (`transport.rs:104`), and NIP-98 `authenticate` is only sent afterwards and only "opt nostr_secret_hex non-empty" (`transport.rs:108-115`). VC-36.3 marks it Open that the client "never reads an acknowledgement, so a rejected signature leaves the session anonymous with no signal" (`transport.rs:113`); VC-36.4 confirms "The client has no Authenticated state."
- Failure: In a correctly hardened production deployment, any network peer who can reach `/wss` subscribes to the full knowledge-graph stream with no credential at all, and a headset whose NIP-98 signature is rejected reads everything indefinitely while believing it is signed in — it learns of the downgrade only when a write is denied (VC-36.15's notice).
- Confidence: high; the only unstated element is whether some undocumented connect-time gate exists server-side (inferred absent from the diagrams)
- Severity: high
- Marked by authors: no (the missing auth-acknowledgement carries an Open marker at VC-36.3; the open read stream itself is stated without any marker)

### F-02 — Dev deployments boot with a default-armed, peer-agnostic full authentication bypass
- Topics: VC-36.15
- Evidence: `VISIONCLAW_DEV_MODE: "${VISIONCLAW_DEV_MODE:-1}"` (`docker-compose.unified.yml:95`) since ADR-2108 (2026-09-08), so "launch.sh up dev boots an ARMED backend and the operator opts OUT". When active, "Every request granted as DEV_MODE_PUBKEY" (`src/utils/auth.rs:96`) and REST grants are a "LAN-local FULL bypass, peer-agnostic: no NIP-98, no token, no peer check" (`src/utils/auth.rs:203-218`), with further bypass sites at `src/settings/auth_extractor.rs:25`, `src/handlers/memory_cloud_handler.rs:66`, `src/handlers/speech_socket_handler.rs:165`. The material's own caveat: "both services load env_file .env, so the var must never sit in a .env shared with prod — sharper now that the compose default supplies it unasked" (`docker-compose.unified.yml:92-94`).
- Failure: A dev compose brought up with defaults on the shared LAN (the 25G rail / LAN topology of VC-36.16) grants full admin — physics writes, layout, memory, speech — to every LAN peer with no credential and no peer check; a copied `.env` or a dev-auth build promoted toward prod carries the bypass with it. The release-binary exit-2 guard (`src/main.rs:136`, `:161`) protects only release builds.
- Confidence: high
- Severity: high
- Marked by authors: partially (the default flip and the `.env` caveat are documented; the peer-agnostic full-bypass exposure is described but not flagged as a risk)

### F-05 — Route arbitration compares unrebased wall clocks, so clock skew silently kills the memory-route feature
- Topics: VC-38.8, VC-38.12
- Evidence: "sent_at is Unix milliseconds on both paths, the relay's sentAt passed through unrebased and the headset's own `Time.get_unix_time_from_system()` … a headset clock ahead of the desktop's makes desktop frames Stale until the desktop catches up and a clock behind does the reverse; nothing states the unit or bounds the skew" (`xr-client/rust/src/memory_route.rs`, `xr-client/scripts/memory_cloud_layer.gd:491`); likewise the headset's own query route "sent_at is the headset's own wall clock, so a later desktop relay replaces it only while the two clocks agree" (`memory_route.rs:1596`).
- Failure: A headset with a few seconds of NTP skew never shows a single desktop-relayed route (all judged Stale), or the headset's own query routes and the desktop's fight each other unpredictably — with no error anywhere, the feature just goes dark or flaps.
- Confidence: high
- Severity: medium
- Marked by authors: yes (Open, VC-38.8)

## Three most likely root causes

### R-1 — The dev-mode full-auth bypass is armed by default and peer-agnostic: any LAN peer becomes "dev-mode-local-admin" on the vault-mounting container
- Topics: VC-36.15, VC-36.11, VC-39.2
- Chain of events: A dev/unified backend is booted with the documented compose default (`VISIONCLAW_DEV_MODE:-1`, flipped by ADR-2108 on 2026-09-08). The dev nginx on port 3001 is reachable from the LAN (the material shows LAN clients hitting it, and the Codescape `/codescape/` path is LAN-published "by owner decision"). Any peer on that segment — no NIP-98, no token, no peer check — is granted every request as `DEV_MODE_PUBKEY = "dev-mode-local-admin"`, a power user, on the REST chokepoint (`src/utils/auth.rs:203-218`) and auto-granted on the `/wss` authenticate frame (`src/handlers/socket_flow_handler/filter_auth.rs:28`, `:43`). That container is `visionclaw_container`, which mounts `/vault` and carries the RuVector connection string. An anonymous party obtains full write access to the knowledge estate and everything the vault holds; because every bypassed request is attributed to the same constant identity, nothing in the logs distinguishes the intruder from the operator.
- Evidence: `docker-compose.unified.yml:95` arms the default and is labelled "DEV SERVICE ONLY"; `project/src/main.rs:296-299` grants as `DEV_MODE_PUBKEY`; `src/utils/auth.rs:96`, `:116-121`, `:203-218` (peer-agnostic full bypass); the release-build refusal (`project/src/main.rs:109`, `:136`, `:161`) protects only release binaries. The material's own caveat: "both services load env_file .env, so the var must never sit in a .env shared with prod — sharper now that the compose default supplies it unasked. `docker-compose.unified.yml:92-94`". Four further bypass sites exist: `src/settings/auth_extractor.rs:25`, `src/handlers/memory_cloud_handler.rs:66`, `src/handlers/speech_socket_handler.rs:165`, plus the still-constructed dev bearer (`graph_scene.gd:94`, `:470`, `:1214`).
- Warning signs visible today: the armed-by-default flip is documented as ADR-2108; the `.env`-sharing hazard is written down; the bypass is explicitly described as "LAN-local FULL bypass, peer-agnostic: no NIP-98, no token, no peer check"; the material also records the dev bearer "DIVERGENCE" as still live client-side.
- Confidence: high
- Severity: high

### R-2 — Codescape runs with authentication open while its nginx path is LAN-published: unauthenticated command execution and code-graph disclosure
- Topics: VC-39.2, VC-39.5, VC-39.7
- Chain of events: Codescape is activated for real use. Its main listener (port 4100) runs OpenAccess (`codescape-server/src/auth.rs:120-124`, `routes/mod.rs:69`), and the dev nginx publishes `/codescape/` on port 3001 to the LAN by owner decision (`nginx.dev.conf:63-65`, recorded as the owner's waiver of A2 gap 4). Anyone on the segment opens the web client with no credential, receives the client codebase's position stream and graph, and can issue typed or voice commands — the final transcript goes through the same executor as typed commands (`routes/mod.rs:289-351`), and the command set includes delete-type actions (`codescape-model/src/wire.rs:119-131`, types Query/Update/Create/Delete). The same party joins `/ws/presence` claiming any DID, because the shim "accepts the Schnorr signature unverified, the claimed DID is only a label" (`codescape-server/src/xr_presence.rs:20-23`, `:65-67`). Result: disclosure of a customer's code-graph structure, mutation of the shared scene under a spoofed identity, and no audit trail that resists dispute.
- Evidence: register rows VC-39.7 R1 ("OPEN until P6: the main port runs OpenAccess... while port 3001 /codescape/ is LAN-published in dev by owner decision") and R2 (unverified presence shim, bounds 64 members/256 rooms); ADR-2143 is `implementation_status: partial`, `activation_status: inactive` (`:6-7`) with P2–P6 open (`:231`); voice execution path `routes/voice.rs:192-372` with `execute(Command)` at `routes/mod.rs:348-351`; port 4100 published to 127.0.0.1 only by default (`docker-compose.unified.yml:526`) but the 3001 path is the LAN surface.
- Warning signs visible today: the register carries both rows as OPEN; the ADR itself waives the publication gap; nothing in the material shows an auth layer shipped since.
- Confidence: high
- Severity: high

### R-3 — All client traffic runs over plaintext ws:// and http:// with an unacknowledged NIP-98 handshake: LAN capture of the stream and a silent anonymous downgrade
- Topics: VC-36.3, VC-36.4, VC-36.10, VC-36.11, VC-36.16, VC-38.12
- Chain of events: The documented deploy is `XR_BACKEND_WS=ws://<lan-host>` (VC-36.16) — cleartext WebSocket to a LAN address — and `_http_base` derives `http://` from a `ws://` base for every REST write (`graph_scene.gd:1311`). Everything crosses that channel in the clear: the graph position stream, memory-cloud metadata, memory-search query text and hit keys (`memory_search.gd:206`, `memory_query.rs:540`), and the `Authorization: Nostr <b64>` kind-27235 headers (`graph_scene.gd:1212`, `signer.rs:128`). Anyone on the segment reads the estate's data; captured Authorization headers are replayable to the extent the server's kind-27235 timestamp tolerance allows (replay tolerance is nowhere stated — inferred). Independently, the client never reads an acknowledgement of `authenticate` (`transport.rs:108-115`, Open at `:113`), so a rejected signature leaves the session anonymous with no signal — the capture or a key rotation degrades silently.
- Evidence: `graph_scene.gd:72` default `ws://localhost:4000`; VC-36.16 launch line `XR_BACKEND_WS=ws://<lan-host> (port 4000)`; VC-36.10 "nginx :3001 does NOT proxy /ws/presence — the client points at the LAN backend directly"; `transport.rs:113` Open note; `graph_scene.gd:1206-1207` exact-URL signing invariant.
- Warning signs visible today: plaintext defaults and ceremony are documented as the verified path; the unacked-authenticate gap is carried as Open in two topics (VC-36.3, VC-36.4 state diagram has no Authenticated state).
- Confidence: medium (cleartext transport is stated; replay viability and tolerance are inferred)
- Severity: high
