## agentbox / critical

### F-01 — Identity forgery via X-Agentbox-Pubkey is live in the verified revision; the fix post-dates it
- Topics: AB-10.14, AB-11.14, AB-03.2
- Evidence: Path 2 of `verifyAgentEventRequest` trusts `X-Agentbox-Pubkey` when it is 64-hex, from any TCP peer (`agentbox/management-api/lib/agent-event-auth.js:90-96,:157-160`), and `resolveAgentDid` does the same (`agentbox/management-api/lib/action-plane.js:221-231`), while `server.js` binds `0.0.0.0` (`server.js:49`) on the shared `visionclaw_network`. The material states outright: "at the stamp path 2 trusted the stamp from any TCP peer so a MANAGEMENT_API_KEY holder on the docker network could forge it" and "The stamped lineage does not contain the commit" — the loopback-only fix (`proxyVerifiedPubkey`/`peerIsProxy`) is agentbox main `b9e0ea9a8`, after `verified_commit 3f05ae9e`.
- Failure: any sibling container holding `MANAGEMENT_API_KEY` (bearer passes the general gate) sends a forged header and emits agent events / action-plane dispatches as **any** `did:nostr`, including the operator's; `reconcileSourceUrn` passes because the claimed URN matches the forged identity, poisoning the audit chain and CTC attribution.
- Confidence: high
- Severity: high
- Marked by authors: yes (Drift "resolved 2026-10-12 on main" — but they themselves note the stamped lineage still has the behaviour)

### F-02 — The host Docker socket is chmod'd world-rw every boot and never narrowed
- Topics: AB-02.24, AB-06.13, AB-06.1
- Evidence: flag-off (the shipped default, `agentbox.toml:2414`) runs `chmod o+rw` on the host socket **every boot** (`entrypoint-unified.sh:589-592`); the socket is bound rw into agentbox in the default overlay (`docker-compose.override.yml:117`); under `role_isolation` the entrypoint "stops widening it but never narrows it" and "the socket is the HOST inode, earlier boots left it o+rw, and only a host-side chmod 0660 narrows it" (OPEN R2, `docker-compose.override.yml:116-117`); the custody design itself concedes "while devuser can drive it every in-container boundary is void".
- Failure: every agent session, MCP server and hook runs as devuser; any of them connects to the host daemon directly (the GET-only `/run/docker-ro.sock` is not a boundary when the real socket is reachable) and mounts the host root — host-level escape from the primary workload.
- Confidence: high
- Severity: high
- Marked by authors: yes (custody W0/W1, OPEN R2)

### F-03 — All keys and tokens are same-UID devuser files; profile isolation is not an OS boundary

Every agentbox process runs as devuser, so co-resident code can read the agent key, the bridge key and the AoE daemon token alike" (AB-11.16 DIVERGENCE); agent key persisted 0600 devuser (`agent-identity.js:164-166`), `nostr.key` 0400 devuser under flag-off (`entrypoint-unified.sh:1020`); "profile isolation routes configuration under ONE OS user devuser … it is NOT an OS access boundary" (AB-02.12).
- Failure: one malicious skill/plugin/hook exfiltrates the box's signing keys and the AoE daemon token in a single read; it can then sign and publish as the box off-host, and impersonate any profile's persisted `did:nostr`.
- Confidence: high
- Severity: high
- Marked by authors: yes (DIVERGENCE; GOVERNANCE-capabilities item 5 as future work)

### R-1 — Host escape through the always-widened Docker socket (role_isolation ships off)
- Topics: AB-06.13, AB-02.24, AB-05.16, AB-06.1, AB-11.16
- Chain of events:
  1. Ordinary agent workload executes arbitrary shell as devuser — orchestrator `spawnAgent` (AB-04.13), the voice bridge's Bash allowlist (AB-12.7), skills, hooks.
  2. The host Docker socket is bound rw into agentbox (`docker-compose.override.yml:117`); with `role_isolation` off (the shipped default), the entrypoint `chmod o+rw`'s it **every boot** (`config/entrypoint-unified.sh:589-592`), so devuser can drive the host daemon.
  3. The daemon is host root: run a privileged container, mount host paths, `docker inspect` every sibling for env (MANAGEMENT_API_KEY, NOSTR keys, Loom keys), read the vault host binds and NAS backup targets.
  4. `role_isolation` stays false (`agentbox.toml:2414`, setup default `agentbox.default.toml:1729`) pending the owner's rehearsal — and even once flipped on, the socket is the **host inode**, still `o+rw` from earlier boots until a host-side `chmod 0660` (OPEN R2); the entrypoint never narrows it.
  5. Client corpus is exfiltrated or destroyed from the host side; no in-container audit surface records host-side actions.
- Evidence: `../project/agentbox/docker-compose.override.yml:117`; `../project/agentbox/config/entrypoint-unified.sh:589-592`; `../project/agentbox/agentbox.toml:2414`; AB-06.13 — "The Docker daemon is root on the host, so while devuser can drive it every in-container boundary is void (custody design §0, bypass 1)" and OPEN R2 "only a host-side chmod 0660 narrows it"; AB-02.24 invariant "With the flag off … the entrypoint does not widen … it still runs `chmod o+rw` on every boot" (AB-06.13 E0).
- Warning signs visible today: the compose comment itself registers R2/Q2 as an open owner question; `role_isolation` is false in the live manifest and the setup default; the custody design names this as bypass 1; `degraded docker-socket` is only even *recorded* when the flag is on.
- Confidence: high (the bypass is stated outright; only the specific triggering workload is inferred).
- Severity: high

### R-2 — Same-UID identity forgery: in-container code acts as anyone, then trims the audit tail

- Evidence: "a process inside the agentbox container can still stamp any pubkey over loopback (TODO-unified X-1), so attribution on the session and break-glass hop is bounded by the same-UID boundary" (`agent-event-auth.js:157-160`, marked Debt in ES-02.1 and ES-04.1). ES-05.11: "Same-UID process → Application gate does not establish OS isolation". With `role_isolation` off — "the shipped default" (ES-10.12) — "the entrypoint widens the host Docker socket o+rw for devuser" (`entrypoint-unified.sh:589-593`), and even under the flag the socket "is the HOST inode, already widened by earlier boots... only a host-side chmod does" (ES-10.12 Open).
- Failure: one compromised or buggy process inside the container emits agent-events and journal entries under any operator/agent `did:nostr` it chooses (poisoning governance attribution and VisionClaw's rendered provenance), reads the AoE token and `.env`, and via the raw socket is host-root.
- Confidence: high
- Severity: high
- Marked by authors: yes (Debt, TODO-unified X-1; the socket state is an explicit Open)

### F-07 — Pod writes can silently go unsigned at three layers, including a degraded-boot placeholder identity
- Topics: ES-08.2, ES-04.4, ES-08.3
- Evidence: the adapter's signing is off unless `integrations.solid_pod_rs.sign_requests=true` — "default keeps prior unsigned behaviour byte-identical" (`pod-signer.js:34-35`); ADR-2064 closed the fail-open only "with sign_requests on... It remains reachable only with the flag off, where unsigned is the declared baseline" (ES-08.2). The client path degrades the same way: "opt signRequest throws → logger.warn NIP-98 signing failed, request proceeds unsigned" (`ldpClient.ts:112`) — unmarked. And "the did:nostr:local placeholder fallback that agent-identity.js:41-43 says the entrypoint still runs unconditionally" means "a degraded boot can silently produce a NON-SOVEREIGN identity" (ES-04.4, marked DIVERGENCE).
- Failure: with the default configuration, pod writes leave the box unauthenticated — either silently denied by WAC (users see opaque 403s with a warning buried in client logs) or, wherever anonymous access is permitted, applied with no attribution; a degraded boot mints and uses a fake identity without any operator signal.
- Confidence: high
- Severity: high
- Marked by authors: yes for the agentbox half (DIVERGENCE, ES-04.4; RESOLVED-with-flag-on framing in ES-08.2); the `ldpClient` warn-and-proceed-unsigned arm is unmarked

### F-08 — Neither governance rationale gate can fire on a VisionClaw case, and the two gates read different tiers
- Topics: ES-05.12, ES-05.13, ES-05.14

- Confidence: high
- Severity: medium
- Marked by authors: yes (OPEN, DIVERGENCE, Tension)

### F-10 — MCP startup overrun disables the email server for the entire session, and the durable fix is not yet deployed

- Severity: medium

### F-11 — Cross-repo identifier integrity rests on unenforced conventions: untyped hash equivalence, stale contract versions, a compile-time cross-repo artefact, and a pin that is ahead
- Topics: ES-03.6, ES-03.9, ES-09.20, ES-01.1, ES-09.1

### F-13 — Replay-cache saturation refuses all new authentication, and the cache appears fillable with self-signed tokens
- Topics: ES-04.3
- Evidence: on a full replay cache "the code REFUSES new auth (ReplayCacheFull) and must NOT evict... Bounded memory beats availability" (`nip98.rs:189-197`, `:307`). - Failure: a remote attacker mints unlimited self-signed fresh tokens and fills `REPLAY_CACHE_MAX_ENTRIES`, after which every legitimate login, WebSocket upgrade and pod write in the estate is refused until TTL pruning recovers — an unauthenticated-feeling DoS of the whole NIP-98 auth plane, delivered by the deliberate fail-closed design.
- Confidence: low; inferred — the material does not state whether unknown-pubkey tokens reach the claim step, or the cache size relative to mintable events
- Severity: medium
- Marked by authors: no (fail-closed-under-flood is framed as an INVARIANT; exploitability is unexamined)

### F-14 — Privacy redaction and governance publication both fail open with near-invisible logging

- Confidence: medium (the arms are stated; the deployed `OPF_MODE` value is not)
- Severity: medium
- Marked by authors: no (both are presented as contracts/behaviour, not as risks)

### F-15 — Secrets custody is unaudited in practice: plaintext .env, per-boot session invalidation, incoherent token rotation, an unbounded break-glass, and an everything-admitted house key
- Topics: ES-10.10, ES-04.5, ES-05.15

### R-2 — Erasure failure: the documented pod-delete path never reaches RuVector, so "deleted" client memory stays semantically searchable forever, with no backup, journal or restore
- Topics: ES-08.9, ES-07.9, ES-08.8, ES-07.1
- Chain of events: (1) A client (or operator on their behalf) deletes agent memory via `SolidPodService.deleteAgentMemory:363` → `agentMemory.ts:196-204` → `ldpClient.deleteResource:206`; the pod returns 204 and the deletion "succeeds". (3) The embedding row "persists and stays semantically searchable" — ES-07.9 D5 calls this the "Largest erasure hole". (4) Rows are pubkey-scoped (agentbox.toml:379-395), so the subject's own namespace still surfaces them via `memory_search`. (5) Invariant 6 of DATA-authority-erasure requires a dropped secondary write to be logged — "this call path does not even attempt the secondary write, let alone log its absence". - Evidence: agentMemory.ts:41,196-204; ldpClient.ts:206-216; ES-07.9 D5 (`allow_namespace_repair=false`, agentbox.toml:505); ES-08.8 FATAL note citing docs/DATA-authority-erasure.md Known divergences; ES-07.1 SCOPE.

- Confidence: high — the gap is stated in two independent topics.
- Severity: high

### R-3 — Custody loss by same-UID agent escape: default-off role isolation, a widened host Docker socket, bypassPermissions defaults and evadable deny rules
- Topics: ES-10.12, ES-05.10, ES-05.11, ES-10.10, ES-02.1, ES-04.1, ES-01.5, ES-04.5
- Chain of events: (1) `[security].role_isolation` ships false. (2) "the entrypoint widens the host Docker socket o+rw for devuser" (entrypoint-unified.sh:589-593); the socket is the HOST inode, "already widened by earlier boots", and skipping the chmod "does not narrow it" (entrypoint-unified.sh:589-612). - Evidence: entrypoint-unified.sh:589-612; role-accounts.json:20-120; agentbox.toml:647-662; agent-event-auth.js:157-160; ADR-2122:231-232; ES-09.1 ENVFACT (host Docker socket mounted).

### F-01 — Drag and drag-end broadcasts send the entire graph including private nodes to every connected client
- Topics: VC-13.2, VC-03.9
- Evidence: The snapshot path applies `PUBKEY_VISIBILITY_FILTER` via `compute_private_opaque_ids` + `apply_drop_set` (`position_updates.rs:704-715`), but the drag handlers "encode the whole graph with default class ids and reach every client through `broadcast_to_all`" and "neither the pubkey drop-set of the snapshot path nor the pre-flagged type bits of fetch_nodes apply to these frames, ADR-2003 is not honoured here" (`position_updates.rs:1204-1211`). The visibility filter is documented as default-ON and fail-closed for anonymous sessions (`position_updates.rs:17-40`), yet the drag broadcast path bypasses it entirely.
- Failure: Any authenticated user drags any node. The `nodeDragUpdate` handler sends `BroadcastNodePositions` encoding every node in the graph — including nodes marked private and owned by other users — to every connected WebSocket client. A viewer-role user in a multi-tenant deployment receives the full private node set of every other tenant during any drag interaction.
- Confidence: high
- Severity: high
- Marked by authors: yes (TENSION)

### F-02 — /ws/client-messages accepts any non-empty token string without verifying it against NostrService
- Topics: VC-04.25
- Evidence: "the token's CONTENTS are never verified against NostrService, only its presence, so any non-empty string passes" (`client_messages_handler.rs:131-142`). The handler extracts `Authorization: Bearer` or `?token=` and only checks non-emptiness. The in-code comment says "Currently allows but logs unauthenticated connections" but the code "actually REJECTS an empty token with 401" — the verification gap is the unverified contents.
- Failure: An attacker connects to `/ws/client-messages` with `Authorization: Bearer x` (any single character). They receive the full stream of client messages including `content`, `session_id`, and `agent_id` for every message sent to any session. No cryptographic proof of identity is required.

- Severity: high

### F-03 — NIP-98 replay cache is process-local with no cross-replica protection
- Topics: VC-03.4
- Evidence: "Process-local scope — no cross-replica replay protection (SECURITY-profiles.md)" (`src/utils/nip98.rs:221`, `REPLAY_CACHE`). The cache is `Mutex<HashMap>` behind a process-local static. A replayed token claimed on replica A is still admissible on replica B.

The signature verifies, the URL and method match, and the replay cache on this replica has never seen the event ID — the request is admitted. ### R-1 — The ADR-2003 pubkey visibility filter never applies to the position broadcast paths, so private nodes are continuously disclosed to every connected WebSocket client
- Topics: VC-13.2, VC-13.3, VC-03.9, VC-13.6
- Chain of events:
  1. Two tenants (or a customer plus a low-privilege contractor account) connect to `/wss`. In a release build the upgrade requires authentication (VC-03.2), so both hold valid sessions — one may be a mere Viewer.
  2. Physics runs. Every rate-limited broadcast step (`UpdateNodePositions` → `PhysicsOrchestratorActor` → `ClientCoordinatorActor.broadcast_with_filter`) serializes **all finite nodes** into a V5 frame; the `BroadcastOptimizer`'s `visible_indices` are visibility-culled only with culling off by default and "the caller ignores them and sends every finite node" (VC-13.3, broadcast_optimizer.rs:7-11, 235-259).
  3. The per-client filter applied by the coordinator is a *node-id subscription filter* defaulting to disabled — "client.filter.enabled == false (default per-client node filter) → try_send(SendToClientBinary(unfiltered_binary clone))" (VC-13.3, client_coordinator_actor.rs:431-455). The record states this is "a SEPARATE mechanism from the pubkey visibility drop-set filter, which gates the one-shot snapshot (fetch_nodes …) and initial state sync, **not this ClientCoordinatorActor broadcast**" (VC-13.3 note, citing position_updates.rs:15-24).
  4. Independently, any drag makes it worse: "the drag and drag-end broadcasts encode the whole graph with default class ids and reach every client through broadcast_to_all, so neither the pubkey drop-set of the snapshot path nor the pre-flagged type bits of fetch_nodes apply to these frames, ADR-2003 is not honoured here" (VC-13.2 TENSION, position_updates.rs:1204-1211, binary_protocol.rs:580-586, client_coordinator_actor.rs:1475).
  5. The other tenant captures frames containing ids, positions, velocities, SSSP distance/parent, cluster, anomaly, community and centrality for private nodes they do not own. Customer audit finds private node existence, geometry and analytics leaving the server; contract lost.
- Evidence: VC-13.2 TENSION note (position_updates.rs:1204-1211; binary_protocol.rs:580-586; client_coordinator_actor.rs:1475); VC-13.3 note separating the two filter mechanisms and the BroadcastOptimizer full-snapshot behaviour (broadcast_optimizer.rs:7-11, 235-259; client_coordinator_actor.rs:431-455); VC-03.9 stating position_updates.rs "is the real site" of `PUBKEY_VISIBILITY_FILTER` and that client_filter.rs is a different filter; VC-13.6 showing the drop-set applied only on the one-shot `fetch_nodes` snapshot (position_updates.rs:704-715).
- Warning signs visible today: the TENSION note in VC-13.2 explicitly says ADR-2003 "is not honoured" on the drag path; VC-13.3 explicitly scopes the drop-set filter to the snapshot only; VC-03.9 records that the drop-set encoder was inert on the tick path until 2026-08-31 — the filter has a history of not being wired where it matters.
- Confidence: high — the bypass is stated in the record; the incident realization (a second party capturing frames) is inferred.
- Severity: high

### R-2 — RBAC role deletion is not revocation: offboarding via `DELETE /users/{pubkey}/role` leaves the target at ambient authority (Editor by default, Admin if power-user), so terminated users retain write access
- Topics: VC-03.7, VC-03.8, VC-05.1, VC-09.9
- Chain of events:
  1. An employee or agent credential is compromised or the employee leaves. The operator revokes by calling `DELETE /api/admin/rbac/users/{pubkey}/role` — the natural "revoke" verb exposed by the API (VC-05.1, :182-209).
  2. `remove_checked` deletes the explicit row; effective-role resolution then falls to ambient authority: "1. explicit row … 2. Admin if POWER_USER_PUBKEYS match … 3. else configured_default" (VC-03.7, role_store.rs:359). `RBAC_DEFAULT_ROLE` unset → **Editor** (ADR-2010 compat default, role_store.rs:195).
  3. Editor maps to `AccessLevel::Authenticated` — "read + WriteGraph" (VC-03.7). The supposedly revoked user can still POST `/api/files/update_graph` and `/api/graph/update`-class mutations (any non-settings mutating route classifies as WriteGraph, VC-03.6), and can still POST `/api/decisions/record` (Authenticated, VC-05.6). If the pubkey is listed in `POWER_USER_PUBKEYS` (nostr_service.rs:134), deletion leaves them **Admin** outright.
  4. The ex-user mutates the graph / records decisions after "revocation"; the customer discovers post-departure writes; contract lost.
- Evidence: VC-03.8 — "removal is NOT revocation: deleting the row drops the target to their AMBIENT authority (Admin if power-user, else configured_default), never denies outright. Genuine revocation requires an explicit Viewer assignment" (role_store.rs:500 path); VC-05.1 — the delete response carries a "note" warning "the target may still hold effective_after by ambient default" (:203); VC-03.7 default-Editor and the Editor→Authenticated mapping; VC-03.6 mutating-method classification.
- Warning signs visible today: the API surface offers DELETE as the revocation affordance while the record states it does not deny; the default ambient role is a *writer* role; `POWER_USER_PUBKEYS` silently overrides deletion with Admin.
- Confidence: high — the behaviour is stated as ADR-2010 design with explicit warnings; the incident realization (operator misuse of DELETE during an offboarding) is inferred.
- Severity: high

### R-3 — `/ws/client-messages` authenticates on token *presence only*: any non-empty string opens a live stream of client/agent messages
- Topics: VC-04.25, VC-03.2, VC-01.8
- Chain of events:
  1. The attacker reads the client (or the in-code comment) and learns the `/ws/client-messages` upgrade takes an Authorization Bearer token.
  2. They connect with `Authorization: Bearer x` — any non-empty value. The handler rejects only an *empty or missing* token with 401; "the token's CONTENTS are never verified against NostrService, only its presence, so any non-empty string passes" (VC-04.25 DOC-DRIFT note, client_messages_handler.rs:131-142).
  3. The socket is accepted, the actor starts a 100 ms drain loop over `app_state.client_message_rx`, and forwards every queued message as `{type:client_message, content, timestamp, session_id, agent_id}` (client_messages_handler.rs:10, VC-04.25).

### R-1 — Erasure is structurally incomplete: the Pod delete never reaches RuVector, and provenance is append-only plaintext
- Topics: VC-22.6, VC-22.4, VC-22.10
- Chain of events:
  1. A client demands erasure of an agent's memory (GDPR-style). Operator runs `deleteAgentMemory`.
  2. The Pod-side `.jsonld` resource is DELETEd; 2xx **and 404 both count as success** (agentMemory.ts:194; ldpClient.ts:206,210,215).
  3. Nothing propagates to the vector store: "this Pod-side delete never calls `mcp__claude-flow__memory_delete` or any RuVector endpoint — RuVector is external Postgres reached only via MCP, no delete-propagation hook exists in this path."
  4. The embedding row persists and remains searchable (docs/DATA-authority-erasure.md:87).
  5. The row now has a *second* consumer: the server holds a direct read-only RuVector client (tokio-postgres from `RUVECTOR_PG_CONNINFO`, crate visionclaw-memory-cloud, Cargo.toml:133-138), so the leftover data is queryable server-side too.
  6. Independently, governed facts about the same subject sit in GRAPH_PROVENANCE, which is append-only — retraction only ADDS `dl:validTo` and "history never removed" (provenance_writer.rs:218,478-502). The crypto-shredding fix (ADR-2102) is PROPOSED only.
  7. There is no durable erasure record or per-store acknowledgement; ADR-2102 is written precisely because today "a partial erasure … [is] a silent success rather than … recorded and retryable" (VC-22.10 note).
  8. The client discovers their "deleted" content still retrievable/searchable through RuVector (and provable in provenance) — custody/privacy failure.
- Evidence: VC-22.6 DIVERGENCE and DRIFT notes as quoted above; VC-22.4 "PROPOSED ADR-2102: keep the append-only invariant and satisfy erasure by crypto-shredding… or… declare provenance out of erasure scope explicitly"; VC-22.10 "PROPOSED ADR-2102: one durable erasure record, five store acknowledgements, and a partial erasure that is recorded and retryable rather than a silent success".
- Warning signs visible today: the DIVERGENCE/DRIFT notes themselves; DATA-authority-erasure.md:87 documents the tombstone gap; both remediation ADRs (2102, 2103) sit at PROPOSED with no implementation.
- Confidence: high — the gap is explicitly documented; only the triggering client erasure request is assumed.
- Severity: high
