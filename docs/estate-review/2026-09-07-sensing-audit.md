## R-01 — Uploaded WASM authentication is a public-data digest

`firmware/esp32-csi-node/main/rvf_parser.c:171-238` labels its entrypoint `rvf_verify_signature` and its comments “Ed25519” and “SHA-256-HMAC”. The actual operations concatenate a 32-byte `pubkey` with the signed region through SHA-256 and compare the first 32 signature bytes. This is neither an Ed25519 verification nor an HMAC construction. A check computable entirely from public-key bytes and payload does not authenticate possession of a private signing key. If those configured bytes are instead kept secret, the system still has an undocumented secret-prefix hash contract rather than the stated public-key verification contract.

`wasm_upload.c:110-128` calls this function when verification is enabled; `nvs_config.c:89,259-277` supplies configuration and the missing-key rejection. The existence of those fail-closed gates does not fix the verification primitive they invoke. This is a source-level authentication mismatch, not a network exploit demonstration. The closeout owner should replace the primitive with a defined, tested signer/verifier pairing and bind publisher identity, key provisioning/rotation, package format and retained signed artefact identity. Unknown/malformed algorithms must be rejected rather than silently substituted.

## R-02 — A measured execution budget does not pre-empt execution

`wasm_runtime.c:669-706` calls synchronous `m3_CallV`, then measures elapsed time and records budget faults. This penalises completed over-budget calls and can stop a module after repeated faults. It does not show a fuel counter, execution interrupt or pre-emption inside a non-returning call. A watchdog elsewhere could have a different failure scope; it was not established here. ADR-040's isolation/budget claims therefore need explicit proof with a nonterminating module and a retained observation of the sensor/task recovery path. Do not infer bounded execution from post-call telemetry.

Host capability checks are present (`wasm_runtime.c:95-114` and subsequent host functions). The raw-WASM development case deliberately grants all capabilities when the stored mask is zero. This corrects the Rust builder comment (`wasm-edge/src/rvf.rs:199-203`) claiming no loader checks capability flags; it does not close R-01 or R-02.

## R-03 — ADR-032's accepted hardening is not an implementation receipt

The TDM beacon serialiser/deserialiser (`hardware/src/esp32/tdm.rs:317-362`) has cycle, period, drift and reserved bytes; it contains no MAC field or verifier. The firmware raw-CSI path (`csi_collector.c:93-125`) carries a sequence number and copies I/Q data without the proposed CRC field. The cross-room tracker distinguishes two collections: pending exits are bounded (`cross_room.rs:228-232`), but the transition log is an unbounded `Vec` appended at `:298`. Treating the former bound as proof of the latter would hide the ADR's specific unresolved requirement. Stale-frame recalibration exists (`coherence_gate.rs:130-136`); it is a narrower implemented behaviour than the full seven-item security plan.

## Review and validation limits

The 13 record bodies, implementation modules and composition points were inspected. Source searches for a negative claim were restricted to the named crate/firmware scope: absence there does not establish absence in every vendored project. Directory existence alone was not treated as end-to-end delivery. The sensing server's absent named fusion symbols leave integration unestablished; an alternative composition path may exist and would need its own evidence.

A standalone `rustc --test` compile of the std-only TDM module succeeded, but this environment refused execution of the resulting binary with `Permission denied` in both temporary and user-cache output locations. No pass count is claimed and no access restriction was bypassed. Historical cargo/hardware results elsewhere in the corpus were not presented as fresh runs. No unsupported benchmark or withdrawn hardware-validation claim was restored.
