# GPU analytics, interaction, XR presence and analytics support audit

This audit covers all 34 panels of VC-15 (GPU analytics and pathfinding), VC-16 (drag, pin, layout, constraints and agent beams), VC-17 (XR presence crate) and VC-18 (analytics support handlers and the analytics WebSocket). Every panel was read against VisionClaw `86cdd7635582`. All four topics were restamped from `8692b12ba987` to that pin, with every citation re-resolved there.

Dispositions: 34 corrected, 0 accurate, 0 accurate-with-limits, 0 inaccurate-unfixed. In four of the corrections (VC-15.2, VC-15.12, VC-16.8, VC-18.10) only citations or counts were wrong. The other thirty were wrong about mechanism.

The most important finding is that five analytics surfaces answer without doing their work:

- **Community detection:** `POST /analytics/community/detect` is sent to a `ForceComputeActor` stub that always refuses.
- **PageRank:** all three routes read an actor address that is never set.
- **Stress majorization:** all six routes reach `ForceComputeActor` stubs.
- **Params and focus:** both POSTs reach a no-op handler that still answers success.
- **Constraint apply and remove:** both reach no actor at all.

The previous diagrams drew working GPU chains for several of these.

## Findings

**W3VCE-01: community detection never reaches the GPU.**
- **Trigger:** `POST /analytics/community/detect`.
- **Consequence:** the handler takes `get_gpu_compute_addr()`, which returns `Addr<ForceComputeActor>` (`src/app_state.rs:1672`). It sends `RunCommunityDetection` there (`src/handlers/api_handler/analytics/community.rs:61-64`, `:91`). That handler only returns `Err("Community detection should be handled by ClusteringActor")` (`src/actors/gpu/force_compute_actor.rs:3347-3352`), so with a GPU present the route always answers 500 (`src/handlers/api_handler/analytics/mod.rs:77-88`).
- **Evidence of a known pattern:** a working chain exists, `GPUManagerActor` (`src/actors/gpu/gpu_manager_actor.rs:375`) to `AnalyticsSupervisor` (`src/actors/gpu/analytics_supervisor.rs:520`) to `ClusteringActor`. The anomaly route already uses it for this reason (`src/handlers/api_handler/analytics/anomaly.rs:35-38`).
- **To close:** send to `gpu_manager_addr`, and add a route-level test that fails on the stub reply.

**W3VCE-02: the PageRank routes are unreachable.**
- **Trigger:** `POST /analytics/pagerank/compute`, `GET /analytics/pagerank/result` or `POST /analytics/pagerank/clear`.
- **Consequence:** all three read `AppState.analytics.pagerank` (`src/handlers/api_handler/analytics/pagerank_handlers.rs:121`, `:184`, `:239`). `AppState::new` builds it as `None` (`src/app_state.rs:1296-1300`), and no code assigns it later, so every call answers "PageRank actor not available".
- **Evidence of a known pattern:** the supervised path exists. `GPUManagerActor` handles `ComputePageRank` (`src/actors/gpu/gpu_manager_actor.rs:850`) and forwards it to the `PageRankActor` that `AnalyticsSupervisor` spawns (`src/actors/gpu/analytics_supervisor.rs:132`, `:599`). This is the same defect ADR-2053 fixed for the pathfinding routes.
- **To close:** route PageRank through `gpu_manager_addr`.

**W3VCE-03: the stress-majorization routes reach `ForceComputeActor` stubs.**
- **Trigger:** any `/analytics/stress-majorization/*` route.
- **Consequence:**
  - All six routes send to `get_gpu_compute_addr()`.
  - Trigger, stats and reset-safety return `Err`; params returns `Ok` without forwarding (`src/actors/gpu/force_compute_actor.rs:3437-3490`).
  - `configure` overwrites `unified_params.temperature` and `unified_params.damping` (`src/actors/gpu/force_compute_actor.rs:3709-3719`). That is a physics write outside `apply_physics_patch`, in tension with ADR-2140's single write path.
  - The real `StressMajorizationActor` handlers (`src/actors/gpu/stress_majorization_actor.rs:311`) are unreachable over HTTP.
- **Not established:** whether the overwritten values reach the device before the next resync from the store needs a runtime check.
- **To close:** address the supervised actor, or remove the routes.

**W3VCE-04: the analytics params and constraint endpoints misreport.**
- **Trigger:** the `/analytics/params`, `/analytics/focus`, `/analytics/constraints` and `/analytics/gpu-metrics` routes.
- **Consequence:**
  - `POST /analytics/params` and `POST /analytics/focus` reach a no-op that returns `Ok` (`src/actors/gpu/force_compute_actor.rs:3355-3365`).
  - `GET /analytics/params` ignores the settings it fetches and returns fixed builder values (`src/handlers/api_handler/analytics/params_handlers.rs:344-354`).
  - `GET /analytics/constraints` turns a guaranteed `Err` (`src/actors/gpu/force_compute_actor.rs:3368-3373`) into a successful empty set (`src/handlers/api_handler/analytics/params_handlers.rs:129-133`).
  - `POST /analytics/constraints` applies the update and then answers 503 (`src/handlers/api_handler/analytics/params_handlers.rs:194-199`).
  - `GetGPUMetrics` returns hard-coded zeros (`src/actors/gpu/force_compute_actor.rs:3329-3344`).
  - `analytics_execution` telemetry is missing on the mailbox-error and no-GPU branches (`src/handlers/api_handler/analytics/performance_handlers.rs:184-193`), which contradicts the "every response" claim the topic made.
- **To close:** route these to the actors that own the data, or remove them, and add tests on the reply bodies.

**W3VCE-05: the `/api/constraints` and `/layout/zones` routes record but do nothing.**
- **Trigger:** the `/constraints/*` and `/layout/zones` routes.
- **Consequence:**
  - `apply` and `remove` validate, log and answer "recorded" (`src/handlers/constraints_handler.rs:181-188`, `:218-223`).
  - `list` always falls back to an empty list (`src/handlers/constraints_handler.rs:236-273`).
  - `define` caches constraints on `ForceComputeActor` correctly (`src/actors/gpu/force_compute_actor.rs:3376-3393`). It also writes the physics `computeMode` through `UpdateSettings` (`src/handlers/constraints_handler.rs:37-77`), outside `apply_physics_patch` (ADR-2140 tension).
  - `POST /layout/zones` is a TODO that answers success (`src/handlers/layout_handler.rs:313-321`).
  - The previous VC-16.6 drew all constraint routes reaching `ConstraintActor`; none of them address it.
- **To close:** wire apply and remove, or delete them.

**W3VCE-06: the 0x44 agent co-presence channel has no production ingress.**
- **Trigger:** any agent publishing co-presence state.
- **Consequence:**
  - `IngestAgentPresence`, `SweepStaleAgentPresence`, `GetAgentPresence` and `GetAttentionNode` are sent only from the test module (`src/actors/presence_actor.rs:1177`).
  - `PresenceActor::started` schedules subscriber eviction only (`src/actors/presence_actor.rs:634-640`).
  - ADR-2020's channel is therefore implemented and unit-tested, but nothing in the server publishes into it or sweeps it.
- **To close:** add a server ingress and a periodic sweep.

**W3VCE-07: `POST /analytics/sssp/compute` discards its result.**
- **Trigger:** `POST /analytics/sssp/compute`.
- **Consequence:**
  - A full CPU Dijkstra runs in `GraphStateActor`. It rescans every edge on each pop (`src/actors/graph_state_actor.rs:787-814`).
  - The handler then drops the distances and paths, and answers "SSSP computation started" for a finished computation (`src/handlers/api_handler/analytics/sssp_handlers.rs:226-232`).

**W3VCE-08: the analytics WebSocket echoes a cadence it does not apply.**
- **Trigger:** an `updateSubscriptions` message.
- **Consequence:**
  - The handler clamps and stores `update_interval_ms` and echoes it (`src/handlers/api_handler/analytics/websocket_integration.rs:435-451`).
  - The push timer is armed once, in `started` (`:409`, `:357-364`), so the default 5000 ms stays in force (`:90`).

**W3VCE-09: the presence handshake timeout is checked late.**
- **Trigger:** a client that opens the presence socket but never authenticates.
- **Consequence:** `HANDSHAKE_TIMEOUT` is 10 s (`src/handlers/presence_handler.rs:34`), but it is only tested on the 15 s heartbeat tick (`src/handlers/presence_handler.rs:438-441`). An unauthenticated socket therefore lives about 15 s.

**W3VCE-10: the ADR-2140 SSSP-toggle debt is closed.** `toggle_sssp` now writes through `apply_physics_patch` (`src/handlers/api_handler/analytics/sssp_handlers.rs:126`), and the feature-flag handlers derive `sssp_integration` from the store rather than holding it (`src/handlers/api_handler/analytics/feature_flags_handlers.rs:11-16`). VC-18's Debt note and its "wholesale replace" description were stale and have been rewritten.

**Generator advisories, checked by hand:**

- VC-16's drag panels now draw the ADR-2169 hold model (`HoldNodes`, `ReleaseNodes`, `ReleaseHolder`, and explicit `nodePin` / `nodeUnpin`).
- VC-16.5 now draws the layout mode as a stored field written through `apply_physics_patch` (`src/handlers/layout_handler.rs:92-106`), with seven modes advertised.

**Open:** `POST /layout/radial` and `POST /layout/reset` take no `AuthenticatedUser` extractor (`src/handlers/layout_handler.rs:198`, `:330`), unlike `POST /layout/mode`. Whether the enclosing `/api` scope authenticates them is outside this trace.
