# VisionClaw governance, insight and Solid pod panels

I assessed all 36 panels of VC-24 (ACSP decision elevation, 12 panels), VC-25 (insight loop, KPI, briefing, NLQ and semantics, 11 panels) and VC-26 (Solid pod integration, 13 panels). The evidence is source tracing at VisionClaw `86cdd7635582` and agentbox `c57d9c0508f4`. All three topics were stamped at `8692b12ba987`, 217 commits behind the pin. I restamped all three and re-resolved every citation at the pin. Of the 36 panels:

- 12 are accurate.
- 2 are accurate with limits.
- 22 are corrected.
- None is inaccurate and unfixed.

The most important finding is behavioural. ElevationActor's boot reconciliation reloads only `pending` cases. An approved case whose draft PR is open lives only in memory, and its PR url is never persisted. A restart therefore loses the merge poll, and `concept_elevated` never fires for that case. The old VC-24.5 note said the whole path had no reconciliation, which was too broad. VC-24.4 said reconciliation existed, which was right but incomplete.

Two more panels were materially stale:

- **VC-25.7** showed the NLQ refusal paths answering 200. They answer 500.
- **VC-26.10** described a client fetch that no longer exists. The client now pins one immutable ontology generation.

VC-26's nip98 and ldpClient citations mostly pointed at doc comments or neighbouring code, even at the old stamp. Tracing them found a security-relevant gap: the embedded pod verifies NIP-98 tokens without binding the request body to the signed payload hash.

## Findings

**W3-VC-G-01: approved elevation cases are not recovered after restart (Debt, VC-24.5).**
- **Trigger:** the server restarts while an ElevationActor case is approved and its draft PR is open.
- **Mechanism:** `Reconcile` reads only `repo.list(Some("pending"), …)` (`src/actors/elevation_actor.rs:1351`). The approved case is held in the in-memory `elevating` map (`src/actors/elevation_actor.rs:1572`). ElevationActor's only store writes are `create_or_update` (`:1176`, `:1300`), `record_decision` (`:1443`, `:1516`, `:1523`) and `set_status` (`:1385`, `:1644`). None of them records the PR url.
- **Consequence:** the GOV-2 merge poll never sees the case again. The kind-31404 `concept_elevated` receipt and the durable `elevated` status are never written, even when the PR merges.
- **Contrast:** DecisionElevationActor persists the PR url before tracking it (`src/actors/decision_elevation_actor.rs:363`) and re-arms the poll at boot.
- **To close:** persist the PR url on the case row, reload `approved` rows that carry one, and test with a restart between PR creation and merge.

**W3-VC-G-02: NLQ refusals are reported as server faults (Tension, VC-25.7).**
- **Mechanism:** `translate_query` and `explain_sparql` return every failure through `error_json!` (`src/handlers/natural_language_query_handler.rs:119`, `:178`). That macro builds `HttpResponse::InternalServerError` (`src/utils/response_macros.rs:82`).
- **Failures covered:** an LLM error, a reply with no SPARQL block, a mutating query rejected by the read-only validator, and invalid SPARQL on explain.
- **Consequence:** a client cannot tell a refused query from a broken service by status. Monitoring counts user input as server errors.
- **Panel:** it previously showed 200 and now shows 500.
- **To close:** map validator and extraction refusals to 4xx (422 or 400), and keep 500 or 502 for LLM transport failure.

**W3-VC-G-03: the client JSON-LD fetch now pins a generation (Drift and Debt, VC-26.10).**
- **Change:** `fetchJsonLd` and `fetchTurtle` resolve through `pinnedUrl` (`client/src/features/ontology/services/jss/schemaParser.ts:73-97`, `:118`, `:174`). `pinnedUrl` fetches `index.jsonld`, requires a 32-hex `visionflow:generation`, and reads `@<generation>/` paths.

- **Dead exports:** `getOntologyJsonLdUrl` and `getOntologyTurtleUrl` (`client/src/features/ontology/services/jss/contextLoader.ts:29`, `:33`) have no caller in `client/src`, and their doc comment still presents them as the fetch path.
- **Fix:** the panel is redrawn.
- **To close the debt:** delete the two helpers or repoint their comment.

**W3-VC-G-10: Solid pod writes are not bound to the signed payload hash (Tension, VC-26.4).**
- **Mechanism:** `extract_user_identity` calls `validate_nip98_token(token, &expected_url, expected_method, None)` (`src/handlers/solid_proxy_handler.rs:225`). The wrapper selects `BodyBinding::RequiredWhenTagged` (`src/utils/nip98.rs:439`). With no body, that policy falls to `(RequiredWhenTagged, _, _) => {}` (`:556`), so a `payload` tag is never compared.
- **Scope:** the `/solid` scope has no other body check (`solid_proxy_handler.rs:1773-1807`). The app-level wraps (Logger, CORS, Compress, Timeout) do not inspect bodies, and nothing under `src/middleware` references payload hashes.
- **Consequence:** a holder of an unused signed token for a PUT, POST or PATCH can send different bytes to the same URL and method within 60 seconds. The single-use claim (`nip98.rs:573`) limits this to one substitution, as in SP-ID-01 (`docs/estate-review/2026-11-01-solid-identity-boundaries.md`).
- **Evidence class:** source tracing only; no request was sent.
- **To close:** pass the received body and use `BodyBinding::Required` on write methods, with a route-level test that a body not matching the signed hash is refused.
