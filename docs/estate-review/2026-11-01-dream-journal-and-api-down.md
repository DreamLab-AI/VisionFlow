# Dream journal delivery and API-down acceptance audit

A valid hash chain does not establish complete execution evidence. The current client can report unpaired=0 while a remote call or completion is missing; session collisions can discard different operations as duplicates; concurrent appends can reuse a session sequence. The retained API-down experiment script can retire after a failed restart, and its acceptance checker does not establish continuous outage, successful restart or a newly completed ledger write.

This pass assesses every section of ADR-2071, corrects AB-23.19 and adds AB-23.23 for the journal boundary. Thirteen of the original 22 AB-23 panels are now assessed, plus the new panel. Nine original panels remain queued: 1, 4, 5, 8, 9, 17, 18, 20 and 22. No owner ADR status or production implementation is changed. The wider estate audit remains active.

These probes assert observed behaviour, including defects; they are not remediation tests.

Rust delivery uses loopback HTTP with scripted responses. Tick tests substitute supervisorctl and use temporary workspaces and clocks. The C3 probe extracts only that predicate from the actual checker; the full activation script is not executed. Node uses Fastify injection and temporary event files. There is no live daemon stop, external model, forum write, database call or production night. [Reproduction instructions](evidence/2026-11-01/dream-journal-reproduction.md) and committed probe sources retain those boundaries.

A historical activation receipt exists locally at `.claude/evidence/activation/ADR-2087-activation-20261004T100615Z.md`. Its C1/C2/C3 rows agree with the ADR's recorded 80 paired effects, eleven day files and four verdicts with 130 failed/skipped posts. It is historical evidence, not a rerun. Its overall STAGED verdict concerns ADR-2087 forum receipt delivery, whereas its ADR-2071 C1–C3 rows pass; those statuses must not be conflated. The private receipt is hashed in the manifest, not republished.

## Findings and acceptance work

All source paths below are relative to agentbox.

| Finding | Evidence and consequence | Acceptance required |
|---|---|---|
| AB-J1 / high: unpaired is not remote pair completeness | `journal.rs:165-215` increments open_calls after called regardless of delivery, then decrements before completed posts. Both call-success/completion-failure and call-failure/completion-success yield recorded=1, failed=1, unpaired=0. The latter completion has no causation. The field documentation promises a stronger property. | Rename the local counter, track acknowledged and missing records separately, and reconcile by session/step on the receiver. Do not use unpaired=0 alone as a pairing acceptance condition. A crash can also prevent final stats from being persisted. |
| AB-J2 / high: attempt identity can collide and lose different evidence | `session_for` normalises names and truncates the entire night-plus-seconds string (`journal.rs:300-315`). A 160-character night ID removes the changing suffix; a/b and a-b collide; same-second restarts reuse identity. The route hashes session plus key, and duplicate event IDs return the old envelope without comparing payload (`exec-record.js:52-54`; `execution-journal.js:144-151`). The route probe sends A then B under the same key: B receives duplicate success and is absent from disk. | Give attempts an independently generated, persisted identity; reserve space for it when rendering names. Bind idempotency to canonical payload content and return a conflict for changed content. Test restarts within one second and long/normalising names. The session and route probes establish both boundaries, not an observed live collision. |
| AB-J3 / high: single writer does not imply unique session ordering | `append` reads seq before awaiting dispatch and commits counters afterwards (`execution-journal.js:152-185`). Two concurrent public append calls with distinct event IDs both receive seq 0 using the real disk adapter. The hash chain still verifies. A fresh unhydrated journal also re-appends the same ID at seq 0; production `action-plane.js:169` constructs it without hydrate. | Serialise allocation, deduplication and append per session, restore state before admission, and validate session-sequence uniqueness independently of hash-chain integrity. The concurrent probe uses the journal API directly, not a claimed concurrent dream-engine HTTP run; the restart probe recreates the journal object, not a live service restart. Restart hydration is already an acknowledged ADR limit. |
| AB-J4 / medium: acknowledgement and delivery counters are weak evidence | Any successful HTTP response carrying a string event_id counts as recorded, including an empty ID; duplicate is ignored (`journal.rs:255-269`). After three sequential failures the session never probes again, even when the fixture endpoint is ready to succeed. No retry or outbox is present. | Validate acknowledgement shape and distinguish appended, duplicate, rejected and unknown delivery outcomes. Define bounded recovery and durable buffering requirements before promising replay after outages. The breaker is intentional fail-open policy; its permanent session-wide loss is a qualification, not itself a deviation. A lost acknowledgement may follow a successful server append; the probes do not claim to resolve that ambiguity. |
| AB-J5 / medium: every-side-effect coverage is overstated | Direct inbox writes for shared remotes (`engine.rs:244`), annexe-health failure (`:838`), abandoned attempts (`:890`) and damaged run state (`:2061`) have no tool pair. `inbox::add:174-215` writes directly and has no internal journal. Separately, the repo wrapper posts lifecycle events before/after the body (`engine.rs:508-529`), contradicting the October statement that locked/finished nights journal nothing. | Maintain a side-effect coverage inventory and test failure/early-return branches. Either wrap these inbox operations or document intentional exclusions. Distinguish lifecycle events from tool effects. This finding is source inspection; those engine branches were not freshly executed here. |
| AB-J6 / high for future reuse: restart failure is recorded as completion | The retained tick ignores start failure, writes done and started_at, then retires the marker (`adr-2071-api-down-night.sh:145-148`). The fixture leaves the API substitute STOPPED with phase=done and no marker. Subsequent ticks cannot retry. | Keep recovery pending until a confirmed healthy restart; retain the marker on failure and report an actionable failure. Test start refusal, STARTING timeout and lost scheduler. The trap covers only the stop-to-state interval and is disarmed thereafter; recovery depends on later ticks. This script is retired, so the finding is not a claim of an active scheduled outage. |
| AB-J7 / medium: fresh marker does not rearm old state | The done/missed branch runs without comparing state.night to the new marker (`:92-95`). A November marker with October done state is immediately consumed while the API remains running. | Make state experiment-specific and validate its identity before reuse. Provide an explicit rearm operation or document state reset, with tests preserving prior receipts. A fresh marker alone is insufficient despite the script's reuse wording. |
| AB-J8 / high for future acceptance: date text can end or misclassify the outage | A regex matches date text without parsing JSON or tying it to an engine invocation (`:132-138`). The fixture restarts at 00:45 from invalid JSON, before the window. Matching date takes precedence over RUNNING, masking an interruption. | Use a run-bound terminal receipt newer than the stop, require valid structured data and record actual process transitions independently. Reject an interruption even if a same-date record exists. |
| AB-J9 / high: C3 can pass without establishing its stated evidence | `adr-2087-check.sh:397-419` requires a dated health file, at least one verdict and failed/skipped post, plus matching done state, nonempty stopped_at and allowed reason. The extracted predicate passes with stopped_at=not-a-timestamp, no started_at and engine_exit=99. It checks neither ledger append nor that all relevant work happened during a continuous outage. | Bind stop/start and engine timestamps to one attempt, require successful completion and specific ledger evidence, and distinguish new work from an earlier completed skip. Verify restart success separately. This demonstrates insufficient current acceptance logic; it does not overturn the historical manual run's additional evidence. |

Normal completion writes repo counters into health (`engine.rs:336-361`) and adds night-level counters after turn.completed (`:448-449`, `records.rs:382-399`). The no-repo and all-locked early returns do not perform that normal final write; they deliberately avoid replacing other night evidence. Health writes themselves are fail-open. Complete coverage therefore cannot be inferred from the presence of one aggregate file.

## Comparison and utility

[OpenTelemetry's Collector resilience guidance](https://opentelemetry.io/docs/collector/resiliency/) distinguishes memory buffering, retry and persistent queues, with explicit loss conditions when capacity, retry limits or storage fail. Its [OTLP exporter specification](https://opentelemetry.io/docs/specs/otel/protocol/exporter/) defines retry behaviour for transient errors. These provide useful delivery-design comparisons, not an assertion that the custom journal implements OTLP or should share its semantics unchanged.

For operators, the useful next deliverable is a per-attempt evidence view showing what ran, what the receiver acknowledged, what remains missing and whether delivery recovered. Keep any durable outbox distinct from the canonical chain: drain it through the same API writer, with payload-bound deduplication and restored ordering. Expose incomplete evidence as a first-class outcome. Measure recovery after endpoint outage and client restart, conflicts under reused keys, orphan pairs and time to a confirmed API restart. These are proposed utility tests inferred from the findings, not measured product performance or adoption claims.
