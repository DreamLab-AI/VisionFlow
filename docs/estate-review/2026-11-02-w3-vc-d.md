# VisionClaw GPU supervision, physics step, SimParams ABI, broadcast and wire frames

I assessed all 41 panels of topics VC-10 to VC-14 by source tracing at VisionClaw `86cdd7635582`. All five topics were stamped at `8692b12ba987`, 217 commits behind the pin, and the sources under four of them had changed materially. I restamped every topic and re-resolved every citation at the pin. The result is 34 panels corrected, 7 accurate, none accurate-with-limits and none inaccurate-unfixed. The most important finding is that the drag model changed under the corpus. At the pin a drag is a server-side hold (`HoldNodes`, `ReleaseNodes`, `ReleaseHolder`; ADR-2169): each connection may hold two nodes, updates arriving too fast are coalesced rather than dropped, a released node rejoins the simulation, and a lasting anchor is a separate `nodePin`. VC-13.2 and VC-13.8 still described a drag that left the node pinned, with up to five drags and rate-limited updates thrown away. The same change moved the stability bypass, the speed floor and the reheat into `step_overrides`, which VC-11.1 and VC-11.9 did not show. The review also turned up two generator blind spots that had let stale line numbers pass the strict gate.

## Findings

**VC-D-01: drags are holds, not pins (VC-13.2, VC-13.8, VC-11.2).**
- *Trigger:* any `nodeDragStart`, `nodeDragUpdate` or `nodeDragEnd`.
- *Consequence:* the old panels said a drag sends `PinNodePositions`, that `nodeDragEnd` leaves the node pinned, that the cap is five drags, and that an update inside 16 ms is ignored. None of that is true at the pin. A drag sends `HoldNodes` (`src/handlers/socket_flow_handler/position_updates.rs:143-145`), the cap is `MAX_DRAGGED_NODES_PER_CLIENT = 2` (`:15`, `:88-90`), and a fast update is kept in `drag_pending` and applied by a trailing timer (`:306-319`, `:339-353`). Release sends `ReleaseNodes`, and the node rejoins the simulation (`:176`, `src/actors/gpu/force_compute_actor.rs:3048-3058`). A disconnect releases by holder (`src/handlers/socket_flow_handler/types.rs:508-521`). An explicit pin is `nodePin` (`position_updates.rs:422-465`, `message_routing.rs:60-62`). VC-11.2's DEBT note said drags arrive as `PinNodePositions`; at the pin they arrive as `HoldNodes` (`force_compute_actor.rs:3027`).
- *Closed:* I redrew VC-13.2 and the VC-13.8 drag lane, and corrected the VC-11.2 note.

**VC-D-02: per-step overrides now drive bypass, speed and reheat (VC-11.1, VC-11.9).**
- *Mechanism:* `step_overrides` (`force_compute_actor.rs:4568-4590`) bypasses the stability kernel while warmup is running, while any node is held, or for 2 s after the last release. During a hold or that window it floors `global_speed` at 2.0 and withholds the reheat (`:4579-4586`). A hold that is not refreshed is released after `HOLD_EXPIRY` (5 s, `:4520`, `:1920-1933`).
- *Other errors in VC-11.9:* it named the 1.5 reheat seed `SetLayoutMode`; the handler is `SetRadialLayout` (`:2480`, seed at `:2602`). It said `PinNodePositions` seeds a reheat of 0.3; it now queues a one-shot `RELEASE_IMPULSE` of 0.05 (`:3013-3014`, `:4537`).
- *Gate gap:* VC-11.9 cited plain `line N` text, which the gate never checks.
- *Closed:* I redrew the VC-11.1 tick and rewrote VC-11.9 with gate-checked citations and a Held state.

**VC-D-03: kernel arguments were attributed to the wrong kernel (VC-11.2).**
- *Wrong at the old stamp:* the panel said the force pass receives `prev_force_x/y/z` and `pinned_mask`.
- *At the pin:* both go to `integrate_pass_kernel` (`src/utils/unified_gpu_compute/execution.rs:999-1027`). Class metadata goes to the non-stability force-pass variant and to integrate (`:808-810`, `:1018-1020`).
- *Not shown before:* the stability variant is chosen by `stability_threshold > 0` (`:661-665`), and the hold-overlay edge-rest snapshot runs before the force pass (`:718-741`).
- *Closed:* I redrew the launch messages.

**VC-D-04: Path B converter now delegates to Path A; GPU-wire-abi is stale (VC-11.3).**
- *At the pin:* `From<&PhysicsSettings> for SimParams` is a single delegation to `SimParams::from(&SimulationParams::from(physics))` (`src/models/simulation_params.rs:865-867`). The panel drew it as building its own flag word.
- *Drift (still open):* `docs/GPU-wire-abi.md:150-155` still gives the converters as lines 236-317 and 319-407 and describes a separate Path B flag derivation that always sets `ENABLE_SSSP_SPRING_ADJUST`.
- *Closed in the topic:* panel corrected. Closing the drift needs a GPU-wire-abi edit.

**VC-D-05: constraints upload on change only (VC-11.5).**
- *At the pin:* both writers call `replace_constraint_cache` (`force_compute_actor.rs:1657-1662`). `sync_constraints` uploads only when the cache is dirty or the resident count differs from it (`:1675-1689`). A new GPU context re-marks the cache dirty (`:3554`, `:846`). The force kernels read a per-node constraint index through `g_constraint_index` (ADR-2173; `crates/visionclaw-gpu/src/cuda_sources/visionclaw_unified.cu:157`, `src/utils/unified_gpu_compute/construction.rs:141-144`).
- *Closed:* notes added to VC-11.5 and VC-12.3.

**VC-D-06: runtime PTX identity check (VC-12.5, VC-12.6, VC-12.7).**
- *Build side:* `build.rs` now emits `NAME_PTX_TAG` (`crates/visionclaw-gpu/build.rs:272-278`).
- *Load side:* `load_ptx_module_sync_raw` first calls `check_baked_artefact` (`crates/visionclaw-gpu/src/ptx_loader.rs:472`, `:452-462`). If the baked file is present and its content tag differs, loading fails with `PtxIdentityMismatch` (`:423-446`). A missing tag or file skips the check.
- *Effect:* this narrows, but does not close, VC-12.6's DIVERGENCE about a stale cached OUT_DIR artefact.
- *Closed:* step added to the build and load flows.
