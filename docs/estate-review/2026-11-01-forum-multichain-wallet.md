# Two-chain wallets: identity, freshness and delivery

Compiled chain pins and family-specific replay work, but they do not establish fresh balances, durable payment intent or account-safe asynchronous delivery. Six targeted native checks confirm five boundary behaviours and one rejection control. The consumed client's existing 725 tests also pass. This batch changes documentation only; it does not activate the parked sidestr work or send transactions.

## Findings and adversarial checks

| ID | Evidence, impact and limit |
|---|---|
| **W1 — mutable DREAM identity** | `wallet/profile.rs:215–225` accepts any 64-hex asset ID for either pin. The native fixture replaces DREAM's ID with `ab` repeated 32 times, retains ticker DREAM and receives no warning. This contradicts D3's fixed-ID statement. It does not demonstrate minting an asset or a remote configuration attack. Either enforce the compiled identity or amend the decision and prominently expose the actual asset ID. |
| **W2 — malformed entry changes fallback chain** | `profile.rs:279–312` parses each whole Entry. A sole txbt4 entry with `mirror: 17` is dropped and the resolver returns DREAM with a warning. The no-known-entry fallback is intentional; the surprising part is a bad optional field causing that route. Reject explicit invalid deployment configuration visibly, or implement and document field-level fallback. |
| **W3 — URL shape validation** | `profile.rs:136–148` only checks prefixes. Native fixtures accept `https:///`, normalise it to `https:`, and accept a bare `wss://`, both without warnings. This proves unusable configuration passes validation, not a successful malicious network request. Parse URLs and require a host; preserve useful diagnostics in the visible configuration state. |
| **W4 — valid does not mean current** | A native fixture replays the full txbt4 file at height 26 and separately accepts its valid genesis-only prefix at height 0. `wallet/mod.rs:379–411` replaces the snapshot after every successful replay without comparing the previous tip. `loaded_at` is the download time, and `ready:680–686` accepts an existing snapshot after a later load failure. A browser rollback and stale-balance spend were not executed. Keep a known tip, compare authenticated signer announcements, distinguish download time from chain freshness and stop new spend construction when freshness is unresolved. |
| **W5 — ambiguous delivery reported as no send** | `wallet/relays.rs:35–150` distinguishes accepted, rejected and no-answer outcomes internally. `wallet/mod.rs:661–663` collapses zero accepted responses into “Nothing was sent” and records no pending intent. A relay may have received the event before its ACK was lost. This is source reasoning, not a timed network experiment. Persist transaction identity before publication, report uncertain delivery, and reconcile/rebroadcast the same transaction before constructing a replacement. |
| **W6 — late reservation and mutable account binding** | `send_asset_with:734` builds from the snapshot minus currently pending inputs; `deliver:651–677` waits for relay responses before adding held inputs. `bind_owner:454–480` can replace the pending list/owner during that wait; `save_pending:483–493` reads the then-current owner. Separate controls can therefore start without a shared in-flight reservation, and completion has no owner-epoch guard. These are source-supported race paths, not reproduced double-spends or cross-account theft. Capture owner/chain/asset context, reserve inputs before await and commit the receipt to that captured context. |
| **W7 — migration and reconciliation lack explicit failure states** | Migration calls `save_pending` and then removes the legacy entry even though storage write errors are ignored. Reconciliation removes an included transaction, or an old transaction whose inputs are all still unspent; a conflicting spend leaves the latter condition false indefinitely. These storage-failure/conflict paths were not injected. Delete legacy data only after confirmed durable write, retain recoverable receipts, and distinguish confirmed, conflicted, uncertain and dropped transactions. |
| **W8 — chain scoping is not payment verification** | `paid_hand:520–534` accepts any pending entry with the requested hand root without comparing the supplied script; its chain branch checks an input script but not settlement amount or recipient. This helper can find a candidate transaction; it cannot certify a paid obligation alone. The preceding poker audit also found missing replay/payment-field binding. Derive and compare chain, asset, sender, destination, amount and root before showing settled. No live hand or payment was attempted. |
| **W9 — configuration-only wire binding** | Per-chain house mapping protects the intended deployment, but protocol 1's shared asset tag and lack of duplicate-house-key rejection leave correctness dependent on configuration agreement. The current two distinct configured keys are a positive control. Add a capability/identity receipt binding chain, genesis, asset and seat, plus validation of accidental seat reuse; consider explicit wire binding in protocol 2. This is a design recommendation, not an observed exploit. |

Existing protections matter: unknown chain IDs cannot add pins; cross-chain blocks fail validation; extension responses cannot freely replace the unsigned transaction; signature checks remain active; pending keys include chain and account; and tip totals are not summed across assets. None of W1–W9 should be read as a demonstrated breach of those protections.

## Comparison and user utility

These are interface and trust-model comparisons, not a claim of Ethereum compatibility or a market-size estimate. EIP-1193 treats account and chain changes as explicit events and specifies connection failures. Its useful lesson here is to make account/chain context changes observable and invalidate dependent asynchronous work. The proposed immutable context and owner epoch are audit recommendations, not requirements imposed by that Ethereum specification. [EIP-1193](https://eips.ethereum.org/EIPS/eip-1193).

Current sidestr-nostr 0.6.0 documentation describes comparing a mirror with an authenticated signer's tip announcement and distinguishing a behind/different tip. This is a closer technical fit for W4 than merely retrying the download. It is comparison material, not proof that the consumed dependency or client integrates that API; signer authenticity also cannot prevent an unanchored signer from lying or establish freshness without an age policy. [sidestr tip documentation](https://docs.rs/sidestr-nostr/0.6.0/sidestr_nostr/tip/index.html).

NIP-01's OK message acknowledges an event ID and acceptance result. It does not attest to subsequent chain inclusion. The wallet's useful product receipt should therefore separate submitted, relay-accepted, included and uncertain states, with a transaction link and a safe retry action. [NIP-01](https://github.com/nostr-protocol/nips/blob/master/01.md).

Source evidence supports a community testnet demonstration: the same forum identity can tip a contribution or settle a table result in either configured asset. No evidence here establishes demand, liquidity, financial reliability or a reason to add more chains. Before expanding, measure whether members can identify the asset, understand an interrupted transfer and recover the receipt after changing account or reloading. Prioritise W5–W7's recoverable intent, W4's freshness and W1–W3's visible identity/configuration failures. Keep the parked activation decision intact while documenting acceptance criteria for a future owner-approved trial.

## Validation and remaining work

All 725 existing native tests pass in the consumed client. The six isolated audit tests pass: DREAM asset override, typed-entry fallback, malformed HTTPS, bare WSS, unknown-chain rejection and valid old-prefix replay. The audit tests were appended only inside the disposable archive and retained as evidence; product sources were not edited. A future-compatibility warning concerns dependency `proc-macro-error2 2.0.1`; it is not a failing test.

Browser concurrency, storage quota failure, interrupted ACK recovery, WASM compilation, mobile cost, producer freshness and deployed binary provenance remain open. Structural diagram gates and visual inspection are recorded in the batch gate evidence; they do not substitute for semantic review of the remaining estate.
