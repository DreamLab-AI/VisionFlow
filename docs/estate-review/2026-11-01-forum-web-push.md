# Forum Web Push: wake-up receipts, quiet hours and account teardown

ADR-2023's payload-less design keeps message text out of push requests. Its current delivery and teardown paths do not support several stronger promises: bookkeeping can strand a newer event, concurrent drains can erase a later count, and a fresh registration never writes the localStorage credential copy used for server-side logout cleanup. Visible forum windows suppress notifications even when they show the login page, contrary to WebKit's documented user-visible requirement.

## Findings and acceptance work

| ID | Finding and recommended acceptance test |
|---|---|
| **F1 — successful-send bookkeeping can strand activity** | **Executed actual-SQL interleavings.** First count is pushed and drained; a second count arrives while that send is still awaiting bookkeeping; `SQL_MARK_PUSHED` then copies the current `bump_seq`. One pending count remains, but `SQL_PENDING_DUE` returns no device. The old comment assumes the worker always drains after bookkeeping, which is not enforced. Another test shows an older success backdating `last_push_at` after a newer claim, enabling a further early claim. Mark only the generation/sequence actually claimed, guard claim completion, and test delayed provider responses with concurrent event/drain work. |
| **F2 — drain has no atomic claim or registration generation** | **Executed actual-SQL interleavings.** Two drains read one count; the first subtracts it, a new event increments, and the second subtracts its old snapshot, erasing the new event while both responses describe the original. A request authenticated before token rotation can also subtract a new owner's count because mutation predicates include only id. Use an atomic generation-bound claim with a recoverable acknowledgement; retain retriable data until the client can safely acknowledge it. Test overlapping drains, token rotation and lost HTTP responses. |
| **F3 — token-based logout fallback has no stored token copy** | **Executed bridge write plus source trace.** `pushStoreCfg` writes IndexedDB only. Rust `register` invokes it and sets active/refreshed flags, but never writes `nostrbbs:push_cfg`. Both `disable` and `teardown_on_logout` read that missing localStorage key for the server deletion request. Browser unsubscribe/IndexedDB cleanup are still attempted; this is not a claim that every logout leaves a live subscription. Persist an account-bound teardown capability, or use a worker-owned teardown handshake with acknowledgement; test fresh enable/logout while browser unsubscribe fails and navigation happens immediately. |
| **F4 — draining is earlier than visible delivery** | **Executed worker fixtures plus WebKit documentation.** A rejected `showNotification` follows a successful drain with no application acknowledgement or retry. A never-resolving fetch leaves the handler pending and shows nothing during the bounded observation; source has no abort/deadline. A visible login window drains then suppresses display without checking account, focus or relay health. Handle policy-compliant visibility, bounded network work and display failure; verify on real WebKit and Android. A malformed click URL also throws before root fallback in the fixture; catch parse failures. |
| **F5 — preference changes and failures do not consistently suppress delivery** | **Executed due-query case, source-traced send path.** A queued DM remains due after preferences disable DMs and set quiet hours; `flush_pending` never loads those preferences. At initial fan-out, a failed preference read substitutes defaults with replies/DMs enabled. Decide whether quiet hours mean no new accumulation or no wake-ups, then enforce the chosen user-visible contract at delivery. Test queued work across mute/quiet-hour changes and selective DB faults. |
| **F6 — registration and caps discard work** | **Executed SQL refresh case; source-only cap/coordination gaps.** Refresh clears all pending counts; owner reassignment retains old DM budget and last-push state. Candidate/device truncation happens before counter bumps, so omitted work is never available to cron. Counter batch failure is logged but sending continues. Daily localStorage check/set is not a cross-tab lock, nor does it bind asynchronous responses to the current account. Use stable registration generations, preserve intended pending work, and distinguish bounded omission from retriable throttling. |
| **F7 — empty body is not metadata-free or delivered** | **Source and protocol evidence.** Category is sent in the clear `Topic` header, and urgency/TTL vary. `SendOutcome::Delivered` means a successful provider status, not user-agent delivery or notification display. RFC 8030 explicitly separates acceptance from delivery. Rename/record these stages separately; keep the provider request generic if category disclosure is outside the intended threat model. |

A reliable member experience needs three observable states: accepted for notification, fetched by a device, and shown or explicitly suppressed. Current counters collapse those states. Prioritise F1–F4 before enabling push for members; measure omission and preference handling before claiming reliable busy-period alerts. These are follow-up implementation recommendations. Product code and activation settings were not changed.

## External comparison and utility

WebKit requires a user-visible notification for each push and says violating that promise can revoke a subscription. Its guidance supports an explicit device acceptance test for the visible-tab branch; passing a fixture that expects no display does not establish browser compliance. [WebKit: Meet Web Push](https://webkit.org/blog/12945/meet-web-push/), checked 2026-11-01.

RFC 8030 distinguishes a provider's 201 acceptance from delivery to the user agent. It also defines the unencrypted Topic header for replacement/coalescing. The forum's counter design can remain payload-less, but should name its receipt stages and disclose the category metadata it sends. [RFC 8030, sections 5 and 5.4](https://www.rfc-editor.org/rfc/rfc8030.html), checked 2026-11-01.

ntfy documents replay from a cached message ID, timestamp or time interval, subject to server cache configuration and replay limits. That is a useful contrasting recovery model: a subscriber can resume from a position instead of destructively clearing an aggregate count before display. It is not proof of exactly-once delivery, indefinite retention or equivalent privacy. The forum could retain content-free event/sequence receipts and let devices acknowledge them, preserving its existing member/read-authority model. [ntfy subscription and replay API](https://docs.ntfy.sh/subscribe/api/#fetch-cached-messages), checked 2026-11-01.

Members need dependable alerts that respect their quiet hours. A prospective operator should be able to distinguish unsupported browser, disabled server, broken registration, throttled work and a successfully displayed alert. No market-share, demand or comparative cost claim follows from this technical review.

## Validation limits

All 85 selected checks pass: 74 existing and eleven audit cases. SQLite tests deliberately order real SQL statements to demonstrate permitted interleavings; they do not measure live D1 concurrency frequency. JavaScript tests use the actual worker with fake browser globals; the 25 ms unresolved-fetch observation is not a claim about an operating system's lifetime limit. Existing RFC signature/token tests validate primitives, not live VAPID interoperability.

No real notification, account login, push registration, deploy or provider call occurred. Browser race/receipt tests, iOS behaviour, Workers runtime execution, full workspace suites and activation evidence remain outstanding. Diagram gates and visual checks are recorded separately. The wider forum and linked-estate audit remains active.
