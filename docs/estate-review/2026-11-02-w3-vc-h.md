# VisionClaw agent integration, external services and client render state

I assessed all 42 panels in four VisionClaw topics: 27 (agent estate integration), 28 (external services), 30 (client boot and state) and 31 (graph render pipeline). Every panel was read line by line against VisionClaw `86cdd7635582`; topic 28's agentbox citations were read at agentbox `c57d9c0508f4`. Results: 8 accurate, 4 accurate-with-limits, 30 corrected, 0 inaccurate-unfixed.

All four topics were stamped at `8692b12`, which is 217 commits behind the pin, so I restamped each one and re-resolved every citation in it. The biggest change was on the client agent path. `BotsVisualization`, `BotsNode` and `agentWorkTargets.ts` no longer exist, and agents are now drawn by a single marker pass (ADR-2142), so VC-30.12, VC-31.5 and VC-31.11 were redrawn. Remapping by identical text also exposed citations that were already wrong at `8692b12`, for example most anchors in VC-27.7 and VC-30.5.

Source tracing also found five code defects in VisionClaw:
- the client's release-mode auth warning can never fire;
- remoteLogger feeds its own failure warnings back into its buffer;
- the McpRelayManager circuit breaker cannot trip and is bypassed on the start path;
- the MCP relay's "orchestrator unhealthy" branch is unreachable;
- MultiMcpVisualizationActor is never constructed.

The citation gate has a blind spot of its own. In a list such as `file.ts:312-321,336-340,365`, nothing after the first range is ever checked.

## Findings

**W3VCH-01: comma lists after a range are never checked (generator).**
- *Trigger:* `citeCheck` expands `:a,b,c` only when the first item is a bare number (`scripts/diagram-index-gen.cjs:596`). In `endpoints.ts:312-321,336-340,365`, the `336-340` and `365` are never resolved. The bare-number pattern also refuses a number followed by `.` (`:511`), so a list that ends a sentence (`workspaceApi.ts:62,80,136.`) leaves its last item unchecked; that item still holds at the pin.
- *Consequence:* these four topics contained 22 such lists. Three tails had silently gone wrong. `endpoints.ts:365` (VC-30.4) now lands on a debug log instead of the `updatePhysics` push at :369. Two `binaryProtocol.ts` tails in VC-30.10 were off by one line.
- *What was done:* I rewrote the affected lists in comma-colon form (`:316-325, :340-344, :369`), which the gate does check, and checked every remaining tail by hand.
- *To close:* make the expansion accept a range as the first item, or fail on any number it leaves unparsed.

**W3VCH-02: the client never sees its own "server is a release build" warning.**
- *Evidence:* `initializeAuthInterceptor` registers `authResponseInterceptor` as `onResponse` only (`client/src/services/api/authInterceptor.ts:131-135`). `UnifiedApiClient` runs `onResponse` only when `response.ok` is true (`client/src/services/api/UnifiedApiClient.ts:276-303`) and passes it no config. `warnIfServerInReleaseMode` (`authInterceptor.ts:27-38`) needs status 401 and a sent dev token, and `sentDevToken` reads that config (`:125-126`).
- *Consequence:* the ADR-06 §D1 hint is dead code.
- *Panel:* VC-30.8 previously drew it on an `onError` path that is never registered; corrected and marked **Debt**.
- *To close:* register the hook as `onError` (or call it before the throw) and pass the request config.

**W3VCH-03: remoteLogger re-logs its own failures.**
- *Evidence:* after a failed POST that is not a 404, `flush` calls `console.warn` (`client/src/services/remoteLogger.ts:193-194`). That is the intercepted wrapper (`:74-77`), so the warning goes back into the buffer (`:110-135`) and is posted on the next flush. A failed batch is dropped, not re-queued (`:187-199`), and `setEnabled(false)` never restores the original console (`:220-228`).
- *Consequence:* the panel claimed the call was "non-recursive, raw console". Against an endpoint that keeps returning 5xx, the logger posts at least one entry a second indefinitely.
- *Panel:* VC-30.7 corrected and marked **Debt**.
- *To close:* send internal warnings through the saved `originalConsole`.

**W3VCH-04: the McpRelayManager circuit breaker cannot protect anything.**
- *Evidence:*
  - every caller builds a fresh manager (`src/handlers/consolidated_health_handler.rs:210,428`);
  - `ensure_relay_running` calls `check_relay_status_internal` directly, bypassing the breaker (`src/services/mcp_relay_manager.rs:171`);
  - `std::thread::sleep` blocks an async executor thread for 2 s (`:194`);
  - `ensure_mcp_ready` (`:280-292`) and `start_health_monitoring` (`:237-260`) have no caller in `src/`.
- *Consequence:* the old VC-27.2 drew the breaker on the start path and showed a live 30 s health loop; neither is true.
- *Panel:* VC-27.2 rewritten, with **Debt** markers.
- *To close:* hold one manager in AppState, route the start path through the breaker, use `tokio::time::sleep`, and delete or wire the dead functions.

**W3VCH-05: the MCP relay keeps a dead orchestrator sink.**
- *Evidence:* `is_orchestrator_healthy` is only ever set to `true` (`src/handlers/mcp_relay_handler.rs:73,302`), so the unhealthy branches (`:333`, `:390`) are unreachable. When the orchestrator stream closes or errors (`:141-143`, `:167-171`), the loop ends without clearing `orchestrator_tx` or scheduling a retry.
- *Consequence:* client frames go to a dead sink and only log the failure (`:361-368`).
- *Panel:* VC-27.3 marked **Debt**.

**W3VCH-06: MultiMcpVisualizationActor is dead.**
- *Evidence:* the only reference to the actor outside its own file is a re-export (`src/actors/mod.rs:69`).
- *Consequence:* VC-27.6 still listed the `subscribers` field and the `Subscribe`/`Unsubscribe` variants that ADR-2089 removed, and cited wrong lines.
- *Panel:* class diagram redrawn from `multi_mcp_visualization_actor.rs:26-49`, `:65-99`, `:102-157` and `:224-238`, with a **Debt** note.
- *To close:* delete the actor or start it.

**W3VCH-07: `/wss/agent-events` accepts `?token=` in release builds.**
- *Evidence:* the query carrier is accepted in every build (`src/agent_events/ingest.rs:267-271`), while `/ws/mcp-relay` compiles it out of release under ADR-2058 (`mcp_relay_handler.rs:496-505`).
- *Severity:* the insecure-default escape hatch is compiled out of release (`ingest.rs:64-68`), so this is a credential-in-logs exposure, not an authentication bypass.
- *Panel:* VC-27.13 marked **Tension**.
- *To close:* apply the ADR-2058 cfg gate here too.

**W3VCH-08: `/api/visualization/agents/ws` has no token check of its own.**
- *Evidence:* the upgrade runs no session check (`src/handlers/bots_visualization_handler.rs:204-210`), and the `/api` RbacGate lets public reads through (`src/main.rs:1131-1137`).
- *Consequence:* today it only ever streams an empty roster.
- *Panel:* VC-27.11 marked **Open**.
- *To close:* decide the policy before a real roster source is wired in.

**W3VCH-09: the BotsClient "superseded" label is wrong.**
- *Evidence:* AppState starts the `:9500` poll at boot with backoff (`src/app_state.rs:1185-1196`), and `ingest.rs:16-20` calls it not deprecated and the only agent-state snapshot source.
- *Panel:* VC-27.1 marked **Tension**; its anchors were corrected (struct `:108`, `new()` `:120-126`, connection stores `:153,166,171`, tests `:312,337`).

**W3VCH-10: the agent capsule's "done" fade is reachable only by `offline`.**
- *Evidence:* the shader treats activity below 0.1 as done (`client/src/rendering/materials/AgentCapsuleMaterial.ts:165-167`). Agent activity now comes only from `agentStatusActivity` (`client/src/features/bots/agentVisualConstants.ts:96-108`, packed at `GemNodes.tsx:1010-1011`), where only `offline` maps below 0.1.
- *Consequence:* the material comment (`:163-164`) still describes the deleted work-target beam.
- *Panel:* VC-31.5 marked **Drift**.

**W3VCH-11: product documentation drift.**
- `docs/reference/configuration.md:233` still points the Perplexity readiness read at `app_state.rs:1516`; it is now at `:1488` (VC-28.3, **Drift**).
- `layoutApi.setMode` no longer translates mode names (`client/src/api/layoutApi.ts:47-60`). `toEngineLayoutMode` is gone under ADR-2140, and the old VC-30.8 still described it.

**W3VCH-12: two JEV advisories from the baseline run were real defects.**
- `ragflow_handler.rs:383/393` (VC-28.2) are a log line and a struct field. The missing-Authorization 401 is at `:259-262`/`:266-269`.
- `GraphManager.tsx:135` (VC-31.10) is off by one: `useFpsMonitor()` is at `:134`.

`ragflow_service.rs:420` (VC-28.1) is the comment that opens the streaming arm; the arm starts at `:419`, which is now cited.

`binaryProtocol.ts:425` (VC-31.9) was a doc-comment line; the handler is at `:427`. `GraphManager.tsx:386` (VC-31.2) disappeared when the panel was rewritten.

A final-run advisory on my own rewrite, `GraphManager.tsx:472-480`, was right: the label copy is `fillLabelPositions` at `:482`, now cited as `:474-484`. That check also showed the edge hook runs at priority -0.5 and GemNodes at -1, not -2 as VC-31.2 and VC-31.4 claimed (`useEdgeBufferComputation.ts:173`, `GemNodes.tsx:1049`); both are corrected.

## Verification

**Evidence class.** Source tracing only, at the pinned revisions: VisionClaw `86cdd76355823a51bb64d503c005fe277726e724`, read with `git show`/`git grep` and never from the working tree; and agentbox `c57d9c0508f4044915f9aecea4b9aa5629cc6a35` for topic 28's `../project/agentbox/...` citations, read in the submodule checkout. No product test, runtime, browser or deployment check was run. No product code was edited.

**Restamps:**
- Topics 27, 30 and 31: `visionclaw` restamped from `8692b12` to `86cdd76`.
- Topic 28: `visionclaw` restamped to `86cdd76`, and `agentbox` from `6500582` to `c57d9c0`.

**How citations were re-resolved.**
1. A script replicating the gate's binding rules (participant-bound bare numbers, same-line continuation, comma expansion) extracted every citation. Its counts matched the gate for three topics; for topic 30 it found 473 against the gate's 472. The extra item is the unchecked sentence-final `workspaceApi.ts:136` (W3VCH-01): that file did not change, so the remap left the number alone, and it still holds at the pin.
2. Lines outside diff hunks between the two revisions were moved only where the line text was identical at the pin.
3. Lines inside hunks, and lines in deleted files, were re-derived by hand from the symbol with `git grep -n`.
4. Every panel was then read against the pin, which caught citations that were already wrong at `8692b12`.
