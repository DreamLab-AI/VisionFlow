## agentbox / critical

### F-01 — Default boot widens the host Docker socket for devuser: any agent-run command gets host root
- Topics: AB-02.24, AB-06.13, AB-05.16
- Evidence: `role_isolation` defaults false (`agentbox.toml.schema.json:1981-1984`); with the flag off the entrypoint runs `chmod o+rw` on the host socket every boot (`config/entrypoint-unified.sh:589-592`), and compose binds the host socket rw (`docker-compose.override.yml:117`). The material itself states the consequence: "the Docker daemon is root on the host, so while devuser can drive it every in-container boundary is void" (custody design §0, bypass 1), and R2: earlier boots leave the host inode o+rw, narrowed only by a host-side chmod (`docker-compose.override.yml:116-117`). The mitigation is not safely enableable yet — under the flag "JunkieJarvis, the mirror hook and dream-engine cannot sign" until W3b (`agentbox.toml:2220-2226`, AB-05.16 drift note).
- Failure: any LLM-driven Bash command in a session (runs as devuser) talks to `/var/run/docker.sock`, mounts the host filesystem or spawns a privileged sibling — full host compromise that bypasses every in-container control (users, seccomp, capabilities) the material documents.
- Confidence: high
- Severity: high
- Marked by authors: yes (custody bypass 1; OPEN R2 in AB-06.13; AB-05.16 drift)

### F-02 — One OS user for everything: PID 1 hands every secret to all supervised programs, and all key files are devuser-readable
- Topics: AB-02.24, AB-02.14, AB-11.16, AB-02.12, AB-07.9
- Evidence: with `role_isolation` off (the default) `_ab_role_env_capture`/`_ab_role_env_scrub` "return at their first line, and PID 1 still carries every `.env` key" (`entrypoint-unified.sh:411`, `:1221` — the invariants are stated only under the flag); every supervised program inherits PID 1's env (AB-02.14), nostr-gateway receives `AGENTBOX_PRIVKEY_HEX` (`flake.nix:2280`, AB-07.9), and `/run/secrets/nostr.key` is written 0400 devuser when the flag is off (`entrypoint-unified.sh:1020`). Files are no better: "a 0600 file is a same-uid boundary only. Every agentbox process runs as devuser, so co-resident code can read the agent key, the bridge key and the AoE daemon token alike" (AB-11.16 DIVERGENCE). Profile isolation is explicitly "NOT an OS access boundary" (ADR-2007, AB-02.12).
- Failure: a prompt-injected agent — or any dependency it installs — runs `env` or reads `/run/secrets/nostr.key` as devuser and exfiltrates or uses the operator's Nostr signing key, signing kind-31403 governance decisions as the house identity. No per-process boundary exists to stop it.
- Confidence: high
- Severity: high
- Marked by authors: yes (DIVERGENCE in AB-11.16; invariants scoped to the flag in AB-02.24)

### R-1 — The host Docker socket grants devuser host-root by default, and nothing inside the container can narrow it
- Topics: AB-06.13, AB-02.24, AB-11.16
- Chain of events: agent-side code is compromised (prompt injection through a DM, a voice transcript, browser-sidecar content, or any devuser-run MCP/consultant tool) → it runs as devuser → with `[security].role_isolation = 0`, the shipped default, the entrypoint has widened the host socket `o+rw`, so devuser drives the host Docker daemon → the daemon is root on the host, so the attacker mounts the host filesystem or spawns privileged containers → host credentials (including the bound `~/.claude`), backup credentials and client data are exfiltrated or destroyed. Flipping the flag on does not fix a already-widened socket: it is the host's own inode and only a host-side `chmod 0660` narrows it.
- Evidence: host socket bound rw into agentbox (`docker-compose.override.yml:117`); flag-off boot does `chmod o+rw` every boot (`entrypoint-unified.sh:589-592`); OPEN R2 — "the socket is the HOST inode, earlier boots left it o+rw, and only a host-side chmod 0660 narrows it" (`docker-compose.override.yml:116-117`); flag ships off (`agentbox.toml:2227`, `setup/agentbox.default.toml:1664`); custody rationale: "while devuser can drive it every in-container boundary is void" (custody design §0, bypass 1, cited at AB-06.13); every process runs as devuser, so the landing plane is shared (AB-11.16 DIVERGENCE).
- Warning signs visible today: OPEN R2 registered with owner question Q2 and deliberately registered once, in AB-36; the entrypoint's flag-off branch re-widens the socket on every single boot; the custody rehearsal gating the flag had not passed at the stamped commit.
- Confidence: high
- Severity: high

### R-2 — `payment_settlement` is declared zero-tolerance but no route ever passes it to the authority gate
- Topics: AB-05.13, AB-11.10, AB-03.10
- Chain of events: a spend or settlement is initiated (`POST /v1/pay/buy`, `/v1/pay/withdraw`, `POST /v1/llm/receipt`, or the `paymentGate` on `POST /v1/comfyui/workflow`) → the manifest declares `payment_settlement` zero-tolerance with task properties, expecting a signed kind-31403 escalation → but no route passes that action class to the authority gate — `mandate_revoke` is the only class any route names (`management-api/routes/llm-marketplace.js:473`) → the payment path executes on the caller's own credential with no signed approval binding and no `authority.deny` journal record, because the gate was never invoked → a forged or mis-scoped settlement (see R-3 for how the caller identity can be forged) moves real value with no durable authority trail.
- Evidence: author-marked Debt: "`payment_settlement` is declared `zero-tolerance` with its own task properties (`agentbox.toml:1134`, `:1182`) but no route passes that action class to the authority gate; `mandate_revoke` is the only class any route names (`routes/llm-marketplace.js:473`)" (AB-05.13); the gate only acts when a caller invokes it with an action class, and its task-property triple tightens but is caller-triggered (`authority.js:378`, `:438`, `:52`); the money routes carry only generic auth/payment guards in the route tables (payments.js:147-525, llm-marketplace.js:100-556, comfyui.js:74).
- Warning signs visible today: the Debt line itself; the fact that exactly one route in the entire estate wires any authority class.
- Confidence: high that the class is unwired (author-stated); which payment route triggered the incident is inferred
- Severity: high

## Not judgeable from this material

# Post-mortem — client-attributable data custody failure

Twelve months after the verified state of this material, a client terminated after demonstrating that data they had asked to be erased was still retrievable through the agent memory search path, and that state they relied on (governed ontology additions) had vanished after a routine forced resync. Forensic work is not complete; the three root causes below are ranked hypotheses, each independently sufficient to produce a client-loss-grade custody, security or data-loss failure. Everything cited is as the material states it; where I reason past the material I say "inferred".

### R-1 — Erasure is structurally incomplete: Pod delete never reaches RuVector, and the provenance/decision stores have no decided erasure mechanism at all
- Topics: VC-22.6, VC-22.1, VC-22.4, VC-22.5, VC-22.7
- Chain of events:
  1. Client requests erasure of their agent memory. Operator (or client UI) runs the only delete path that exists: `deleteAgentMemory`.
  2. That path deletes one Pod resource and reports success — including when the resource was never there (`deleteResource` treats 404 as success, ldpClient.ts:210,215).
  3. The embedding row in RuVector (external Postgres, the declared write-master for vector/agent memory) is untouched — no tombstone, no propagation hook exists anywhere in the path.
  4. Separately, the client's transcripts/decision records persist in `GRAPH_PROVENANCE` (append-only by invariant) and in SQLite (`kpi_agent_events`, `enrichment_decisions`); retraction "only ADDS dl:validTo and deletes nothing". The one mechanism that would reconcile append-only provenance with erasure (crypto-shredding, ADR-2102) is still only PROPOSED — the ADR's stated purpose is to force the choice "rather than leave it to omission", and no closure is recorded.
  5. Client demonstrates their content is still searchable. Contract lost.
- Evidence: "no reverse tombstone to RuVector - embedding row persists and stays searchable (docs/DATA-authority-erasure.md:87)"; the delete path "never calls mcp__claude-flow__memory_delete or any RuVector endpoint" (client/src/services/solidPod/agentMemory.ts:191, client/src/services/solidPod/ldpClient.ts:206); provenance append-only invariant (crates/visionclaw-adapters/src/provenance_emitter.rs:32-33; provenance_writer.rs:218,478-502); ADR-2102 still PROPOSED (VC-22.4 note); RuVector as write-master (VC-22.1).
- Warning signs visible today: the DIVERGENCE box in VC-22.6 is already the incident, pre-verified; the backup script's own contract confirms Oxigraph (which holds provenance) has "NO point-in-time backup" (VC-22.11 DriftNote), so even a "restore from backup" remediation path does not exist.
- Confidence: high
- Severity: high

### R-2 — Shipped RBAC posture: public reads on, and every authenticated-but-unassigned pubkey resolves to Editor
- Topics: VC-22.9, VC-20.7, VC-33.6
- Chain of events:
  1. Operator deploys with the shipped compose, which sets `RBAC_PUBLIC_READS=1` and `RBAC_ALLOW_OWNERLESS=1` (docker-compose.unified.yml:106,107).
  2. Code-level fail-closed defaults are inverted by env: `public_reads_enabled()` is `.unwrap_or(false)` in code (src/middleware/rbac_gate.rs:126-133) and main.rs:795,801 refuses to start owner-less — but the compose flags re-open both.
  3. No Owner is assigned (the flag exists precisely to permit that), so the only fallback is `POWER_USER_PUBKEYS` to Admin.
  4. Any nostr pubkey that authenticates (NIP-98) and has no explicit role resolves to **Editor** — the third of four write-capable tiers (src/services/role_store.rs:359, default Editor unless `RBAC_DEFAULT_ROLE=viewer`, role_store.rs:366).
  5. Anonymous clients read; arbitrary authenticated keys mutate whatever the RbacGate lets Editor touch.
