# agentbox ruvector-catalog ADR-007 to ADR-009

I assessed three ADRs: `skills/ruvector-catalog/docs/adr/ADR-007`, `ADR-008` and `ADR-009` in agentbox at `c57d9c0508f4`, 73 headed sections in all (23, 21 and 29, title headings included). All three are **imported copies**. The upstream owner is `mamd69/ruvector-catalog`; `ruvnet/ruvector` is only the catalogued monorepo. agentbox adopts none of their obligations, so **0 adopted decisions**: 70 sections are `imported, not adopted`. The other three sections are the estate-authored "Closeout extension — 2026-09-05" sections. Those make claims about the vendored source, so I assessed them against the pin, and all three hold. The most important finding is that the vendored V3 code hard-codes the benchmark's own queries into its intent classifier. ADR-009's acceptance queries and the "A/A+" grades in `BENCHMARK-RESULTS.md` therefore measure tuning on those queries, not generalisation. This supports the closeout's demand for held-out evidence. Second, the vendored search engine differs from ADR-007 on threshold, ranking arithmetic, domain routing and the HNSW stage. Third, ADR-008's catalogue-level types and most of its new fields are absent, unread or unpopulated.

## Findings

### F1. The benchmark queries are encoded in the classifier (hold-out contamination)

- **Trigger:** running ADR-009's five benchmark queries, or reading `BENCHMARK-RESULTS.md` as evidence that V3 meets ADR-009 §5.
- **Consequence:** the V3 passes and grades are not held-out evidence. Three of the five queries hit literals written into `intent.ts`, and a fourth is helped by the data:
  - **Q2:** `'best selling books'` is an `OUT_OF_SCOPE_STRONG_PATTERNS` entry (`skills/ruvector-catalog/src/discovery/intent.ts:51-57`). A single match yields out-of-scope at 0.9 confidence (`intent.ts:248-257`), unless a problem section also matches (`intent.ts:140`). That is exactly the "90% confidence" in `BENCHMARK-RESULTS.md:10`.
  - **Q4:** `'ruvector-catalog'`, `'technology recommender'` and `'improve the ruvector'` are `META_SIGNALS` (`intent.ts:33-38`). A meta match injects `sona`, `reasoning` and `hnsw` into the query (`intent.ts:119-131`). That is the ReasoningBank #1, SONA #2 result in `BENCHMARK-RESULTS.md:12`, which ADR-009 §5.1 Q4 requires.
  - **Q5:** `'clinical'` and `'healthcare'` are vertical keywords (`intent.ts:26`). A match then forces every healthcare-vertical technology into the results (`search.ts:186-212`).
  - **Q3 (suggestive only, not a classifier literal):** OSpipe is the only technology in the defaults file with a non-empty `useCases` array (`src/catalog/data-cap-defaults.ts:185`).
- **Evidence class:** source tracing only. I did not run the queries.
- **What would close it:** a held-out query set disjoint from the classifier's literals, with results bound to source and data revisions. Raw similarity should be reported separately from boosted scores. This is the closeout's own CP acceptance condition.

### F2. The vendored search engine is not ADR-007's design

- **Trigger:** any CLI `search`.
- **Consequence:** ADR-007's threshold derivation and its precision projections describe a different algorithm from the one that ships. The differences:
  - **Threshold:** 0.15, not 0.25 (`src/discovery/search.ts:27`). For vertical queries the initial cut is 0.045 (`search.ts:175`).
  - **Weighting:** done by repeating text (`search.ts:69-75`, `:274-280`) before sublinear TF (`src/discovery/embeddings.ts:103`). A ×3 field therefore contributes about 2.1×, not 3×. `crate`'s 0.5 rounds up to 1 (`search.ts:276`), so the crate name counts as much as the name.
  - **Retrieval:** a linear scan over all documents (`search.ts:179-184`). There is no HNSW stage (`search.ts:4`).
  - **Domain routing:** there is no first-pass domain filter. Only a vertical match filters, and only after scoring (`search.ts:186-212`).
  - **Re-ranking:** additive bonuses (+0.1 primary, +0.05 production, +0.05 keyword overlap, `search.ts:216-223`), not the ADR's ×1.2, ×1.05 and ×1.02 multipliers or its +0.1 exact-term bonus. The CLI prints the boosted score unlabelled (`cli.ts:94`), so values up to about 1.2 are possible.
  - **No-match message:** a query with nothing above threshold prints "Found 0 matches" (`cli.ts:92`). The out-of-scope message (`cli.ts:86-90`) depends on the classifier, not on the score threshold that ADR-007 §3 specifies.
- **What would close it:** the owner ratifies the implemented algorithm or amends the code (the closeout's CP-01/03/07/08/09 condition).

### F3. ADR-008's data model is partly typed, little read and largely unpopulated

- **Trigger:** any consumer relying on ADR-008's field semantics.
- **Types present:** the `Technology` and `Capability` extensions match exactly (`src/types/index.ts:42-48`, `:61-64`).
- **Catalogue-level types absent:**
  - There is no `Catalog` interface.
  - `outOfScope` is a `string[]`, not `OutOfScopeCategory[]` (`src/catalog/data-sections.ts:164`, `src/catalog/store.ts:23`).
  - `VerticalMapping` has a different shape (`types/index.ts:228-233`).
  - `ProblemSolutionEntry` is replaced by `ProblemSection` (`types/index.ts:220-226`).
- **Fields never read:** `grep` over `src/` outside the data files finds no reader of `primaryFor`, `relatedExamples` or `relatedCapabilities`.
  - The primary boost uses `cap.primaryCrate === tech.crate` (`search.ts:108`), not `primaryFor`.
  - The vertical filter uses `VERTICALS` technology IDs (`search.ts:189-193`), not `tech.verticals`, which is only appended to the indexed text (`search.ts:80`).
  - Capability `synonyms` and `problemStatement` are unused. Section synonyms come from `PROBLEM_SECTIONS` instead (`intent.ts:241`, `:312`).
- **Population:** the catalogue holds 60 technologies in 16 capabilities, not 80. `useCases` is non-empty for 22 of the 60: all 21 in `data-cap-enriched.ts` and 1 of 39 in `data-cap-defaults.ts`. `verticals` is empty for 41. `plainDescription` is present for all 60.
- **Generation path missing:** `package.json:16` names `scripts/build-catalog.ts`, and `package.json:21-24` publish `catalog.json`, `templates/` and `VERSION`. None of these exists in the tree at the pin (`git ls-tree` of `skills/ruvector-catalog/`).
- **What would close it:** an authoritative data source with field-coverage validation, which is the closeout's condition.

### F4. The ADR set disagrees with itself and with the later report

- **Evidence class:** document consistency only.
- **Different queries:** ADR-007's V2 table (`ADR-007:38-46`) uses a "database mobile" Q3 and a healthcare Q5. ADR-009 §1.3 (`ADR-009:42-48`) defines Q3 as desktop monitoring.
- **Conflicting Q1 result:** ADR-007 gives prime-radiant 0.52 as V2's top match for a short "hallucination detection" query (`ADR-007:40`). ADR-009 §2.1 uses the full-sentence query and puts prime-radiant at #4 with 0.15 (`ADR-009:62`), while saying its V2 values come "directly from the benchmark reports" (`ADR-009:12`). These may be two different runs, but they cannot both be "the" benchmark, and neither ADR names its run.
- **Conflicting grades:** `BENCHMARK-RESULTS.md:9-13` re-grades the same measured runs differently. V2 Q1 is B- there and C in ADR-009 (`:65`). V1 Q2 is C there and F in ADR-009 (`:83`). Repo Q1 is C there and D in ADR-009.
- **Latency criterion:** the same report gives V3 at 26 ms warm (`BENCHMARK-RESULTS.md:24`). ADR-009 §5.2 requires under 10 ms. The two figures measure different things (CLI process against in-context reading), which is the closeout's point. Either way, the report does not show the criterion met.
- **What would close it:** one revision-bound measurement record that the ADRs cite instead of restating figures.

### F5. The vendored SKILL.md no longer carries the CAG design ADR-009 accepts

- **Trigger:** ADR-009 §5.2 "All problem-solution headers from V1 SKILL.md preserved", and ADR-007's Neutral consequence that the CLI is secondary to SKILL.md.
- **Consequence:** at the pin, `SKILL.md` is an 84-line "Architect's Playbook" (`skills/ruvector-catalog/SKILL.md:6`). It has no problem-solution headers and no scope-boundary section. One header survives in `references/capability-map.md:31`. In this copy, the CAG premise the accepted ADR depends on is gone. agentbox commit `79715e7bd` ("Claude-5 context-engineering upgrade") cut the vendored file from 237 lines with four "I need to" headers (as imported at `5c194927c`) to 72 lines with none. I did not compare with upstream.
- **What would close it:** an annotation on the ADR recording that the agentbox copy diverged, or restoring the headers.

### F6. The closeout's cross-repo link depends on the checkout layout (Drift)

- **Trigger:** following the closeout links in a standalone agentbox checkout.
- **Consequence:** the six-level `../../../../../../VisionFlow/...` link resolves here only because `/home/devuser/workspace/agentbox` is a symlink to `/home/devuser/workspace/project/agentbox` (`readlink -f`). In a plain agentbox clone it points above the workspace and 404s. `BENCHMARK-RESULTS.md:3` already admits this for its own link.
- **What would close it:** an absolute repository URL.
