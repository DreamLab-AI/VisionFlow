# VisionClaw settings, hexagon, observability and config topics (wave 3, w3-vc-c)

I assessed all 42 panels in VisionClaw topics 06 (settings round trip), 07 (hexagonal ports and crates), 08 (observability, health and dev loop) and 09 (config and env flags). The method was source tracing at VisionClaw `86cdd7635582`. All four topics were stamped `8692b12` and cite files that changed in the 217 commits since, so I restamped every topic to the pin and re-resolved every citation from its symbol.

Result: 7 accurate, 31 corrected, 4 accurate-with-limits, 0 inaccurate-unfixed. Most corrections are line drift, but nine are substantive.

The most important finding is in VC-06.6. The panel drew the api-keys routes driving eight `ProtectedSettingsActor` messages. At the pin only `GetApiKeys` has a sender. `POST /api/auth/nostr/api-keys` writes the `NostrService` user map, while `GET` on the same resource reads an actor that starts from defaults and is never written, so on source evidence a user never reads back the keys they saved.

## Findings

### F1. API keys written to one store and read from another (VC-06.6, Tension)

- **Trigger:** a non-power user calls `POST /api/auth/nostr/api-keys`, then `GET` on the same resource.
- **Consequence:** the GET answers `default_api_keys`, not the saved keys. Seven of the eight `ProtectedSettingsActor` handlers (`ValidateClientToken`, `StoreClientToken`, `UpdateUserApiKeys`, `CleanupExpiredTokens`, `MergeSettings`, `SaveSettings`, `GetUser`) have no sender anywhere in `src/` or `crates/`. A second copy of the actor also exists in `crates/visionclaw-actors`.
- **Evidence:**
  - POST: `src/handlers/nostr_handler.rs:293` calls `src/services/nostr_service.rs:484-508`, which writes `user.api_keys` at `:495`.
  - GET: `src/handlers/nostr_handler.rs:319` reads `src/app_state.rs:1578-1586`, which sends `GetApiKeys` to the actor started as `ProtectedSettingsActor::new(ProtectedSettings::default())` at `src/app_state.rs:1159`. The `Default` impl seeds `users` with an empty `HashMap::new()` (`crates/visionclaw-domain/src/models/protected_settings.rs:132`), so `crates/visionclaw-domain/src/models/protected_settings.rs:223-236` returns `default_api_keys`.
  - Mount: the routes sit under `/api` (`src/handlers/api_handler/mod.rs:120`, scope `/auth/nostr` at `src/handlers/nostr_handler.rs:54`).
  - Duplicate actor: `crates/visionclaw-actors/src/protected_settings_actor.rs:7`.
- **What would close it:** have both verbs use one store (read from `NostrService`, or route the POST through `UpdateUserApiKeys`), delete the unreachable handlers and the duplicate crate copy, and add a round-trip test. This needs a runtime check to confirm the observed behaviour.

### F2. A layout reset leaves the settings actor's snapshot stale (VC-06.4, Open)

- **Trigger:** `POST /api/settings/physics/reset-layout`, followed by any physics PATCH.
- **Consequence:** `reset_layout` writes the defaults to the GPU actors and to SQLite but never sends `UpdateSettings`. `apply_physics_patch` merges onto the actor snapshot, so fields the PATCH does not name are written back with their pre-reset values. Nothing reloads the snapshot until the process restarts: the hot-reload watcher is disabled and nothing sends `ReloadSettings`.
- **Evidence:**
  - Reset writes GPU and SQLite only: `src/settings/api/settings_routes.rs:1823-1863`.
  - The PATCH merge base is the actor snapshot: `:618` and `:637`.
  - GET reads SQLite first: `:480-485`.
  - Reload exists but nothing sends it: handler at `src/actors/optimized_settings_actor.rs:1182-1201`; watcher disabled at `src/app_state.rs:1125-1129`.
- **What would close it:** send `UpdateSettings` with the reset physics from `reset_layout`, or merge from `stored_physics()`. This needs a runtime check to confirm.

### F3. A GPU refusal leaves the snapshot ahead of the store (VC-06.3, Tension)

- **Trigger:** `GPUComputeActor` refuses an `UpdateSimulationParams` that has already passed `validate_for_gpu`.
- **Consequence:** the request returns 500, but the actor snapshot already holds the value. The SQLite write and the broadcast are skipped.
- **Evidence:** `src/settings/api/settings_routes.rs:673-680` (`UpdateSettings` succeeds first), `:700-706` (early return), `:774-779` and `:796` (skipped).
- **What would close it:** call the GPU actor before `UpdateSettings`, or roll the snapshot back on refusal.

### F4. `generate_types` does not read Rust structs for settings (VC-06.9, Drift)

- **Trigger:** a developer adds a field to `PhysicsSettings` and runs `cargo run --bin generate_types`, as `AGENTS.md:13` instructs.
- **Consequence:** `settings.ts` does not change. `generate_typescript_interfaces` returns a hand-written raw string. Only `ontology-agent.ts` is built from Rust values.
- **Evidence:** `src/bin/generate_types.rs:64-570` (the string), `:576-597` and `:768-776` (the ontology writer). The project doc makes the "from Rust structs" claim at `AGENTS.md:13`. This was already true at `8692b12`, so the old panel's "read the settings type graph" was never right.
- **What would close it:** derive the TypeScript from the types (the domain structs already derive `Type`, `crates/visionclaw-domain/src/config/visualisation.rs:510`), or correct `AGENTS.md`.

### F5. The ADR-2049 warm-up stage still cannot fail on a dependency compile error (VC-08.11, Tension)

- **Trigger:** a dependency stops compiling.
- **Consequence:** the production stub stage stays green. `cargo build --release 2>&1 | tail -40 || echo ...` runs with no `pipefail`, so the stage's status is `tail`'s.
- **Evidence:** `Dockerfile.production:101-102`. No `SHELL` or `pipefail` appears anywhere in the file. The stated intent is the comment at `:89-93`, and only `cargo fetch --locked` at `:100` actually gates the layer.
- **What would close it:** `SHELL ["/bin/bash","-o","pipefail","-c"]`, with a separate dependency-only build step.

### F6. Build-input env list does not match the build scripts (VC-08.10, Drift and Debt)

- **Trigger:** change `NVCC_CCBIN` or `CUDAHOSTCXX`.
- **Consequence:** the wrapper's stamp does not change, so the timestamp gate can skip a rebuild that cargo itself would run. The doc comment claims the list mirrors the build scripts' `rerun-if-env-changed` declarations, and it does not.
- **Evidence:**
  - The list and its comment: `scripts/lib/build-inputs.sh:46-48`, with the header claim at `:15-17`.
  - What the scripts actually declare: `build.rs:43-45` and `crates/visionclaw-gpu/build.rs:50-54`.
- **What would close it:** add the two variables to the list and correct the comment.
