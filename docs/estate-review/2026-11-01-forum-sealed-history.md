# Forum sealed-history migration and reader contracts

ADR-2017 preserves signed authorship through encryption, and its migrator verifies both envelope signatures and recovered originals before deletion. The remaining gaps concern what that verification proves: it can accept an envelope the forum reader rejects, mark retained plaintext as purged, and finish its recorded set while undiscovered plaintext remains. The independent JavaScript reader also accepts inputs that the Rust format rejects.

## Scope and evidence

This is a whole-document assessment of forum **ADR-2017**, including its six alternatives, consequences, verification record and first-production-run account. ADR-2016 key distribution, ADR-2026 recovery and ADR-2028 replacement key management remain separate assessments. Reading their references does not count as completing those decisions.

Source baseline: forum `c39f41f104b114d6a3fa29013daaf6fa58b45080`; agentbox `9dfc27b16e82e9786535a55e790710493dd51fdf`. The 28 forum exports in the [evidence manifest](evidence/2026-11-01/nf-sealed/source-manifest.json) match the original diagram revision `1b27f79`. Twenty-six also match website-consumed pin `9c36b60`; the other two differ only in `SigningKey::from_bytes` argument conversions, including test/example sites. These comparisons establish source identity and the inspected differences, not the revision currently running remotely.

Tests use fixed synthetic keys and an in-memory relay. The real migrator library, core crypto and reader implementations are exercised; the fake relay does not execute Worker admission, D1 transactions or WebSocket transport. No production keys, grants, account changes or purge calls were used. [Reproduction instructions and logs](evidence/2026-11-01/nf-sealed/README.md) distinguish existing tests from added probes. The earlier September production run remains historical evidence, not a fresh deployment verification.

## ADR-2017 section assessment

| Section / obligation | Current evidence and disposition |
| --- | --- |
| Metadata: accepted, complete, live; format/MLS/drift/deletion/search review triggers | The implementation and historical close-out exist. “Complete” does not close the issues below. A reader-contract revision and post-purge verification are additional useful triggers. Current live identity is not established here. |
| Context: preserve signed history without author forgery or tombstones | Supported by `core/src/sealed.rs:312–417`. The inner event retains its author's signature. Silent deletion avoids introducing a kind-5 against the restored original ID. The ADR's symmetric drift description is stale: the exemption now covers only the past bound. |
| Decision: outer kind, migrator author, time, e/zk/sealed tags, ciphertext and signature | `sealed.rs:312–350,449–492` builds this shape. The encrypted payload is the serialised seven-field event. Public tags expose the original ID and zone/epoch/key as well as the channel; see H7. |
| Opening: six checks and strict seven-field JSON | Rust `open_sealed` checks kind, original signature/ID, marker ID, absence of inner zk, channel and timestamp; `InnerWire` rejects unknown/duplicate fields. Outer verification and zone-key selection belong to callers. Migrator `open_and_check` verifies the outer signature but omits a reader-required zk public-key binding (H1). JavaScript diverges on duplicate fields and missing zk (H5). |
| Reader substitution, deduplication and delayed key arrival | Client `read_cache.rs:42–143` restores the whole original, remembers envelopes, replaces placeholders and deduplicates restored IDs. Its tombstone predicate can keep a restored original hidden. This supports local message identity, not every retrieval route: direct original-ID lookup still fails after purge (H7). BBS's keyless placeholder behaviour remains the separately reviewed signer/masking boundary. |
| Relay rules | `nip_handlers.rs:1440–1468,1717–1763` requires admin authority and an encrypted mapped zone for any sealed marker. Parseable sealed kind-42 gets a past-only timestamp exemption; future drift remains bounded. `zone_config.rs:208–227` checks tag/content shape, not actual decryption, secret possession or the current epoch key. This corrects the older NF-12.11 description. |
| Silent purge: authentication, limits, kind, no tombstone/broadcast, audit and response | `admin_events.rs:89–128,145–152,209–314` validates 1–200 hex IDs and a nonblank reason, authenticates NIP-98 admin, deletes only kind 42 and returns outcomes. The endpoint itself accepts any kind-42 ID, including an envelope; proof of a replacement belongs to the CLI. Logging is attempted after deletion and its error is discarded (H6). |
| Migrator: identity, keys, channel map, commands, persistence | `cli.rs:148–253` checks relay admin, selects commands and reports summaries. Keys come from the environment/key file/grants; `keys.rs:250–280` refuses conflicting keys and chooses the highest held epoch. `grants.rs:92–165` verifies wrap/seal signatures, author consistency and admin grants. `channels.rs` validates the explicit channel map. State binds relay and migrator; atomic save fsyncs the temporary file then renames it (`state.rs:186–206,259–277`). No multi-process writer lock or directory fsync is established. H2–H4 qualify success and recovery. |
| Alternative 1: admin text re-post | Correctly rejected: it changes authorship and IDs. The envelope keeps an independently verifiable signed original. |
| Alternative 2: kind-5 purge | Correctly distinguished from storage migration: client deletion semantics can hide restored originals. NIP-09 is an author deletion request, not a promise of global erasure. |
| Alternative 3: a new envelope kind | Retaining kind 42 reuses existing channel filters, but existing kind-42 filters do not make original-ID and hidden reply-tag searches work. Compatibility is conditional (H7). |
| Alternative 4: migration-time timestamps | Keeping the original time preserves chronological placement. It also requires completeness-aware timestamp pagination (H3). |
| Alternative 5: no relay exemption | Historical messages would fail the ordinary age bound. The implemented past-only exception is narrower than the text's blanket exemption. |
| Alternative 6: delete without preservation | Correctly rejected for historical continuity. H1 and H4 show why independent-reader and post-purge checks must accompany preservation claims. |
| Consequences: metadata and BBS attribution | The outer author is the migrator; original author/reply/p tags are inside ciphertext. The exposed original ID allows correlation with any retained old copy, so author unlinkability is not established. BBS attribution is deliberately limited. |
| Consequences: cached plaintext, backups and search embeddings | These exclusions are real limits. Migration cannot erase another holder's copy. No retention expiry, cache purge or historical embedding cleanup was executed or proved here. Treat each as a separately owned follow-up with evidence. |
| Consequences: agent exclusion, migrator access, epoch rotation | The migrator must possess the target keys. Removing an agent cohort or rotating the current key does not erase copied old keys. A dedicated revocable admin reduces future service access, but cannot revoke old plaintext/key copies. The runbook's “not an agent” prerequisite needs qualification for ADR-2016's `agent_keys=true` exception. No cohort changes were made. |
| Consequences: irreversibility, guarded exemption and versioning | Accepted deletion is destructive at the relay; backup recovery is separate. Relay gates and future bounds remain material. Unknown/malformed sealed input must fail in every reader, which JavaScript currently does not always enforce (H5). |
| Consequences: original-ID permalink and nightly suggestion follow-ons | Still open in current source. `note_view.rs:106–110` uses `ids:[original]`; agentbox suggestions `:296–297` queries original root/reply tags. Substituting after retrieval cannot retrieve an envelope excluded by those filters. |
| Verification: historical workspace checks and feature tests | The ADR's 2,280-test/full-workspace/WASM/deny/rustdoc record belongs to its named historical commits. This audit records fresh scoped tests separately; it does not reissue that entire certificate. |
| First production run: 430 sealed/verified/purged, read-back, logged-out checks, backup and admin logs | Preserved as the ADR's dated account. No independent current database or deployment observation was made. The account does not demonstrate first-removal rotation or resolve today's reader and completion gaps. |

## Findings and acceptance criteria

| Finding | Evidence, consequence and required follow-up |
| --- | --- |
| **H1 — migrator verification can approve a client-unreadable envelope** | **Reproduced, high recovery priority.** `engine.rs:544–602,654–691` opens with a recorded/selected secret without checking the zk public key against it. An existing valid admin-signed envelope encrypted under epoch 2 but declaring another valid public key is adopted, verified and its original purged. Client `zone_crypto/mod.rs:489–490` rejects that disagreement. The normal constructor produces a correct tag; this requires malformed admin-generated/imported data, not an unauthorised publisher. Require the same zone/epoch/public-key binding as readers before adoption, verification and purge; add a client-reader round trip to migration acceptance. |
| **H2 — inconsistent success responses become irreversible local success** | **Reproduced, high reporting priority.** A relay response `{"deleted":0}` with no outcome IDs leaves the original present, but `engine.rs:483–510` marks it purged and only emits a warning. A retry sends no delete. `cli.rs:246` judges success from an empty skipped list. This fixture models an inconsistent successful peer; the actual handler's ordinary partial D1 failure returns HTTP 500, which `NetRelay` rejects. Reject incomplete/overlapping/out-of-request outcome sets, retain uncertain entries as retryable, and verify absence before declaring purge complete. A dishonest remote can still lie; document that trust boundary. |
| **H3 — recorded-set completion is not complete channel migration** | **Reproduced.** `fetch_all` flags a full repeated timestamp page and steps past the second (`relay.rs:144–175`). `seal` propagates the warning but proceeds. With 1,001 messages at one second, 1,000 were sealed, verified and purged with zero remaining recorded work; one plaintext message remained. The CLI prints a warning but can exit successfully. Persist scan completeness, block a whole-channel completion claim when ambiguous, and support a deterministic secondary cursor or authoritative export. Re-scan for residual plaintext and explain deliberately excluded invalid originals. |
| **H4 — verify stops checking history once it is purged** | **Reproduced.** `engine.rs:360–374` excludes Purged entries. After a successful purge and removal of the sole envelope, verify checks zero, reports no failure and leaves the purged count intact. The state-module claim that its digest supports verification after purge is therefore not realised by this command. Add `verify --include-purged` or make full retained-history verification the default; test missing envelopes, missing keys and a zero-checked result. This is recoverability monitoring, not a guarantee of future remote retention. |
| **H5 — Rust and agentbox disagree on malformed sealed messages** | **Reproduced.** JavaScript `zone-keys.js:549–577` parses JSON before checking fields, so duplicate `content` properties collapse to one and a valid final signed event passes. Rust's strict deserialiser rejects duplicates. At `:595–600`, a sealed marker without zk returns Plain before the marker is validated; the Rust reader returns Failed. Actual encrypted-zone admission requires zk, limiting that second path; the reader still violates the ADR's universal no-fallback claim for imported/unscoped data. Use shared cross-language vectors for duplicate fields, missing zk, unsupported versions and all six checks, with identical outcomes. These cases do not forge the original signature. |
| **H6 — deletion does not guarantee its audit receipt** | **Source-confirmed.** `admin_events.rs:293–305` discards the result of `audit::log_admin_action`, after separately executed deletes. Thus success does not prove the promised audit row exists. Partial deletes can also precede an HTTP error. `audit.rs:38–54` propagates insertion errors, so this is a real caller decision, not an infallible logger. Make deletion and a durable receipt transactional where feasible, or expose an explicit audit-pending/error state with recovery. Inject a log-insert failure in a Worker/D1 integration test; this audit did not execute that runtime fault. |
| **H7 — migration preserves identity but not unlinkability or all links** | **Source-confirmed.** Public sealed tags contain the original ID, and outer time/zone/channel remain visible. A relay retaining pre-migration IDs can join them to old authors/text. Existing original-ID and reply-tag queries still miss the encrypted replacement. Provide a zone-authorised original-ID resolver and a documented retention/metadata statement; test permalinks, reactions, replies and suggestions from a fresh client after deletion. An observer with an old plaintext copy cannot be made to forget it. |

An additional planning distinction matters: `plan.rs:115–125` counts any parseable marker as “already sealed”, without opening or signature verification. The audit's forged-marker fixture inflated that count, but the subsequent seal step correctly rejected adoption and published a good replacement. Rename this count to “candidate envelopes found”, and report cryptographically verified preservation separately; this is misleading planning output, not a demonstrated unsafe purge path.

## Comparisons and user utility

NIP-09 asks relays to remove or stop publishing author-matching events and asks clients to honour deletion semantics; it explicitly cannot guarantee deletion from every relay/client. The forum's silent storage replacement serves a different user action: retain the conversation while changing its storage representation. Keep those actions distinct in operator tools, and show remaining plaintext locations. [NIP-09](https://raw.githubusercontent.com/nostr-protocol/nips/master/09.md), checked 2026-11-01.

MLS standardises asynchronous group key establishment with forward secrecy and post-compromise security. That does not itself supply a historical-board migration, erase old copies or repair original-ID links. The forum's utility is continuity of signed discussion history; its epoch-key history access should not be marketed as MLS-equivalent compromise recovery. [RFC 9420](https://www.rfc-editor.org/rfc/rfc9420.html), checked 2026-11-01.

Marmot's current README calls the protocol adopted, retains Nostr identity/event-shaped payloads and uses MLS for group key agreement. Its threat model separately treats receipt, retention, history completeness and retained-key exposure, while explicitly labelling itself a draft rather than an implementation audit. This is a relevant design comparison and a reason to revisit ADR-2016's older “still a draft” rationale; it is not evidence that Marmot is a drop-in board replacement or that a particular client is qualified. [Marmot protocol](https://raw.githubusercontent.com/marmot-protocol/marmot/master/README.md), [threat model](https://raw.githubusercontent.com/marmot-protocol/marmot/master/security-considerations.md), checked 2026-11-01.

For users, the next useful deliverable is a migration receipt that separates discovered, reader-verified, deleted, unresolved and externally retained history. It should retain scan limits and show fresh-client access tests, permalink continuity and post-purge recovery checks. Fix H1/H2 before treating a green migration result as sufficient to discard the last backup. This audit recommends those changes; it does not implement or deploy them.

## Fresh validation

All 103 native Rust tests, seven Rust documentation tests, 47 existing JavaScript tests and four JavaScript audit cases passed. Six native tests and the four JavaScript cases were added for this audit. The relay tests exercise pure decision/parser/response code; they do not execute the full Worker/D1 handler. Source-only findings retain that label.
