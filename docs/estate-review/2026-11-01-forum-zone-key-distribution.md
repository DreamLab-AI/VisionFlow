# Forum zone-key distribution, rotation and recovery

Zone posts are encrypted and keys distributed through signed gift wraps, but creating a new key does not establish that every writer has moved to it. Grant tracking also leaves gaps after partial delivery and across browser tabs. These are lifecycle problems around the cryptography: they affect removal guarantees, access to history and the meaning of the admin interface's success messages.

## Scope and evidence

This is a whole-document assessment of **ADR-2016** and the superseded proposal **ADR-2026**, against forum main `c39f41f104b114d6a3fa29013daaf6fa58b45080`. ADR-2028 is consulted for succession and branch status; its complete implementation/design review remains open. The repository README explicitly places its NIP-171 implementation on `feat/upgrade-phase-0-1`. A scoped search of the archived main checkout finds `ZONE_GROUPS_ENABLED` and `zone_epoch_keys` only in documentation. That establishes the main-branch boundary, not absence on the upgrade branch.

[Retained sources, probes and command logs](evidence/2026-11-01/nf-zone/README.md) bind these observations to source bytes. Four added native probes exercise real grant planning, grant-ledger, write encryption/decryption and relay shape-check functions. Account switching in a browser, IndexedDB transactions, full Worker admission and a live removal/rotation are not executed. No production key or grant is used. Source-only findings below are kept distinct from native reproductions.

## ADR-2016 section assessment

| Section / obligation | Current evidence and disposition |
| --- | --- |
| Metadata, accepted/complete/live and review triggers | The implementation exists. The close-out records historical deployment evidence; this audit does not independently verify the running revision. The first removal/rotation trigger remains material because current code does not enforce an authoritative current epoch (Z1). |
| Context: membership ACL is insufficient against relay/host/backup readers | Sound distinction. Core NIP-44 encrypts text, while relay membership controls access to events. A retained key and an obtained ciphertext are sufficient for decryption; membership revocation cannot erase either. |
| Gate: exact string true, default off and zone flag | Client `zone_crypto/mod.rs:91–112`, relay `zone_config.rs:82–100,135–140,194` and config `schema.rs:82–94` implement the described checks/default. Agreement of deployed environment values is an operational requirement, not established by identical parsers. |
| Public zones cannot be encrypted | Config `validate.rs:250–256` rejects encrypted public zones. Relay defence is specifically `!is_public_read`, where public read also requires no cohorts (`zone_config.rs:135–149`); its fallback is narrower than the ADR's categorical wording for malformed raw config. No normal config-validation bypass is demonstrated. |
| Keys: random secp256k1 pairs, increasing epochs, private grant kind, admin and secret/public-key checks | Generation and validation exist in `mod.rs:190,307`; wrap/seal verification exists at `:676`. Increasing epochs are chosen from local state in `admin/zone_encryption.rs:249`. There is no shared epoch reservation or conflict refusal in the main client (Z2). Grant authority is cached per page (`store.rs:313`), not rechecked for every grant. |
| Messages: kind-42 encryption, retained tags, zk and relay refusal | `apply_write_plan` encrypts via the signer and replaces zk while preserving other tags. Relay shape validation checks the zone, numeric epoch, hex key and payload shape; it neither decrypts nor checks the current epoch (Z1). |
| Client write, read, search and preview behaviour | Resolved encrypted zones with no key refuse writes. Missing channel/zone resolution instead passes plaintext through (Z7). `read_outcome` checks the selected key against zk and produces missing/failed outcomes. Channel publication tests the resulting zk tag before search ingestion (`pages/channel.rs:859–881`); encrypted IDs suppress previews. These guards depend on correctly classified encrypted traffic. |
| Gate off and BBS | Held keys still decrypt because reads do not consult the gate. Fresh grant sync does consult it (`app.rs:795–811`), so the history claim requires keys already held. The keyless BBS masks zk content and suppresses composition on gated encrypted boards (`bbs-client/src/relay.rs:69–98`, `screens.rs:906–918`). |
| Agents and agent_keys | `grant_targets` excludes the agent cohort unless enabled. The trade-off correctly says plaintext can reach the agent/model stack. The consequence saying no agent holds a key needs the same qualification; this is a targeting policy, not cryptographic prevention of a member forwarding a key. |
| Membership, history grants and per-device records | Fresh roster reads precede granting. Earlier keys are included by default for recipients selected as missing the newest key. Acknowledgement of the newest can hide a failed historical grant (Z3). The shared ledger repairs concurrent callbacks within one instance; two loaded instances can still lose records (Z4). A relay acknowledgement proves acceptance, not recipient possession. |
| Existing plaintext history | Delegated to ADR-2017; the separate sealed-history audit records migration/reader/purge gaps. Current key rotation alone does not encrypt old plaintext or remove old copies. |
| Protection table | Text confidentiality is conditional on encryption being applied and endpoint key custody. The post-removal claim needs writer convergence and a current-epoch rule (Z1). Metadata, reactions, previously held keys and unencrypted device storage are correctly excluded. Z6 further identifies the account boundary within that device storage. |
| Alternative MLS/NIP-EE/Marmot | The current Marmot repository labels the protocol adopted. Revisit the older draft rationale. Browser suitability, channel migration and the claimed fraction of risk need an implementation comparison and measurements; the ADR does not provide those. |
| Consequences: deployment, search/moderation, admin grant availability, automation, NIP-07 and follow-ons | Auto-grant uses a fresh whitelist, runs on allocation and once per page after hydration/admin/auth, and counts pending work for an extension signer. Once-per-page does not mean a later grant arrival triggers another sweep. A new device depends on surviving grants or another holder; mnemonic identity recovery alone does not derive random epoch keys. Z3/Z5 limit the success and completeness claims. |
| Verification and 2026-10-30 close-out | The historical native/WASM/fmt/clippy counts and deployment run are evidence from their stated revisions. Fresh targeted native results are recorded separately. Neither record supplies a full browser removal/rotation acceptance test. The close-out itself correctly leaves that unestablished. |

## Findings and acceptance criteria

| ID / priority | Trigger, evidence and consequence | Required acceptance evidence |
| --- | --- | --- |
| **Z1 — high: stale writers retain old-key access** | The client chooses its newest locally held key (`store.rs:359–364,455–465`). A native probe encrypts a new post with epoch 1 despite a separate epoch 2 existing, and the epoch-1 holder decrypts it. A separate real relay predicate probe accepts epoch 1 after checking epoch 2. Rotation UI promises too much (`admin/zone_encryption.rs:252–256`). This does **not** demonstrate that a removed member bypasses read ACLs; exposure requires obtaining ciphertext, as the ADR's relay/backup threat model allows. | Define authoritative epoch/key registration, reject stale ordinary writes and retain their drafts, then test a removed holder against an offline writer reconnecting after rotation. Historical sealed migration needs an explicit authorised exception. Show recipient grant acceptance separately from activation. |
| **Z2 — high: conflicting keys replace one another** | Two admins can compute the same next epoch from local state and generate distinct keys. Both are valid grants. `store.rs:106–121,279–296` replaces the map entry identified only by zone/epoch, and IndexedDB `put_zone_key` replaces the same record (`indexed_db.rs:334–343`). The reader then rejects ciphertext naming the displaced key. This is source-confirmed; no browser collision is executed. The grant ledger also omits key identity. | A two-admin/two-device test must preserve both recoverable key records, surface a conflict and resolve one authorised key before accepting new writes. Bind delivery records to the actual key fingerprint; refuse silent replacement. |
| **Z3 — medium: partial history delivery stops retrying** | The native fixture starts with epochs 2 and 1 owed. After newest-key ACKs are recorded while one epoch-1 grant remains absent, `plan_missing` returns no grants (`auto_grant.rs:92–108`). Calling the lower-level history planner explicitly still finds the old key. The admin UI's missing-recipient filter likewise uses the newest ledger. A newcomer can remain unable to read older discussion. | Plan missing work per recipient and epoch independently. Fail or reject one old grant while accepting the newest, then prove the next sweep and manual repair offer exactly the missing history. |
| **Z4 — medium: two tabs overwrite grant history** | The real `GrantLedger` probe preloads two instances from one KV, records different recipients sequentially and reopens the ledger: only the second recipient remains. The existing concurrent-record test still passes for one shared instance. Whole-set rewrites compare with local memory, without merging another tab's later snapshot (`grant_ledger.rs:60–110`). This reproduces the algorithm with an in-memory KV, not actual browser scheduling. | Use atomic merge or individual grant records with appropriate account/relay/key scope. Verify two real tabs and reload preserve the union, including failed transactions. This ledger is advisory; losing a row causes duplicate grants and misleading status, not key revocation. |
| **Z5 — medium: sent counts precede acceptance** | `send_grants` increments sent when `publish_with_ack` returns, while a false ACK is ignored (`auto_grant.rs:153–174`). That relay method queues/defer-sends and returns before any ACK (`relay.rs:640–657`). The UI then promises members will receive keys (`admin/zone_encryption.rs:234–239`), and rotation has already installed the new local key. Source-only: no disconnect/negative-ACK browser injection performed. The durable ledger correctly records only positive ACKs. | Present queued, accepted, rejected and unconfirmed separately, with timeout and retry. An offline or negative-ACK test must not report completed delivery. Per-recipient possession remains a separate optional receipt. |
| **Z6 — high on shared devices: key storage crosses account boundaries** | Database `members-forum` and zone/epoch keys lack account or relay scope (`indexed_db.rs:25,68–105`). Root hydration loads all stored zone keys before account-specific sync. Logout clears identity and notifications but not zone keys (`auth/mod.rs:676–705`). Sync captures one signer/member and is guarded by a page-lifetime boolean (`store.rs:217–245`); logout at the home route need not reload. Source confirms persistence and missing reset; UI exposure to a second account is not browser-tested. | Separate storage by account and relay; clear decrypted memory and dispose subscriptions/signers at logout. Test same-origin A→B switching both at home and after navigation, plus reload and offline cached messages. Provide an explicit shared-device removal policy. Scoping alone does not protect against malicious same-origin scripts or a compromised browser. |
| **Z7 — high, conditional: unresolved routing passes plaintext** | `prepare_outgoing` returns the original event when channel-to-zone resolution fails; `ZoneWriter::prepare` does the same without a channel store (`store.rs:458–459,497–502`). Relay rejection can prevent persistence but occurs after plaintext has reached the relay. Normal mapped encrypted paths refuse without keys, and no ordinary UI race is demonstrated here. | Treat unresolved routing as an error until encryption policy is known. Exercise unloaded/missing channel config and mismatched client/relay gates; assert no plaintext EVENT or search request leaves the browser and the draft survives. |

Two further source limits deserve tests alongside those fixes: admin-authority decisions remain cached for the page's lifetime, and an IndexedDB request success is treated as persistence without awaiting transaction completion. Neither is promoted here to a reproduced browser exploit or durability failure.

## ADR-2026 section assessment

| Section | Disposition |
| --- | --- |
| Metadata: superseded, no implementation, inactive, successor ADR-2028 | Preserve this status. It is historical design input, not an available recovery feature. Main's random keys remain the applicable implementation. |
| Context: lost admin devices, Anagram derivation and revision rationale | The availability problem is real for random keys without surviving grants/holders. The context describes a random revision, while the decision chooses the first unused bounded revision. Those are different concurrency properties. Anagram's exact draft/vector was not independently retrieved in this batch, so its attributed construction remains an ADR claim. |
| Decision: master creation and storage | Showing the master once and avoiding plaintext shared IndexedDB address custody, but require a tested backup/restore flow. Self-encryption still depends on recovering the corresponding account key. No implementation or recovery ceremony is established. |
| Decision: HKDF, domain separation, zone length and counter | The use of standard primitives is appropriate as a proposal. Exact byte encodings of lengths, integers and counter and the revision bound k must be specified before interoperability vectors can be meaningful. This audit implements no bespoke construction. |
| Decision: first unused revision, highest-seen epoch and recovery scan | Two devices reading the same relay history can select the same next epoch and same first-unused revision. A read/derive/check sequence is not an atomic reservation. Incomplete or stale history also weakens the highest-seen rule. Require authoritative ordering/conflict handling and tests for concurrent rotations and incomplete scans. |
| Decision: do not overwrite, legacy keys and dependencies | Conflict refusal is a proposed improvement over Z2. A master cannot reconstruct earlier randomly generated keys; export/backup is a separate requirement. Keeping project-specific code unpublished does not establish its security. |
| Consequences: future access, shared-master audiences, empty epochs and ADR-2016 amendment | Correctly identifies that a master holder retains future derivation power and that independent grants can defeat intended removals. Missing master replacement and no-message epoch recovery remain substantive design gaps. Any adoption needs both those policies and an amendment to random-per-epoch semantics. |
| Verification | Correctly says none. The three proposed vector/refusal/conflict tests are useful but insufficient alone: add deterministic encoding vectors, concurrent rotations, relay omission, empty epochs, legacy restoration and owner/master replacement. Supersession does not make these unresolved obligations disappear; assess their disposition in ADR-2028 separately. |

## Comparisons and user utility

NIP-44 explicitly lacks forward secrecy and post-compromise security. It supplies encrypted payloads, not membership convergence or recovery. The forum's retained epoch keys favour readable history; stronger removal claims need explicit epoch transitions around that primitive. [NIP-44](https://raw.githubusercontent.com/nostr-protocol/nips/master/44.md), checked 2026-11-01.

Marmot now describes an adopted protocol using Nostr identity and event-shaped payloads with MLS for continuous group key agreement, and requires redundant delivery. That makes it a relevant comparison for removal and transport resilience. It does not prove a browser implementation fits this forum or that signed board history migrates unchanged. The ADR's draft-only rationale should be refreshed through a bounded prototype comparing offline rejoin, removal, history access and recovery. [Marmot protocol](https://raw.githubusercontent.com/marmot-protocol/marmot/master/README.md), checked 2026-11-01.

A cohort-controlled discussion archive with selective agent access is a useful product position for this forum. Its next deliverable should make key operations understandable: show which epoch is active, who has an accepted grant, which historical epochs remain missing and whether recovery has been tested. Measure time from approval to first readable post, percentage of promised history readable after a partial grant failure, and successful fresh-device restores. Those outcomes matter more to a community administrator than a successful key-generation toast. Prioritise Z1/Z2/Z6/Z7 before claiming effective exclusion or shared-device isolation; Z3/Z4/Z5 make delivery failures visible and repairable.

## Fresh validation

All **127 native tests and three documentation tests passed**: 41 client zone-crypto cases (three added probes), 12 relay zone-config cases (one added probe), and 74 config tests plus three doc tests. Passing probes demonstrate the reported current behaviour; they do not remediate it or establish browser/Worker integration. All 22 retained source exports match the previous diagram revision `1b27f79`; 19 match website-consumed pin `9c36b60`. The three differences are ADR-2016 close-out metadata/text and two `SigningKey::from_bytes` argument conversions, one in a test. These are source comparisons, not fresh deployment verification.

## Diagram disposition and remaining work

New NF-27.1–5 records rotation, delivery, ledger concurrency, account custody and the superseded recovery proposal. Other NF-05 panels are not credited by this batch. ADR-2028 and its upgrade-branch implementation, real browser/Worker fault tests and live removal acceptance remain open. The estate goal remains active.
