# BBS signer: account lifetime and key custody

The BBS implements local signing and extension delegation, but its sign-out, backup and asynchronous actions do not share a complete account-lifetime boundary. A retained local signer still signs after logout; browser source also permits credentials to be re-adopted and extension results to be published without checking the intended account. This continuation reviews forum ADR-2008, adds six NF-19 panels and corrects custody and boot routing in NF-05.11. It does not close the wider forum or estate audit.

## Findings and acceptance work

**F1 — Sign-out is local handle removal, not account-session teardown.** [BBS logout](../../../nostr-rust-forum/crates/nostr-bbs-bbs-client/src/signer.rs:229) clears its stored signer, public key and error, then [relay clear_signer](../../../nostr-rust-forum/crates/nostr-bbs-bbs-client/src/relay.rs:464) clears only the relay’s signer reference. It does not close the socket, clear subscriptions/deferred writes, reset `AUTHED`, remove forum key/session storage, or erase the baked key. Boot calls adoption again. Thus a readable forum key can restore the account after reload; a PWA can also recover its baked key when its boot conditions hold. This reload behaviour is source-traced, not browser-reproduced. The separate [Forget this device](../../../nostr-rust-forum/crates/nostr-bbs-bbs-client/src/pwa.rs:247) attempts baked-record deletion, ignores deletion errors and clears the BootProfile; it does not remove forum raw-key storage. Acceptance: distinguish “leave this view”, “sign out of this origin” and “forget this device”, close/re-authenticate the socket when account authority changes, and report persistence cleanup failure. Test each action followed by reload and cross-tab activity.

**F2 — Captured signers outlive logout and replacement.** `get_signer` clones an `Rc`; clearing the store cannot revoke that clone. Two audit tests demonstrate valid old-account signatures after logout and after installing a different local key. The [composer](../../../nostr-rust-forum/crates/nostr-bbs-bbs-client/src/screens.rs:1385) awaits the captured signer and publishes its result without checking current account generation; [AUTH](../../../nostr-rust-forum/crates/nostr-bbs-bbs-client/src/relay.rs:543) similarly awaits a clone and sends through the current socket helper. Extension login also installs its result after an await without a cancellation token. These call paths support a delayed-action risk, but no delayed browser prompt or publication was executed. Acceptance: bind operations to an account generation and socket generation, invalidate both at logout/switch, and recheck before installation or sending. Retained native signing is not itself proof of relay acceptance.

**F3 — Extension identity and returned intent are trusted.** Adoption uses stored `publicKey` with provider presence, without asking the extension for its current account. The pure selector accepts a non-hex public key and an unknown session schema version; audit tests record both. A valid raw key also wins without any metadata. An invalid but non-empty localStorage secret prevents the reader from trying sessionStorage, though parsing can still fall through to extension adoption. [Nip07Signer](../../../nostr-rust-forum/crates/nostr-bbs-bbs-client/src/nip07.rs:108) never compares its stored public key with the unsigned author or returned event. The bridge resolves `window.nostr` afresh and only deserialises its result. A signature can therefore be valid yet belong to a different intended account, or contain changed fields; relay signature verification does not establish user intent. Acceptance: validate and refresh provider identity, compare every returned event’s author/kind/tags/content/time with the requested event, verify its signature, and fail with a visible account-change message. The native local signer correctly rejects a mismatched unsigned author; that control does not cover the browser backend.

**F4 — Backup can refer to a different account.** [local_secret_hex](../../../nostr-rust-forum/crates/nostr-bbs-bbs-client/src/signer.rs:291) checks only that some public key is installed, then returns forum storage without deriving/comparing its public key. The [backup panel](../../../nostr-rust-forum/crates/nostr-bbs-bbs-client/src/screens.rs:1972) presents that value beside the active account. If forum key A remains stored while B is installed through paste/generate/passkey/extension, backup can show A. With no forum key, a pasted in-memory key has no later backup route; generated keys do have their initial one-time sheet. Acceptance: tie export to the installed backend and displayed identity, verify the derived public key before rendering, and explain which recovery method applies. This mismatch is established by source composition, not an executed DOM scenario.

**F5 — Buffer cleanup is selective.** [parse_secret_key](../../../nostr-rust-forum/crates/nostr-bbs-bbs-client/src/signer.rs:350) overwrites its own intermediate hex string but leaves the decoded `Vec<u8>` on ordinary drop. The caller’s storage string and input/UI strings are separate allocations. Invalid-scalar return occurs before `arr.zeroize`; success scrubs that local array. Baked adoption explicitly scrubs its local copy on either parse outcome. Core `SecretKey` uses zeroisation on drop, delayed while any signer clone survives. Backup creates several ordinary string copies and may write the clipboard. Acceptance: use the existing zeroisation library for owned secret buffers on success and error paths, minimise copies, and describe browser/clipboard limits accurately. No heap extraction, release-code erasure analysis or claim of recoverable residual bytes was attempted.

**F6 — Client AUTH readiness means signed/sent, not accepted.** [handle_auth_challenge](../../../nostr-rust-forum/crates/nostr-bbs-bbs-client/src/relay.rs:543) sets `AUTHED=true`, replays subscriptions and flushes deferred writes immediately after producing a signed response. It does not await the relay’s matching positive OK. The OK handler only dispatches registered publication callbacks, while `CLOSED` is ignored. A rejection or wrong extension account can therefore leave the local readiness flag ahead of server authority. This does not bypass server checks. Acceptance: correlate AUTH’s event ID with its OK, set readiness only on acceptance, retain/retry or fail queued actions explicitly, and reset readiness on sign-out/account change. Test rejection and delayed OK against a real local relay.

Lower-priority invalid-login tests show that rejected pasted/baked input leaves the old installed account intact. That may be a reasonable failed-switch policy; the UI and API should state it rather than imply every failed login leaves the client signed out.

## External comparison and user utility

[NIP-07](https://github.com/nostr-protocol/nips/blob/master/07.md) defines separate public-key lookup and event-signing methods, with distinct optional NIP-04 and NIP-44 methods. It does not guarantee an approval prompt for every operation. The BBS comments promise prompts more strongly than that contract; its NIP-04 methods also unconditionally call NIP-44. No current NIP-04 caller was traced in this bounded review, so that mismatch is an adapter-contract concern rather than a demonstrated messaging failure.

[Alby’s extension](https://github.com/getAlby/lightning-browser-extension) provides an existing Nostr signer and documents Chromium/Firefox support. It is a relevant integration comparator, not proof of a tested BBS pairing. [NIP-46](https://github.com/nostr-protocol/nips/blob/master/46.md) separates client transport keys, remote-signer keys and the user identity, explicitly requiring discovery of the user public key after connection. That provides a standard route for remote custody; it still needs BBS lifecycle and intent validation. [NIP-42](https://github.com/nostr-protocol/nips/blob/master/42.md) requires AUTH responses to receive OK and scopes authenticated sessions to their connection, supporting the need to distinguish signing from accepted authentication.

A useful product goal is a consistent community identity across the forum, retro client and governance actions. Prioritise reliable sign-out, account-labelled backup and cancellation before adding another signer backend. A user should be able to switch from A to B while an approval is pending, see the stale action cancelled, and obtain a backup or recovery explanation that names B. This is a proposed acceptance journey and market-position inference, not evidence of adoption or competitive superiority. Sources were read on 1 November 2026; one obsolete Alby product URL returned 404 and was replaced by its primary repository.
