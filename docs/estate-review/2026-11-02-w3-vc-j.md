# VisionClaw voice loop and Godot XR client

I assessed all 39 panels of `visionclaw/35-voice-end-to-end.md` (12) and `visionclaw/36-godot-xr-client.md` (27) by source tracing at VisionClaw `86cdd7635582`, and restamped both topics. Totals: 10 accurate, 24 corrected, 5 accurate with limits, 0 inaccurate-unfixed. Topic 35 moved from `8692b12` and topic 36 from `e4ba5eb`, which predates the spatial-volume merge. The most important finding is in the voice loop. The `/ws/speech` socket's ADR-2075 gate covers inbound text commands only. Binary audio, the outbound TTS stream and the outbound transcript broadcast are not gated. So an unauthenticated peer, in its first 30 seconds, can push audio into Whisper and receive every utterance. Its transcript then reaches two ungoverned consumers: a keyword-matched swarm executor and the settings assistant. The default push-to-talk flow misroutes too. The speaker's own utterance arrives after key-up and is never dispatched on the governed path. What is signed and dispatched for the bound agent DID is whatever final transcript arrives while Space is held: the server's "Whisper STT ready" status string, or another socket's speech.

## Findings

**F1. Unauthenticated audio in, broadcast audio and transcripts out (Tension, VC-35.4, VC-35.6, VC-35.10).**
- **Trigger:** a peer opens `/ws/speech` and sends nothing, or sends binary frames.
- **Consequence:** `started()` subscribes the socket to the SpeechService audio and transcription broadcasts before any `authenticate` frame (`src/handlers/speech_socket_handler.rs:511-541`). The forwarders write without a pubkey check (`:556-558`, `:571-583`), so the peer hears every TTS chunk and reads every transcript until `AUTH_DEADLINE` closes it (`:22`, `:486-500`). The Binary arm has no gate either (`:956-976`). The peer's audio is transcribed and broadcast to every socket, and it is consumed by `VoiceInterfaceActor` (`src/actors/voice_interface_actor.rs:136-140`, `:151-176`) and `ElevationActor` (`src/actors/elevation_actor.rs:1122-1125`, `:1141-1197`).
- **Close by:** subscribing only after `authenticate_success`, and refusing Binary frames while `pubkey` is `None`.

**F2. A Whisper transcript can run swarm commands with no governance (Tension, VC-35.6).**
- **Trigger:** a transcript contains any of 20 keywords, including "agent", "node", "graph" and "run" (`src/services/speech_service.rs:1032-1060`).
- **Consequence:** the transcript is parsed and executed through `execute_voice_command_with_context` (`:620-633`, `:1062`). That function can call swarm init and agent spawn on `MCP_HOST` (`:1066-1068`, `:1079`, `:1086`). There is no actor DID, no clarification gate and no signature. Whether `MCP_HOST` answers is deployment state I did not check.
- **Close by:** removing this server-side branch, or routing it through the VC-35.7 governed path.

**F3. Push-to-talk dispatches the wrong transcripts, and the server binding is write-only (Tension and Debt, VC-35.2).**
- **Trigger:** with an agent selected, the operator holds Space, speaks and releases.
- **Consequence:** `shouldDispatchGoverned` requires `state === 'commanding'`, and it is checked on every final transcript event (`client/src/features/voice/pttAgentBinding.ts:61-64`, `client/src/features/voice/usePushToTalkAgentBinding.ts:73-85`, fed by `client/src/hooks/useVoiceInteraction.ts:62-66`, `:84`). The same key-up that stops recording (`client/src/components/VoiceButton.tsx:115-120`) moves PTT to `chatting` or `idle` (`client/src/services/PushToTalkService.ts:212`, `:217`). The audio is sent only on stop (`client/src/services/VoiceWebSocketService.ts:399-411`), so the speaker's own utterance always arrives too late to be governed. Final transcripts that arrive while Space is held are signed and dispatched for the bound DID instead. Those are the "Whisper STT ready" status the server broadcasts in answer to `stt start` (`src/services/speech_service.rs:429`, `src/handlers/speech_socket_handler.rs:571-583`), and any other socket's transcript on the global broadcast. Separately, the server's session binding has no production reader: `selected_agent_did` is called only from tests (`src/services/audio_router.rs:238`). A client unbind sends `actorDid: null`, which the server reads as "keep the old binding" (`:198-201`).
- **Close by:** binding the governed decision to the recording, for example a "bound at release" flag carried with that utterance. Then stop the status strings and other sockets' transcripts from reaching `handleTranscription`, and either read or delete the server binding.

**F4. VC-35 corrections (each closed by this restamp).**
- **Whisper endpoint:** Whisper is a multipart `POST {api_url}/transcription/` followed by polling `/task/{id}` (`src/services/speech_service.rs:492-495`, `:570-591`). The topic said `/v1/audio/transcriptions`.
- **No AudioRouter on the audio path:** TTS audio and transcripts travel on SpeechService's own global broadcasts (`:41`, `:43`, `:366`, `:617`). `AudioRouter`'s `route_transcription`, `route_agent_audio`, `subscribe_user_audio` and `update_agent_position` have no production callers.
- **PocketTts body:** the body hard-codes `speed 1.0` and `stream true`, so `SpeechOptions` speed, stream and format never reach pocket-tts (`:325-326`, `:355`).
- **Constructor:** `SpeechSocket::new` takes no `None` argument (`src/handlers/speech_socket_handler.rs:103-108`).
- **VoicePreamble:** `VoicePreamble::generate` has no production caller (`src/actors/voice_commands.rs:90-108`, with only test callers at `:264` and `:272`).
- **LiveKitVoiceService:** it has no call site, and it builds its own `AudioContext` (`client/src/services/LiveKitVoiceService.ts:150-158`).
- **ElevationActor:** it parses an explicit elevation intent first and opens an ACSP case. It reads the ledger on the cycle, not per transcript (`src/actors/elevation_actor.rs:1145-1203`, `:1214`, `:1235-1237`).
- **Shared TTS task:** there is one `tts_task`, so any authenticated socket's `cancel_tts` cuts every listener (`src/services/speech_service.rs:264-268`, `:287-291`).

**F5. VC-36 corrections (each closed by this restamp).**
- **Connections:** the client now holds one `BackendConnection` per source, each with its own `BinaryProtocolClient`, backoff and generation (`xr-client/scripts/graph_scene.gd:1371-1381`, `xr-client/scripts/backend_connection.gd:83-84`, `:318-356`).
- **Packing:** nodes and edges pack per volume through `ConnectionVolumeSource.pack` (`xr-client/scripts/connection_volume_source.gd:138-162`). The scene's own MultiMeshes are empty templates (`graph_scene.gd:1419-1424`). The stride-16 invariant now lives in `connection_volume_source.gd:31-32` and `xr-client/scripts/node_lod.gd:65-75`.
- **Beams:** a beam starts at the embodiment anchor only. The fallback to a streamed node position that VC-36.7 and VC-36.24 asserted is gone (`xr-client/rust/src/render_store.rs:2125-2129`, `:2152-2154`).
- **Choreography:** the Complete and Park phases, `ALPHA_PARKED` and the `park` event are replaced by a 30 s edge run and a rest phase (`xr-client/scripts/agent_choreography.gd:30-35`, `:282-323`, `:342-358`).

**F6. Layout-mode list drift (Drift, VC-36.12).**
- **Consequence:** the server's advertised `LIVE_LAYOUT_MODES` is forceDirected, hierarchical, radial, dagLeftRight, typeClustering, spectral, temporal (`src/handlers/layout_handler.rs:23-31`). The headset cycles a different six-mode list (`xr-client/scripts/graph_scene.gd:952`). `clustered` is accepted but not advertised (`layout_handler.rs:20-22`, `:64-71`). The headset cannot reach dagLeftRight or typeClustering.
- **Close by:** having the headset read `GET /api/layout/mode`, or aligning the two lists.

**F7. Label fade steps per volume (Tension, VC-36.19).**
- **Consequence:** fade state lives on the client (`render_store.rs:1354-1372`), and the knowledge and ontology volumes share the VisionClaw client (`graph_scene.gd:93-96`). Each pack steps every fade (`render_store_pack.rs:255`, `:126`), so with both volumes visible a fade advances twice per frame. The rate on a headset is unmeasured.
- **Close by:** stepping fades once per frame per client (or per pack slot), and confirming the ramp on a headset.

**F8. Smaller drift recorded in place.**
- **BASELINE token bullet:** `docs/BASELINE-architecture.md:320` still lists `?token=` on `/wss` as open after ADR-2058. The old citation for this resolved into `graph_scene.gd` by mistake (the generator flagged it).
- **Pin comment:** the `BackendConnection` comment on kept pins contradicts ADR-2172 F3 (`backend_connection.gd:353-354` against `:273-275`).
- **process_voice_intent doc comment:** it still promises a settings-assistant fallback that the caller refuses (`speech_socket_handler.rs:305-307` against `:850-858`).
- **Old line refs in VC-36.13 and VC-35.11:** the `HandRay:24`-style refs were wrong and invisible to the generator. They now cite real lines, so this item is closed.
- **Close by:** updating the BASELINE bullet, the `BackendConnection` comment and the `process_voice_intent` doc comment to match the code. All three are product-doc edits outside this audit.
