# Dream adapter controls, scheduling and egress audit

Selecting Loom does not make this adapter LAN-only: a present Z.AI credential enables a cloud fallback, and the verdict path sends that fallback the same prompt after primary failure. Separately, changing evaluator readiness can overwrite a completed night's report and append a HANDOFF row while leaving its terminal run state intact. Both contradict stronger claims in the documentation.

This pass assesses ADR-2053 section by section and updates four AB-23 panels for scheduling, operator controls, provider fallback and placeholder handling. Fourteen other AB-23 panels remain queued. All nine local dream-engine ADRs retain their earlier assessments with open findings; this pass does not close the wider agentbox decisions, nested diagram corpus or live acceptance work. [Migration/provenance](2026-11-01-dream-migration-and-provenance.md) and [recovery/source supply](2026-11-01-dream-recovery-and-source-supply.md) provide the preceding scope.

Current manifest lines are used in this report; the older AB-23 manifest citations elsewhere remain queued.

[Three tests pass](evidence/2026-11-01/dream-controls-probes.log). One [configuration/transport probe](evidence/2026-11-01/dream-controls-probe.rs) checks provider selection, unresolved placeholders, invalid runtime values, empty-host dispatch, Rust/JavaScript discovery disagreement and roster degradation. Two [night probes](evidence/2026-11-01/dream-controls-night-probe.rs) extend the pinned night fixture to check pause/standby bypass and changed readiness after completion. These are observations of current behaviour, not regression assertions that the behaviour is desirable.

Execution uses clean exports, local temporary repositories, scripted models, a recording forge and SSH/SCP substitutions that refuse non-fixture hosts. Night-level journal delivery, sweep, digest, governance, source reading and forum suggestions are disabled. Memory endpoints are empty and fail before network/database use. The provider probe uses a synthetic key and constructs configurations only; no cloud request or live credential is inspected. No daemon, supervisor, real remote annexe, forum or production night is changed. The eleven existing host tests passed in the preceding pass and were filtered out here.

The isolated probe confirms both branches. `engine.rs:1326-1364` passes the same prompt to fallback after any primary verdict error. `Provider::parse` at `llm.rs:35` also maps unknown names to Zai. The retained Z.AI default is an explicit operator choice, not the defect. |
| AB-C2 / high: admission can damage completed-night evidence | `engine.rs:576-602` assesses and persists admission failure before `finished_night` at 641. `records.rs:298-335` writes `report.md`, admission evidence and a ledger row. There is no second model or forge call. | Check terminal identity before any admission/prompt side effect; preserve the original report and return the stored result, or require an explicit reset. Test changed config, missing evaluators and damaged config after completion. Preserve consistent report, ledger and run-state identity. This supplements, rather than invalidates, the earlier unchanged-config recovery test. |

A paused roster returns None, while a targeted dry-run still compiles a prompt with manual standby set. Source shows the same routing for real targeted runs. | Specify whether pause prevents new targeted work, interrupts a running night or only suspends roster scheduling. ## Comparison and user utility

[Kubernetes CronJob documentation](https://kubernetes.io/docs/concepts/workloads/controllers/cron-jobs/) makes concurrency policy, missed-start deadlines and time zones explicit, and warns that scheduled jobs should be idempotent. These are useful contract examples for this adapter's process-local date marker and terminal evidence rules. They are not a recommendation to introduce Kubernetes or proof that a CronJob would fix report mutation.

[LiteLLM's fallback documentation](https://docs.litellm.ai/docs/proxy/reliability) describes configured model-group fallback chains after retries and provides ways to test failure routing. The relevant comparison is explicit, testable routing; neither a fallback chain nor a provider name inherently establishes data locality. This audit did not deploy or benchmark either project.

For an operator, useful progress would be one status view showing effective window, next selection, pause scope, primary/fallback destinations, unfinished nights and last durable roster update. A completed night should retain one consistent evidence identity. Measure recovery without lost reports, agreement between status and runnable nominations, and unplanned destination changes under provider failure. These are audit recommendations inferred from the observed gaps, not claims of market superiority.
