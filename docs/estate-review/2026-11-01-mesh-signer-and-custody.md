# Mesh signer, peer configuration and recovery boundaries

Agentbox's proposed federation signer needs more than a new socket and a kind allowlist. Current configuration cannot be deserialised directly by its chosen mesh library; that library rejects all three proposed control types. UID authorisation does not identify a particular program, and the existing backup selector does not include ordinary role-key filenames. These are implementation and design prerequisites, not evidence of an exposed live federation service.

This pass reads **ADR-2162 in full**, including its planned evolution, activation prerequisites and consequences. It traces the referenced key-separation clauses of ADR-2101, the kind-map contract of ADR-2061 and the consuming ADR-2161; it does not claim a new complete review of those predecessor records. Agentbox is pinned at `9dfc27b16e82e9786535a55e790710493dd51fdf`, forum at `c39f41f104b114d6a3fa29013daaf6fa58b45080`, and VisionClaw at `75b72416bac176ca8fde715cac3bd7c77657b3e7`. All 34 files in the [source receipt](evidence/2026-11-01/mesh-source-receipt.json) match those revisions. Source checkouts and the proposed/none/inactive status remain unchanged.

## Configuration and wire compatibility

Agentbox's JSON schema permits only `standalone` and `client`, forbids additional mesh properties, and has no `peers` property (`schema/agentbox.toml.schema.json:2578-2588`). These are [schema observations](evidence/2026-11-01/mesh-schema-observations.json), not execution of its validator. Its manifest already documents the missing `federated` mode. Forum's `MeshConfig` has a different moderation type and accepts unknown fields; `resolve` checks the presence of relay entries, not their scheme (`config.rs:52-83,145-166`). The desired configuration needs one versioned interpretation across the schema, sole semantic reader, projection, validation and reload behaviour.

No mesh service, peer projection writer, node-key role or proposed control handler was found in the searched agentbox runtime paths. [Search evidence](evidence/2026-11-01/mesh-runtime-search.txt) gives the scope; generic manifest loading and TUI preservation are not peer consumption. `PeerManager` builds sessions from relay URLs and applies kind/pubkey/ID filters; it has no durable inbox (`transport.rs:634-680`). The previous [forum audit](2026-11-01-forum-spaces-and-replication.md) separately traced the absent concrete `PeerConnector`.

D1's reuse requirement should name the required upstream version and codec extension. D3 must define duplicate-key and conflicting-endpoint refusal, canonical hex, URL normalisation, allowed origins, credential/query/fragment treatment, atomic projection replacement, ownership and stale-projection behaviour. Exact endpoint equality must have a shared representation at signing and consumption; the normalisation decision belongs before comparison. Missing or invalid pins must stop federation, with local operation clearly distinguished from a successful connection.

## Signing authority and recovery

Current identity-port permission is `uid → operation → key → kind` (`port.rs:361-379,528-566`); tags and content pass through for `sign_event`. D4 needs a typed catalogue operation that checks the unique `d` value, space authority, revision, active/withdrawn form, endpoint policy and bounded content before signing. Reject repeated or conflicting tags and foreign-owned URNs. Define which component allocates revisions and sequences, and durably reserves them before release. A compromised authorised VisionClaw remains able to request permitted catalogue changes; payload validation constrains the damage but does not prove the truth of the graph it publishes.

UID alone can isolate VisionClaw only with an exclusive effective identity and socket access boundary. VisionClaw's production Dockerfiles select appuser uid 1000; agentbox's ACL grants devuser uid 1000. These file facts do not establish a deployed socket mount or shared user namespace. Before activation, specify actual mappings, a dedicated client account or equivalent workload isolation, parent ownership/modes, mount placement and a negative test from a co-resident agent. The library's 0770 acceptance matters only where an untrusted process belongs to that directory group. Current default socket placement under `/run/secrets` and role provisioning must be assessed together, not inferred from the bind helper alone.

“Signs only two payload classes” is an application policy, not a list of two wire event kinds. NIP-59 authenticates the author through a kind-13 seal; its outer kind-1059 gift wrap uses a one-time key. Forum's sender path performs that wrapping with the sender secret (`transport.rs:420-434`; `gift_wrap.rs:294-327`). The receiver must compare the authenticated seal author to the pinned node, not the outer event author. Keep encryption/decryption inside the mesh custody boundary and expose typed control requests; a general seal/sign/decrypt oracle would defeat the intended restriction. These layer distinctions come from [NIP-59 at the pinned revision](https://github.com/nostr-protocol/nips/blob/400d157c53264b8e58c7b3cdbd21ef546fb7a157/59.md).

Backup selection is a fixed basename allowlist, skips unreadable subtrees and follows no directory symlinks (`secret-backup/src/main.rs:58-67,154-187`). ADR-2162 specifies neither persistent source nor selected filename for its independent seed. Define explicit inclusion and failure on a missing expected key, then rehearse encrypted off-host recovery under the mesh role. Do not solve omission by putting it in broadly sourced `identity.env`. Restoring a key alone also restores its authority without restoring its revision history: include sender counters, accepted watermarks, inbox/outbox state, active catalogue inventory, tombstones and instance fencing. Prevent two restored copies signing concurrently.

Backup README text overstates current manifest verification: it promises sizes and SHA-256 digests, but source writes an optional names-only sidecar and `restore` accepts no manifest (`main.rs:264-278,309-374`). Its displayed `--into` and positional `<paths…>` examples also differ from the actual `--dest` and `--root` fields (`main.rs:103-133`). Age authenticates the encrypted archive; that does not establish selection completeness or the claimed per-member manifest check. Existing synthetic encryption/restore tests pass. This source-only documentation finding is separate from a cryptographic defect.

## Delivery, erasure and rotation

D7 requires durable acceptance and sequence ordering but leaves the delivery transaction unspecified. A literal greater-than-watermark rule can receive sequence 12 before a retraction at 11, advance to 12 and permanently drop 11. Sorting already accepted messages cannot recover the dropped event. This is a design counterexample, not a reproduced production failure. Define whether sequence numbers are global or per recipient, how gaps are recovered, and how catalogue-fetch failure affects the watermark. Global counters also have legitimate gaps when messages target different peers.

Persist the inbox event and watermark atomically; keep delivery acknowledgement separate so a crash after acceptance but before VisionClaw applies it causes redelivery. Consumers need idempotent application. Test duplicate wraps carrying the same logical command, concurrent arrivals, missing catalogue, invalid high-sequence input, disk-full, restart, backup rollback and a crash on each side of the commit/ack boundary. The current identity-port receipt writer appends bytes without `sync_all`; it is an audit-log pattern, not evidence of a crash-durable protocol journal (`receipts.rs:124-140`).

Orderly rotation assumes the old key can still retract every named URN. Lost or compromised keys need a separate revocation/recovery procedure: peers can remove a pin, but must also purge or quarantine already accepted state. Specify stale-key refusal, old-state retention and retraction acknowledgement before retirement. The seven-day foreign-reference lease in VisionClaw's proposal is a consumer rule, not a way to erase information already copied by an uncooperative operator. Cross-operator peering therefore adds policy enforcement and threat-model work; “one added policy column” is a data-model sketch, not the complete migration.

## Comparison and user utility

SPIRE's Unix workload attestor exposes UID/GID selectors and, when enabled, executable path and hash selectors; failed path discovery then fails attestation. This is a useful identity-granularity comparison, not a recommendation to install SPIRE or a claim that a path check alone solves same-uid compromise. VisionFlow should demonstrate which workload can sign from the actual deployment, rather than display a generic “secure signer” badge. [SPIRE Unix attestor documentation](https://github.com/spiffe/spire/blob/main/doc/plugin_agent_workloadattestor_unix.md).

NATS JetStream documents durable consumer positions, acknowledgements and redelivery after a reader fails. The relevant comparison is operational: operators can distinguish accepted data from acknowledged processing. VisionFlow's control plane needs comparable observable states for accepted, awaiting catalogue, delivered, applied, retracted and expired. Durable delivery still requires idempotent side effects; this review did not run or benchmark NATS. [JetStream delivery and acknowledgement](https://docs.nats.io/learn/jetstream/delivery-and-acknowledgment).

A useful first pilot is two nodes owned by one operator, with public/DID spaces, a read-only peer view and one deliberate removal/restart/restore exercise. Measure time to configure correct pins, failed-connection explanations, catalogue age, sequence gaps, delivery lag, removal visibility and recovery without resurrected links. Membership and voice remain dependent on their separately audited prerequisites. Until this path works, position federation as a proposed extension to the spatial knowledge system, not an available cross-organisation workspace.
