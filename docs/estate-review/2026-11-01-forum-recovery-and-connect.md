# Recovery sheets, phone onboarding and local key import

The recovery flow has useful pieces: locally generated keys, printable recovery material and a direct route into the forum on a phone. Its security and completion claims exceed the implementation. Downloaded HTML interpolates an unescaped display name beside the secret; history clearing can fail without stopping import; and the backup gate records an attempt and a latched acknowledgement. The primary phone QR still carries the master key, including when the separate device-card feature is enabled.

This continuation assesses every section of archived ADR-095, ADR-098 and ADR-099. It corrects NF-05.8 and adds five NF-22 panels. The archived decisions remain unchanged; operative device-key ADR-2004 was assessed in the [device review](2026-11-01-forum-device-keys.md). Findings here require implementation work; this documentation change does not repair the product.

## Evidence and execution boundaries

The [manifest](evidence/2026-11-01/nf-onboarding/source-manifest.json) retains fourteen exact forum files at `c39f41f104b114d6a3fa29013daaf6fa58b45080`. All fourteen equal NF-05's historical source revision `1b27f79`. Twelve equal the website-consumed `9c36b6032640c89879ae52fe25da99493979a0b6`; differences in `auth/mod.rs` and auth-worker `devices.rs` are k256 argument conversions, retained in [source differences](evidence/2026-11-01/nf-onboarding/source-differences.json). Website HEAD was `b5eb1ec`; no deployment identity was established.

Nineteen native cases pass: five unchanged decoder tests, thirteen new behavioural probes and one HTML-fixture generation case. Nine source slices retain the original formatter, parser, validation prefix, connect effect, print callback and readiness effect; browser, reactive state and navigation are mocked. The actual core scalar constructor runs, but the full AuthStore, Leptos runtime, persistence and relay do not. Five real Chrome cases then exercise the generated HTML and History API in an isolated context. They use synthetic strings, no real account or secret, and only an inert marker assignment. The [test-kit README](evidence/2026-11-01/nf-onboarding/README.md) records reproduction and limitations.

An initial probe expected uppercase nsec decoding to succeed in the helper but fail in its caller. It failed: both reject uppercase input. The failed log is retained and the final rejection control passes. This is counterevidence, not an uppercase-input vulnerability.

| Decision: live-origin QR | The component formats `origin + base_href('/connect') + '#k=' + nsec`. This is the master credential, not a one-use invitation. Origin is read without a scheme check. |
| Decision: route and optional power path | `/connect` is public in `app.rs:926`; it invokes local-key login and schedules navigation. The sheet retains the bare nsec path. No successful relay admission is awaited by this route. |
| Hard invariant 1: fragment only | Generated URLs use a fragment; the browser HTTP receipt omits it. This property says nothing about page-script, extension, copied-link or pre-mount exposure. The parser does not read query parameters, but no general scrubber for mistakenly supplied query secrets was established. |
| Hard invariant 2: strip before import | Calls occur read→strip→import without an intervening await, but strip returns no result and discards browser errors. Import proceeds on failure. Mount-time clearing also cannot erase exposure before the effect runs. |
| Hard invariant 3: HTTPS | Neither this component nor the route enforces HTTPS. A deployment may enforce it separately; that configuration and its effective response were not verified here. |
| Hard invariant 4: strict validation | The actual validation prefix rejects malformed encodings, wrong lengths and invalid scalars before state mutation. Valid hex/nsec derive the same key. Bare fragments and surrounding whitespace are accepted; percent encoding is not decoded. Uppercase nsec is rejected by both layers. |
| Bearer risk and mitigations | The warning is present, but success means local import. The 1.5-second redirect does not prove that the user read it. A URL adds handling surfaces to a bare secret; fragment exclusion and best-effort clearing cannot prove identical exposure or absence of persistence. |
| Why this beats third-party clients | Treat this as a product hypothesis: a short path into the full forum. No usability comparison, camera test or native-client feature audit establishes superiority. Measure correct account selection and successful forum actions. |
| Consequences: route and History API | The public route and browser call are implemented. Source order is not successful history clearing. |
| Consequences: fourth QR and storage | The primary link is exported. “No new storage” can mean reuse of an existing mechanism, but imported hex is still written according to the existing remember-me preference; successful persistence is not checked. Screen and HTML layouts differ. |
| Alternatives | Query-string secrets remain unsuitable. NIP-49 is deferred, not implemented protection. A separate enrolment protocol or remote signer would change the custody contract and needs an explicit decision and acceptance journey. |

## Findings and acceptance work

**F1 — Downloaded recovery HTML executes unescaped display-name content.** [Signup validation](../../../nostr-rust-forum/crates/nostr-bbs-forum-client/src/pages/signup.rs:241) checks trimmed byte length, while the sheet receives the original signal. The [HTML formatter](../../../nostr-rust-forum/crates/nostr-bbs-forum-client/src/components/recovery_sheet.rs:138) interpolates the name into title/body without HTML escaping. A 30-character `<svg onload=window.auditXss=1>` name fits the validation boundary. Chrome executes the marker in generated HTML containing `SYNTHETIC-RECOVERY-KEY`; an escaped test-only control displays the literal name and does not execute. This proves active-content injection in an exported secret-bearing document, not remote attacker delivery, real-secret theft or WASM memory escape. Escape every text/attribute interpolation for its context, constrain any trusted SVG insertion, and consider an inert export. Acceptance must test the actual download/open flow with adversarial names and synthetic credentials.

**F2 — History clearing fails open.** [The strip helper](../../../nostr-rust-forum/crates/nostr-bbs-forum-client/src/pages/connect.rs:75) ignores `history()` and `replaceState` failures; the effect continues to login. Exact-body native probes retain the fragment and still reach success under a controlled replace failure, or import when history is unavailable. A separate Chrome case deliberately supplies a cross-origin replacement URL: the browser throws `SecurityError` and keeps the fragment. That case proves API semantics, not that production `base_href` is cross-origin or how often clearing fails. Require a successful clear before importing if the strict invariant is retained; otherwise explicitly revise the contract and provide a recovery action. Also define how early the bootstrap removes a secret, because the current effect runs after mounting. [MDN documents the origin requirement and failure cases](https://developer.mozilla.org/en-US/docs/Web/API/History/replaceState).

**F3 — Backup readiness is attempted output plus a latched acknowledgement.** [The print callback](../../../nostr-rust-forum/crates/nostr-bbs-forum-client/src/components/recovery_sheet.rs:338) sets `printed=true` even when printing fails or no window exists. Download also sets it after a void helper with early-return failure paths. The [effect](../../../nostr-rust-forum/crates/nostr-bbs-forum-client/src/components/recovery_sheet.rs:303) emits only a positive callback; [signup](../../../nostr-rust-forum/crates/nostr-bbs-forum-client/src/pages/signup.rs:647) never clears `sheet_ready` when confirmation is unticked. Both failure and latch behaviours are reproduced with extracted callbacks. Printing itself returns no saved-copy acknowledgement ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Window/print)). Keep the deliberate advanced override, make readiness track current acknowledgement, report detectable output failures, and offer a restore check rather than claiming a click proves a backup.

**F4 — Full recovery and phone enrolment are mixed, and the exports diverge.** The [primary connect URL](../../../nostr-rust-forum/crates/nostr-bbs-forum-client/src/components/recovery_sheet.rs:288) always uses the master nsec. The separate device generation result updates screen signals only after server registration succeeds. `RecoveryDownload` has no device or sweep fields; its HTML retains the master link and omits both optional sections. A formatter probe confirms that omission. The current registration failure means this is not proof of a successful production device-card journey. Give full account backup and revocable phone access distinct artefacts and labels, make print/download scope explicit, and test a lost-phone scenario without copying the master to the phone.

**F5 — Connect success is local state, with cross-account metadata and persistence limits.** [Local login](../../../nostr-rust-forum/crates/nostr-bbs-forum-client/src/auth/mod.rs:438) validates first, installs the signer, saves hex, marks authentication and then starts profile hydration. It does not await relay admission. `read_existing_metadata` reuses stored nickname/avatar/status without matching the stored public key to the new key; this is source evidence for carrying old metadata into a newly imported identity, not an executed full-store account-switch test. Storage writes ignore failures and use the prior remember-me preference. The route imports automatically with no account-switch confirmation. Show the public identity before replacement, bind metadata to that identity, distinguish local import from relay access, and surface persistence choice and failure. Acceptance must switch between two synthetic accounts, reject relay access and deny browser storage without displaying a misleading successful recovery.

**F6 — The promised relay-added owner tag is absent from the inspected event path.** [Policy resolution](../../../nostr-rust-forum/crates/nostr-bbs-relay-worker/src/relay_do/nip_handlers.rs:1121) changes the effective principal, while the handler passes the same immutable event to save/broadcast at lines 1542–1554. [Storage](../../../nostr-rust-forum/crates/nostr-bbs-relay-worker/src/relay_do/storage.rs:66) serialises the original tags and stores the original author and signature. This source trace contradicts an appended owner tag on that path; it does not inspect every possible UI profile projection. Preserve signed event bytes. If owner presentation is required, specify a separately authenticated attribution record or projection, its revocation semantics and the visible raw author.

## Comparable approaches and user utility

Sources below were checked on 1 November 2026. These are design comparisons, not a competitive benchmark.

| Reference | Relevant boundary | Implication for the forum |
| --- | --- | --- |
| [Signal linked devices](https://support.signal.org/hc/en-us/articles/360007320551-Linked-Devices) | Its documented workflow scans the new device's QR from the primary device after local unlock; linked devices are visible and can be unlinked. | A user can understand enrolment as granting a named device access. Adopt that clarity and an explicit confirmation step; Signal is a usability comparator, not a Nostr-compatible implementation. |
| [NIP-46](https://github.com/nostr-protocol/nips/blob/master/46.md) | Separates client communication keys from the user's signing identity controlled by a remote signer. It defines pairing and session behaviour. | This offers a different custody trade-off: less root-key replication, but signer availability and session policy become dependencies. Do not label raw nsec import as equivalent pairing. |
| Current forum approach | A URL opens the full forum and imports a bearer key; the device registry adds local owner-policy interpretation. | Its plausible advantage is direct access to forum-specific governance and pod features. That advantage needs a working registration/list/revoke journey and clear limits for DMs and generic clients. |

Prioritise safe recovery export and honest completion feedback, then a phone enrolment journey that visibly shows credential scope, target account, granted capabilities and revocation state. Measure time to the first authorised forum action, wrong-account recovery, successful restoration after original-browser loss, and denial after revocation across existing connections. Keep these as acceptance measurements; this audit has not collected user research or established market demand.

## Diagram changes and remaining scope

NF-05.8 now describes generated-key signup, asynchronous handle/pod work and the backup acknowledgement. NF-22 covers local import, export content, readiness, device-card separation and signed-event attribution. The old NF-05 stamp remains because only this panel was semantically refreshed in this continuation; its consulted source is unchanged at that stamp. Other NF-05 panels retain their own review histories.

No full WASM signup, real download/open origin, print dialog, PDF pagination, QR scan, phone camera, storage-denial, account-switch, relay, live registry or deployed TLS journey ran. The five browser cases qualify the generated formatter output and History API only. These limits do not negate the bounded defects, and the bounded defects do not complete the estate audit.
