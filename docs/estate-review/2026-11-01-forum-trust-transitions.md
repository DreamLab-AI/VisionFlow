# Trust transitions, sweep fairness and audit consistency

Demotion now guards the observed member state and creates its audit record conditionally in the same batch. The older false-audit finding is repaired. Promotion still performs two unchecked, separate writes, and a stale promotion can overwrite a concurrent TL3 grant. Bounded demotion sweeps also restart at the beginning: enough held or persistently failing candidates can prevent later members from ever being considered.

This review assesses every section of ADR-2006 and archived ADR-102, including the later closeout and execution qualifications. It corrects NF-03.8/9 and NF-11.11/12 and adds NF-24. ADR-2014's wider membership-store consolidation remains a separate review; this report does not treat all membership behaviour as covered.

## Findings and acceptance work

**T1 — Repeated capped sweeps can starve later members.** [The engine](../../../nostr-rust-forum/crates/nostr-bbs-relay-worker/src/trust_sweep.rs:253) creates a fresh `None` cursor each invocation. It counts held and failed rows towards the cap and returns once that cap is reached (`:280–301`). `resume_pubkey` contains no timestamp and is neither accepted as an input nor persisted. The entry point nevertheless logs that the next tick resumes from it (`:544`). In the native fixture, three stale TL2 rows retain qualifying counters and sort before one demotable TL1 row. Three consecutive capped runs hold the same prefix and never reach the final row. Replacing the prefix with persistent commit failures has the same result. A larger-budget control reaches and demotes the tail.

This is a parameter-scaled engine counterexample, not an observation of 50,000 real members. The production implication requires at least a cap-sized eligible prefix that remains held or failed. Persist a complete cursor with a sweep generation/threshold snapshot, or use another fair bounded scheduling design. Test repeated ticks, restart recovery, ties, changing activity, persistent errors and return to earlier candidates. Advancing within one invocation is insufficient.

**T2 — Promotion does not share demotion's concurrency or audit guarantees.** [check_promotion](../../../nostr-rust-forum/crates/nostr-bbs-relay-worker/src/trust.rs:202) reads a member, returns early if that snapshot is TL3, computes an earned level, then updates by public key alone (`:238`). In the selected SQL schedule, a concurrent TL3 grant lands after the read; promotion overwrites it with TL2 and logs the stale TL0→TL2 account. A concurrent moderation-count change is also ignored. This contradicts an unqualified claim that promotion never modifies TL3, while preserving the narrower fact that it does not compute TL3.

Both statement execution results are ignored (`:236–266`), and the handler returns `Some(computed)` regardless of those errors. Injecting an update error still creates a promotion audit row; injecting an audit error leaves the promotion without an audit; deleting the member after the snapshot still creates an audit row. The serial-success control behaves as expected. These are exact extracted statements on synthetic SQLite tables, with the ignored-error sequencing mirrored by the probe; they are not an executed Worker race. Apply a guarded snapshot update and conditional audit in one checked transaction, as demotion already does. Report committed, conflict and failed outcomes separately. Reconcile any existing audit discrepancies before using those records as a member-history authority.

**T3 — Hold explanations disappear before reporting.** [decide_demotion](../../../nostr-rust-forum/crates/nostr-bbs-relay-worker/src/trust.rs:326) returns a named reason, but [the engine](../../../nostr-rust-forum/crates/nostr-bbs-relay-worker/src/trust_sweep.rs:281) matches `Hold(_)` and increments only an aggregate. `DemotionSweepResult` has no hold-reason counts or samples. A held-only, untruncated sweep is silent under the scheduled logger (`lib.rs:1162`). Thus balanced totals explain how many rows were held, not why a particular member retained their level. Retain bounded reason counts and a privacy-appropriate diagnostic path. Do not label aggregate arithmetic as per-member explainability.

**T4 — Inactivity alone does not decay earned trust.** The policy tests current counters against the hysteresis band after the time gate; it never ages those counters. A native test leaves an earned TL2 row held after one and ten additional years at unchanged thresholds and counters. That is consistent with the actual predicate and may be the intended policy, but “inactivity-decay” can imply more than it delivers. State the rule explicitly: inactivity makes a row eligible for reconsideration; falling below the band or carrying moderation history determines demotion. If recent contribution is intended, introduce a governed rolling-window model and migration, rather than silently changing existing members' earned rights.

## Comparison and user utility

[Discourse's current trust-level documentation](https://meta.discourse.org/t/discourse-trust-levels-a-detailed-explanation/396792), checked on 1 November 2026, distinguishes all-time early-level activity from a rolling 100-day Regular level, describes a demotion low-water mark and grace period, and reserves its highest level for staff promotion. Its level numbers differ from this forum's. The useful comparison is policy clarity and observable progression, not numerical equivalence or evidence that one policy improves community health.

For this forum, publish the actual earning/retention rule and show members the reason for a transition. Give operators a trustworthy account of committed changes, conflicts, failed writes and sweep coverage. Acceptance should include a concurrent manual grant, a cap-sized persistent prefix, a successful retry after repair and an explanation consistent with the stored audit record. Existing [activity-accounting findings](2026-11-01-forum-read-cache-and-activity.md) remain dependencies: reliable transitions cannot compensate for inaccurate input counters.

[Cloudflare's D1 batch contract](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch) specifies ordered transactional execution and rollback on statement failure. That supports using the existing demotion transaction as an implementation pattern; it does not turn a successful zero-row update into a conflict automatically. Conditional audit creation and checked result counts remain necessary.
