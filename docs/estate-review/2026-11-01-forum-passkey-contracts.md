# Passkey contracts across the clients and auth worker

Both clients send unsigned registration verification requests to a worker that requires NIP-98 authorisation. Even after that mismatch is repaired, the worker discards the PRF salt used at creation and stores a different one for login. This prevents the documented derivation contract from guaranteeing the same Nostr identity on return. The public credential-lookup route also remains present despite comments claiming its removal.

This continuation reviews the passkey dependencies of ADR-2003 and the identity governing document, corrects NF-02.3, NF-02.4 and NF-05.3, and adds six NF-23 panels. The [earlier ADR-2003 section review](2026-11-01-forum-subkey-derivation.md) remains the full decision assessment. This pass adds source and executable evidence about its PRF boundary; it does not claim to finish all forum decisions or repair production authentication.

## Findings and acceptance work

**F1 — Registration fails at the client/worker authorisation boundary.** Forum [register_passkey](../../../nostr-rust-forum/crates/nostr-bbs-forum-client/src/auth/passkey.rs:173) calls `fetch_json_post`; its [header builder](../../../nostr-rust-forum/crates/nostr-bbs-forum-client/src/auth/http.rs:156) sets Content-Type only. [BBS registration](../../../nostr-rust-forum/crates/nostr-bbs-bbs-client/src/passkey.rs:356) does the same. [register_verify](../../../nostr-rust-forum/crates/nostr-bbs-auth-worker/src/webauthn.rs:836) rejects a missing Authorization header before attestation processing. The router supplies no missing signature. This source composition establishes the request mismatch; no HTTP request was made. Sign the exact registration request with the newly derived key, keep the worker's identity binding, and test both clients against the pinned worker with missing, wrong and valid signatures. Do not weaken the server to accommodate the stale clients.

**F2 — The PRF salt changes between creation and login.** [register_options](../../../nostr-rust-forum/crates/nostr-bbs-auth-worker/src/webauthn.rs:739) issues random salt A but does not retain it with the challenge. Both clients use decoded A as PRF input and A's encoded string as the downstream HKDF salt. [register_verify](../../../nostr-rust-forum/crates/nostr-bbs-auth-worker/src/webauthn.rs:1021) ignores the supplied A and stores B, a hash over domain, server secret, credential ID and public key. Login returns B. An audit test holds PRF output constant and invokes actual `derive_from_prf`: A and B produce different public keys; repeating A reproduces the original. This isolates the HKDF input defect without pretending to emulate authenticator PRF. Real PRF input also changes. F1 currently blocks the normal new-registration path first; F2 remains independently relevant to externally provisioned or future repaired registration. Persist a server-issued salt bound to the ceremony and return the same bytes on login. Prove equality before accepting enrolment and define recovery for previously stored incompatible rows. Never repair this by accepting an unbound client salt.

**F3 — Discovery/privacy claims contradict routed behaviour.** [credential_lookup](../../../nostr-rust-forum/crates/nostr-bbs-auth-worker/src/webauthn.rs:1427) remains exposed through [the router](../../../nostr-rust-forum/crates/nostr-bbs-auth-worker/src/lib.rs:275), before the `/api` NIP-98 gate. It distinguishes known IDs and returns their public key. The common IP rate limiter still applies; this is not unlimited enumeration or evidence that random high-entropy credential IDs are guessable. An exact-SQL probe demonstrates the known/missing distinction. Meanwhile, [the fallback](../../../nostr-rust-forum/crates/nostr-bbs-auth-worker/src/webauthn.rs:66) uses an empty secret when configuration is absent. In that condition, unknown-key salts are publicly computable; equal response shape does not conceal which keys match that formula. A synthetic test reproduces the distinction. No live secret configuration was inspected. Remove or possession-gate lookup according to an explicit discovery design, and fail closed on missing required secret configuration. The concatenated SHA-256 construction is not HMAC; use a reviewed keyed primitive if a secret-based indistinguishability contract is retained.

**F4 — Creation support is confused with creation-time evaluation.** Forum [PRF extraction](../../../nostr-rust-forum/crates/nostr-bbs-forum-client/src/auth/webauthn.rs:123) rejects `enabled=true` without `results.first`. BBS has the same requirement. The WebAuthn specification permits creation output with PRF enabled but no evaluation result; a subsequent assertion can evaluate it. This means a capable authenticator may be rejected by the application. A function-toString test for `[native code]` also rejects intercepted creation based on implementation appearance, not measured PRF capability. Add a supported follow-up assertion for the newly created credential, handle cancellation without orphaned enrolment claims, and qualify combinations by actual results. This is source/spec evidence, not an executed hardware compatibility matrix. [WebAuthn PRF](https://www.w3.org/TR/webauthn-3/#prf-extension).

**F5 — The hybrid-transport guard checks an API absent from standard assertions.** Both helpers look for `response.getTransports()` on an assertion and allow the operation when that call fails. WebAuthn defines that method on attestation responses, while assertion responses expose authenticatorData, signature and userHandle. Thus the helper is not evidence that hybrid assertions are blocked. Nor is attachment mode alone proof of a different credential or PRF output. Replace this heuristic with explicit identity equality and a tested credential/transport policy. Keep any unsupported-platform copy versioned against evidence. No hybrid or synced-authenticator flow ran here. [WebAuthn assertion interface](https://www.w3.org/TR/webauthn-3/#authenticatorassertionresponse), [attestation interface](https://www.w3.org/TR/webauthn-3/#authenticatorattestationresponse).

**F6 — The parser verifies a P-256 point while ignoring parts of the credential's claimed format.** Actual `parse_cose_p256_key` accepts valid coordinates without kty/alg/crv, contradictory RSA/RS256 metadata and duplicate x labels where the last wins. An off-curve zero point is correctly rejected. The attestation parser accepts `packed` with an empty statement; the handler recognises the format string but never verifies that statement. This does not bypass the separate NIP-98 ownership proof or the login signature check, and a no-attestation policy may be deliberate. It does mean the implementation must not claim validated packed self-attestation or complete ES256 COSE validation. Declare a no-attestation policy or verify the selected format, enforce supported algorithm metadata and duplicate-key rules, and stop advertising RSA unless it is implemented. Prefer a maintained WebAuthn/CBOR implementation over extending the local parser.

**F7 — Unknown CBOR fields can hide truncated payloads.** `cbor_skip_value` returns a declared byte/text length without checking remaining bytes. A native probe appends a final unknown attestation field claiming 65,535 bytes with no payload; parsing still succeeds. A truncated known authData field correctly fails. This proves inconsistent structural validation, not a memory disclosure or a production denial of service. Recursive skip paths also have no explicit depth budget in source; recursion exhaustion was not tested. Enforce input-length, nesting, duplicate-field and complete-consumption limits and retain rejection controls for ignored fields.

**F8 — Single-use challenge and unique-credential claims exceed the transaction boundaries.** Exact bootstrap schema permits two rows for one owner. In a chosen schedule, two requests read a valid challenge before either commits; both unconditional update/delete batches succeed, with the second deletion affecting zero rows. The handler does not check that result. A serial reuse control correctly finds no challenge. This is an SQLite model of the query boundary, not proof of production D1 interleaving or a bypass of the separate NIP-98 replay store. Both requests are assumed to have independently valid NIP-98 tokens and WebAuthn data. Enforce unique credential identity and atomic challenge claim/consumption with checked affected rows; bind counters to the selected credential and handle zero-counter transitions deliberately. Test concurrent assertions and failure recovery through the real worker adapter.

## Comparable designs and user utility

Primary sources were checked on 1 November 2026. [Yubico's PRF guide](https://developers.yubico.com/WebAuthn/Concepts/PRF_Extension/Developers_Guide_to_PRF.html) separates enabling PRF at creation from evaluating it during assertion, retains per-credential salt, and applies a purpose-bound KDF. That is a useful implementation pattern for this flow; its example encryption keys are not a drop-in Nostr identity scheme.

[wwWallet](https://github.com/wwWallet/wallet-frontend) is a web-first digital credential wallet with a documented PRF compatibility matrix across authenticators, operating systems and transports. Its purpose differs from a community forum. The comparison supports publishing a tested compatibility matrix and explaining recovery paths, not claiming feature parity, equal security or measured market demand. Generic statements that all Windows Hello, password-manager or hybrid flows are incapable should not replace actual compatibility evidence.

The forum's potential utility is a passkey-backed signing identity usable across its governance, messaging and pod features. The first acceptance milestone is mundane but decisive: create an identity, close the original session, return with the same credential, derive the same public key and perform one authorised action. Then test a fresh browser, lost saved metadata, cancelled enrolment, multiple resident credentials and recovery without replacing the identity accidentally. Report creation, local key availability and server acceptance separately. Until that journey works, expanding onboarding claims or transport restrictions would add confusion rather than user value.

## Remaining boundaries

This audit does not establish authenticator attestation policy, hardware trust, deployed TLS/origin configuration, effective database migrations, live rate limits, PRF-provider availability or complete memory erasure. Native signature controls pass, including the existing high-S P-256 case. Passing those controls does not repair the caller/header/salt contracts. Other NF-02 and NF-05 panels retain their existing review histories and source stamps; the wider estate review remains active.
