# NIP-171 upgrade: recovery primitives, incomplete owner and member workflows

Local upgrade code contains working derivation, recovery-record and ticket primitives. It does not yet provide the owner workflow required to activate them. Its existing member-driven epoch reservation remains a documented blocker; a new fixture also shows that a rejected multi-claim event can leave a reservation behind. Browser and agentbox consumers disagree on how an epoch conflict affects sending and historical reading. The feature should remain off under the branch's own activation rule.

This report assesses every section of ADR-2028, adds NF-28.1–6 and corrects NF-05's statement that nothing is implemented. It does not close ADR-2027, ADR-2029, the wider agentbox audit or deployment acceptance.

## Findings and acceptance criteria

**K1 — An event can be rejected after reserving an epoch; owner-only registration remains absent.** `zone_groups.rs:38–45,145–162` uses insert-on-conflict-ignore followed by lookup. `nip_handlers.rs:2551–2567` first checks every claim against existing rows, then inserts each separately. Two different keys for the same previously empty epoch pass the first loop; the first insert survives the second claim's refusal. The new SQLite fixture reproduces this with future epoch 9000. Saving the event happens later, so event-storage failure is another source-visible reservation gap, not separately fault-injected. The preflight comment promising that a refused event claims nothing is false for this input. The known future-epoch squat is explicitly documented by the ADR; the new evidence concerns partial mutation on refusal. The auth worker's admin recipient registration has no epoch number and accepts any admin, not a verified sole zone owner. Add owner-authorised numbered activation, reject unregistered member claims, and make rejection leave reservation state unchanged. Test duplicate conflicting tags, persistence failure, concurrent claimers, non-owner admins and rollback through the actual Worker. Until then keep the flag off. Treat the claimed reset path as unverified; the recorded source search found no implementation.

**K2 — Keeping both browser keys does not make both histories readable.** `store.rs:95` calls `keyset::read_key`, which chooses one key for zone/epoch by legacy priority then public-key order. `read_outcome` rejects a key whose pubkey differs from the event's zk pubkey. The native probe holds both valid keys, encrypts under the unselected one, proves direct decryption succeeds with that key, then gets `Failed` through the real read path. Resolve reads by the message's validated key identity and authoritative binding. Test both histories before and after conflict reconciliation, reload and account switching. Sending should remain blocked at a contested current epoch.

**K3 — Agentbox recognises a conflict but continues sending with the first key.** `zone-keys.js:498–506` rejects a second valid bound-group ticket. Its store retains only the first key and no conflict marker; `latest` and `writePlan` still select it. The new probe verifies two group-signed tickets, observes rejection of the second, and encrypts a new message with the first. This is an unchanged production helper with synthetic inputs, not a live bot transmission. Align browser and agentbox conflict state, persistence and higher-epoch resolution. A common vector suite should verify refusal to send at a disputed latest epoch and access to retained historical ciphertext. The existing agentbox reader and JunkieJarvis routing are present; this is not a missing-format-support finding.

**K4 — Valid recovery primitives do not establish usable or current recovery.** `nip171.rs` explicitly postpones owner consumers; `tickets.rs:573` has only a test call site. `validate_chain` checks the records supplied to it. The new signed/encrypted-record probe accepts both a complete three-record chain and its older valid prefix when the newest record is omitted. This is an observation/completeness boundary, not a forged-record or cryptographic validation bug. Implement bounded completed reads, retained checkpoints, observed-head reconciliation and complete-chain publication acknowledgement before issuing tickets. Then restore a zone on a fresh device, including an unavailable replica, a withheld newer record, missing parents and a known fork. Record what cannot be established when relays omit updates. Native vector success must not be shown as a completed backup in the UI.

**K5 — Owner-encrypted legacy backup cannot replace ordinary-member history grants by itself.** `build_imported_epochs` and `parse_imported_epochs` use the group identity secret for self-encryption. A 1014 ticket gives a member an epoch secret, not that owner secret. Consequently, the ADR's new-member history promise needs a separate owner-mediated distribution mechanism; it does not follow from the imported record plus a current ticket. Giving members the group secret would grant membership authority and violate the owner model. Specify which historical epochs a new member may read, distribute only those epoch keys, and prove fresh-member history access without the master. Include every observed legacy key in the owner's export receipt and test a missing-key failure before migration. This is a design/source finding; no owner-to-new-member workflow exists to exercise.

**K6 — Reader-before-issuer rollout has a durable discard edge.** With its flag off, browser routing treats 1014 as Ignore; `store.rs:329–331` records the wrap as processed. Once persisted, enabling the group flag alone does not revisit that processed ID. There is a specific exception: enabling grant sweep revisits identity-addressed wraps, but not inbox-addressed wraps (`store.rs:258–264`). With the flag on but no binding, processing retries, while the loaded binding cache is session-scoped and is not refreshed by every retry. The existing route tests verify routing; browser IndexedDB replay was not executed. Keep unknown future ticket kinds replayable, refresh binding state deliberately and test an offline/mixed-version member across activation. Require reader and binding readiness before issuance; a deployed dormant bundle alone does not prove it.

**K7 — The cutover clock and its enforcement layer are underspecified.** The dormant deployment runbook starts thirty days immediately while declaring owner migration unbuilt; ADR-2028 says live Phase 4. Existing readers continue to accept 21453 and issuers can fall back to it. The relay sees outer recipient metadata, not the encrypted inner grant kind; without an authenticated derivation/epoch registry it cannot distinguish a valid-looking random public key from a derived one. This follows from the inspected wrap path and [NIP-59's encrypted envelope](https://raw.githubusercontent.com/nostr-protocol/nips/master/59.md). Define an activation receipt naming each zone, code revision, readers, binding and date. Assign visible recipient/epoch policy to the relay and inner-kind retirement to authenticated issuers/readers. Test an offline member returning after the window and the owner's recovery action. No production cutover was attempted.

**K8 — Forum adaptation is not full draft interoperability.** The three consumers deliberately reject epoch zero and bound tickets to u32, while recovery derivation accepts the draft's larger range. The board's signed zk transport remains separate from the proposed room mode, and its signed inner ticket is a documented NIP-59 departure. Record these as an explicit interoperability profile; pin the draft revision and run bidirectional external-client tests for initial membership, rotation, conflict, history and owner replacement. Test the optional zk group hint on the browser read path as well as at relay admission. Do not market an Anagram-compatible board based solely on matching derivation vectors.

## Comparison and user utility

The [current Anagram NIP-171 draft](https://raw.githubusercontent.com/lnbits/anagram/main/nips/nip171.md) remains optional and draft. It starts tickets at epoch zero, permits integers through 2^53−1, blocks sending on conflicting highest-epoch tickets, and separates recovery-chain validation from completed relay reads and publication acknowledgement. The inspected derivation vectors match it. Its operational guidance also acknowledges unseen updates rather than promising global consensus. This supports treating the forum as a specialised signed board adopting selected group-key mechanisms, with interoperability still to prove.

[Anagram's private-group documentation](https://raw.githubusercontent.com/lnbits/anagram/main/docs/private-groups.md) offers a useful usability comparison: key discovery and message history have separate lifecycles; history loading is bounded; failed or incomplete reads retain retry state; recovered tickets trigger bounded retries of pending ciphertext. These are documented behaviours, not independently benchmarked runtime results. For VisionFlow, present distinct states for **key received**, **history loading**, **history incomplete** and **ready to post**, with an actionable recovery path. Measure successful fresh-device recovery, complete authorised history delivery and recovery time under a missing relay or ticket, rather than counting generated keys.

Priority order follows user outcomes: establish owner-only numbered registration and consistent conflict handling; implement owner restore and member-history distribution; make mixed-version activation replayable; then prove the optional external-client journey. The signed board, moderation and kanban remain a distinct product use case. Broad estate positioning and the rest of agentbox require their remaining audits.
