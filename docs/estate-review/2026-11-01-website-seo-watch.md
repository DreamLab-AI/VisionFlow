# DreamLab website nightly SEO watch and proposal boundaries

The nightly SEO audit is running and retains useful site receipts. Its normal proposal publisher, however, commits the proposed files and then compares the now-empty staging area with those files, so it refuses before push. Local fixtures also reproduce incomplete crawler-rule handling, misleading coverage counts, unaccounted model retry usage and an error path that writes a synthetic secret to the ledger and log.

This pass adds the previously omitted service as six [DW-08 panels](../diagrams/dreamlab-ai-website/08-nightly-seo-watch.md) and assesses every section and distinct obligation of ADR-2010. No website code, decision status, scheduler, live state or remote PR was changed. DW-01–07 and other website decisions retain their previous assessment boundaries; this report does not close the whole website review.

The `scrubSecrets` implementation deliberately preserves public keys and only knows matching environment values/token shapes (`lib/safety.mjs:23–49`). The observed failure is a missing invocation at real sinks, not proof that the scrubber can recognise every possible secret. The build environment is cleared and HOME redirected, but the process keeps the same UID and can access the surrounding filesystem. Sharing `node_modules` at `lib/propose.mjs:132–135` also does not prove that installed dependencies match the fetched commit's lockfile. These limits matter before expanding the executable patch surface.

Browser ownership remains a source-only concurrency concern: `lib/audit.mjs:103–117` opens/closes its own tab by ID but invokes evaluate, console and Lighthouse operations against the selected page without an explicit page ID. Another shared-sidecar client could change selection between calls. No concurrent browser interference was attempted in this batch.

## Comparison and user utility

The robot-group counterexample is a conformance issue, not a preference: [RFC 9309 §2.2.1](https://www.rfc-editor.org/rfc/rfc9309.html#section-2.2.1) requires rules from matching user-agent groups to be combined. The present first-group selection cannot support the record's unqualified RFC claim.

| Comparator, checked 1 November 2026 | Relevant capability | Implication for this estate |
|---|---|---|
| [Lighthouse CI](https://github.com/GoogleChrome/lighthouse-ci) and its [configuration](https://googlechrome.github.io/lighthouse-ci/docs/configuration.html) | Commit-oriented Lighthouse automation, collection/assertion/upload stages, repeated collections and configurable assertions; documented server cron collection can monitor production URLs. | Scheduled Lighthouse checks alone are not a differentiator. Reuse explicit sampling, threshold and retained-run contracts; distinguish deploy regressions from noisy live readings. This is a capability comparison, not a measured speed/quality benchmark. |
| [Screaming Frog SEO Spider](https://www.screamingfrog.co.uk/seo-spider/) | Its official feature description includes scheduled crawls, Chromium rendering, crawl comparison and Search Console/PageSpeed integrations. | The watch is narrower than a general SEO audit platform. Its useful prospective distinction is a small, repository-aware, human-reviewed change loop linked to estate operations, once delivery and evidence boundaries work. |
| [Google URL Inspection API](https://developers.google.com/webmaster-tools/v1/urlInspection.index/inspect) | Authenticated inspection reports the version held in Google's index; the endpoint cannot test a live URL's indexability. | Combine authorised index evidence with live fetch receipts when indexing is the question. Keep these observations separate; neither one proves conversion or visibility for a user's query. |

For the site owner, prioritise a trustworthy morning report: show completed coverage and skipped work, explain why an alert changed, distinguish provider failure from a negative finding, and expose whether a proposal reached a reviewable remote object. Next, qualify the full proposal transaction and recovery locally before enabling broader patch authority. Then measure reviewed-and-accepted improvements, time to repair confirmed regressions and relevant enquiry outcomes, alongside costs per useful result. These are recommended acceptance measures, not outcomes measured in this pass.

The market inference is bounded: this component is currently bespoke operational monitoring with a defective optional proposal path. It does not establish a standalone SEO product, superior agent discovery, or a novel crawler. The estate could make it useful through reliable integration and decision evidence rather than expanding the number of checks before existing receipts can be trusted.
