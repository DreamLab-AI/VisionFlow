# Subkey derivation: byte parity and the identity lifecycle

Raw HMAC derivation matches the shared vectors. Its surrounding assurances are weaker: the JavaScript parity runner checks source substrings, the two agentbox send/receive entrypoints disagree on identity modes, and changing a tag does not revoke the old credential. This continuation reviews every section of operative ADR-2003 and archived ADR-094/100, adds four NF-21 panels, and corrects the parity and compromise claims in NF-09.3, NF-12.3, NF-10.2 and NF-10.7. Runtime fixes and deployment acceptance remain open.

## Evidence and boundaries

The [source manifest](evidence/2026-11-01/nf-derivation/source-manifest.json) retains thirteen exact files: ten from forum `c39f41f104b114d6a3fa29013daaf6fa58b45080` and three agentbox consumers from `9dfc27b16e82e9786535a55e790710493dd51fdf`. All ten forum exports equal the existing diagram stamp `1b27f79`; nine equal the website-consumed `9c36b6032640c89879ae52fe25da99493979a0b6`. The remaining `keys.rs` differences are k256 argument-type conversions, retained in [source differences](evidence/2026-11-01/nf-derivation/source-differences.json). These identities do not prove which code is deployed.

Thirty Rust tests pass: 22 existing key tests, five existing shared-vector tests and three audit additions. Twelve JavaScript selection/cache probes use verbatim extracted functions or statement blocks with synthetic roots and mocked key/configuration inputs. Eight scenarios run the unchanged parity runner against isolated source/fixture variants. The baseline runner reports 13 vectors, three invalid-root controls and 18 checks; those checks are not counted again as independent audit tests. No agentbox entrypoint was imported, no real secret was read, and no socket, message, account or deployment was changed. [Reproduction instructions](evidence/2026-11-01/nf-derivation/README.md) describe the precise execution boundary.

## Archived ADR-094 section review

| Section | Disposition |
| --- | --- |
| Status, date, owners and related records | Retain as historical accepted lineage. The current Rust primitive and wasm export exist; the record does not establish current browser execution or a Telegram deployment. |
| 1 Context | Shared deterministic derivation is implemented. Actual forum device helpers choose fresh UUID tags; mirror and gateway consumers select different defaults and modes. Equality requires the same root and exact tag, not merely the same user. |
| 2 Decision and scheme | Signature and raw HMAC construction match. `SecretKey::from_bytes` rejects invalid scalars without modular reduction. The nearby `keys.rs` and wasm comments saying “reduced” are inaccurate. No invalid-HMAC preimage was found or searched for. |
| 2 Cross-language contract | Correct at the primitive-byte level for valid inputs. The claim that both production sides apply the same scalar validation is too broad; the runner adds its own validation. The wasm bridge delegates to core after hex/length checks but was not executed here. |
| 2 Rotation | Distinct tags produce distinct tested children. Old-key signatures remain valid and root plus old tag recreates the old child. Updating a tag requires consumer reload and authorisation changes. |
| 3 Known-answer vector | The retained inline vector, shared fixture and both current language runs agree. This is a compatibility control, not a security proof or a release selection test. |
| 4 Why not reuse PRF derivation | Keeping the two contracts separate is supported. The old empty-salt/`nostr-secp256k1-v1` account is obsolete; current code uses Podkey salt/info and bounded scalar retry. HKDF Expand appends its block counter, rather than prepending it as this section says. |
| 5 Security note | Root recovery of children is supported. It does not imply that a child holder learns the root, or that a registry cannot withdraw the child's delegated rights. The blanket NIP-26 recommendation needs reconsideration: its current specification is marked unrecommended and does not provide an immediate revocation operation. |
| 6 Consequences | Core is a canonical Rust primitive; three independent JavaScript consumers still contain derivation expressions. Wasm exposure is source-supported. Stable shared identity and tag rotation need a documented consumer contract and lifecycle tests. |

## Findings and acceptance work

**F1 — Source-presence checks can certify non-executing or changed derivation.** The [runner](../../../nostr-rust-forum/scripts/identity-vector-parity.mjs:193) marks read errors as successful skips, records current hashes and tests `text.includes(...)`. In isolated controls, removing all agentbox sources still returns success (15/15 checks); replacing all three files with comments containing the expected expressions returns 18/18. Changing the gateway's default tag changes the extracted production selection result but the runner still returns 18/18. Removing an expression, corrupting a vector or deleting the fixture correctly fails. An unrelated comment containing `HKDF` also fails. These are bounded false-negative and false-positive controls, not a claim that current production files are malicious. Export a side-effect-free production selector/deriver, execute it with fixture inputs, and require expected source identities when claiming release parity. Keep an explicitly labelled primitive-only mode for missing sources.

**F2 — Shared configuration does not select a shared identity.** The [sender](../../../project/agentbox/config/nostr-gateway/nostr-send.cjs:34) derives only for `AGENTBOX_GATEWAY_IDENTITY=child`, using the mirror tag; the [gateway](../../../project/agentbox/config/nostr-gateway/gateway.cjs:152) derives only for `gateway`, using the gateway tag. Under `child`, the extracted sender chooses a child while the gateway chooses the raw root; under `gateway`, the reverse happens. Both default to the raw root. This contradicts the sender's “same identity selection” comment. Define supported modes, purpose and expected public key once, then test both entrypoints against that contract. No current deployment setting or message recipient was inspected.

**F3 — Exact primitive tags and consumer tags are different boundaries.** Core preserves all UTF-8 bytes; agentbox `envFirst` trims values and substitutes defaults for empty strings. A native whitespace probe produces different children while the mirror's padded environment value resolves to the canonical unpadded tag. The [mirror cache](../../../project/agentbox/config/hooks/nostr-live-mirror.cjs:211) also returns its first result before rereading root, mode or tag. Same-module tests retain the old child after root/tag changes and retain `null` after re-enabling a cached-off mirror. This does not show that any long-running process supports live configuration edits. Document the exact input bytes, reload boundary and expected public key, and verify consumer adoption after rotation.

**F4 — Validation in the parity runner is not production input validation.** Core's [constructor](../../../nostr-rust-forum/crates/nostr-bbs-core/src/keys.rs:49) rejects all-zero and out-of-range roots. Extracted mirror and sender helpers accept a syntactically valid all-zero root in child mode and produce HMAC bytes. A forced zero-output HMAC mock is also returned without child scalar validation. The mock tests control flow; they do not demonstrate a real invalid-child derivation. Gateway calls `getPublicKey(rawSk)` before selection, and downstream nostr-tools may reject invalid bytes; those boundaries were not executed. Validate roots and children explicitly at each public helper boundary and report errors rather than relying on later signing failures.

**F5 — Recovery, derivation and authorisation need separate claims.** A native probe derives v1 and v2, signs with v1 after v2 exists, verifies that signature under v1 and rejects it under v2. Re-deriving v1 still yields its original bytes. Another confirms that core has no service/account context beyond root and tag. These tests establish deterministic behaviour and signature lifetime, not resistance to cryptanalysis. Root knowledge recovers children; child-only exposure does not by itself establish root disclosure. Existing NF-10.2 and NF-12.3 language wrongly turned the former into a universal rejection of child-only containment. Registry authority, caches, raw-key rights and previously disclosed content must be assessed independently. This builds on the previous device-key evidence rather than recounting those tests as new executions.

**F6 — CI execution is not an enforced release-pair proof.** The [workflow](../../../nostr-rust-forum/.github/workflows/ci.yml:274) checks out agentbox without an explicit `ref` and invokes the parity runner. Its `ci-pass` dependencies omit `drift-gates`. The job has no separate change filter despite a comment saying it runs only for its own scripts/fixtures; workflow-level path filters govern it. No agentbox-origin trigger or paired release manifest is present in this workflow. Source alone cannot establish branch rules. A separate [read-only GitHub snapshot](evidence/2026-11-01/nf-derivation/remote-branch-rules.json) returned `protected: false`, a specific “Branch not protected” response from the protection endpoint, and an empty active-rules list for `main`. That remote branch was at `478f51229734cbbdb58ab57cc2fe2d2ad9c82ac8`, distinct from this audit’s local forum revision; its workflow content was not substituted for the pinned local source. The snapshot establishes the reported protection state at observation time, not a permanent guarantee or a simulated merge. Record both release commits, make claimed source checks mandatory, and configure required checks explicitly before presenting them as merge enforcement.

## External comparison and user utility

[BIP-85](https://github.com/bitcoin/bips/blob/master/bip-0085.mediawiki) provides deterministic application entropy using hardened BIP32 paths and a different HMAC-SHA512 construction. Its structured application/index scheme is a useful comparison for recoverable purpose identities; it is not byte-compatible with this forum contract. The practical opportunity is a versioned recovery descriptor containing the algorithm, exact purpose tag and expected public key, plus separate records of grants and revocation state. Any descriptor design must account for privacy and tag retention; this is a product recommendation, not a new wire format or a claim of BIP-85 support.

[RFC 5869](https://www.rfc-editor.org/rfc/rfc5869) distinguishes extraction from expansion and places the Expand block counter after the info. [Node's HKDF API](https://nodejs.org/api/crypto.html#cryptohkdfsyncdigest-ikm-salt-info-keylen) implements the full RFC function. These clarify the inaccurate comments without motivating a silent identity-changing migration. [NIP-26](https://github.com/nostr-protocol/nips/blob/master/26.md) currently marks delegated signing unrecommended; its kind/time conditions do not supply a general immediate revocation endpoint. It should not be presented as a drop-in fix for the archived ADR's lifecycle gap. [GitHub's protected-branch documentation](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) also makes required checks a repository rule, not an implication of a workflow comment. Primary sources were read on 1 November 2026.

A useful recovery journey should show which identity each component will use, let an operator verify it before enrolment, record how a tag change reaches every consumer, and separately demonstrate withdrawal of the old key's delegated rights. That would make the existing compatibility work useful to users. No adoption, market superiority, live compromise or successful end-to-end rotation is claimed.
