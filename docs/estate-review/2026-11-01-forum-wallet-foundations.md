# Wallet foundations: custody, tip attribution and parent balances

Wallet code protects asset carriers and validates extension signatures, while the optional parent-chain card remains read-only. Its maturity and pair parsers accept inconsistent data, however, and its account-bound requests have no check against late completion. A synthetic starter-pack build also produces a 1,500-sat fee where the confirmation screen offers a fixed “about 250 sats” hint. This audit records those boundaries without activating sidestr or changing product code.

## Findings and practical consequences

| ID | Result and recommended next step |
|---|---|
| **F1 — maturity without reconciliation** | Native tests show `confirmed=100` plus `utxo=[]` yields 100 spendable; a one-unit ordinary UTXO also yields 100; and an ordinary coin above the reported tip is counted as spendable. `parent.rs:148–174` sums only immature coinbase values, then subtracts from confirmed. These inputs can reflect inconsistent snapshots or bad backend data. Reconcile a complete coin set at a common tip, accounting for mempool spends and the backend's balance convention; show Unknown on disagreement. Simply requiring a naive sum can also be wrong when an API omits mempool-spent confirmed outputs. |
| **F2 — numeric and pair identity boundaries** | A mempool inflow of `u64::MAX` casts to -1. Another extreme subtraction and a pair sum overflow both panic in the native debug build; tests deliberately catch those panics. Release/WASM behaviour was not executed and is not claimed to panic. Duplicate identical pair outpoints count twice because Coin retains only `value`. Reject out-of-range amounts, use checked arithmetic and retain/deduplicate outpoints. Extreme values are hardening probes, not plausible present supply. |
| **F3 — late account response** | `pages/wallet.rs:261–269` launches an async read on each account change and writes to one signal without checking current address or request generation. A slow earlier read can overwrite a newer account's view while the rendered address comes from the current account. This is source evidence, not an executed browser race. Bind results to the requested address, cancel/ignore superseded work and clear state on missing identity. |
| **F4 — optional requests can hold the entire card** | `parent.rs:263–319` has no explicit timeout/abort. The caller waits for optional UTXO, tip and pair work before displaying even the main balance. Failures become no split, concealing unsupported routes, malformed answers and outages alike. A stalled request is not an error and can keep the card loading. Source-only finding. Show the main result progressively; bound and label each optional capability independently. |
| **F5 — confirmation is not a built-fee preview** | The actual `build_provision` with 30 synthetic 1,500-sat coins constructs a 30,000-sat pack using 21 inputs and charging 1,500 sats. The page displays a constant 250-sat estimate (`pages/wallet.rs:48,598`) before the transaction is built. It is explicitly approximate, so this is not a breached fee-cap promise. Build first, show the actual fee/recipient/outputs, then sign that same transaction; preserve stale-input and account-change checks. No real coins were used. |
| **F6 — post memo is not recipient attribution** | `chain.rs:459–474` counts the asset in the first non-OP_RETURN output for a valid tip memo without consulting the post author. The UI passes the author to its own send path, but arbitrary chain transactions need not originate there. A self-directed or wrong-recipient memo can therefore be a candidate tally without proving that author was paid. This is source inference, not a constructed/broadcast forged tip. Bind the receipt's recipient to the displayed post author and distinguish pending from confirmed contributions. |
| **F7 — stronger spending labels than evidence** | Pair membership alone does not establish maturity, current unspentness or transaction relay policy. The parent UI's “spendable now” and “spendable on either” sit alongside an accurate backend-trust disclosure, but still overstate these specific parser results. Prefer “backend-reported unspent” and a separately evidenced maturity state; expose backend identity, observation time and chain-tip context. |
| **F8 — documentation drift in custody and build order** | `auth/session.rs` contains contradictory comments about remember-me defaults; actual `remember_me` and login UI default false. Asset verification is before return/publication, not always before local signing. Update those exact descriptions in a product follow-up. This audit does not claim unexpected default durable storage or an asset-burning path through the checked builder. |

## External comparison and utility

Esplora documents separate address totals and UTXO lists; its standard UTXO response does not promise the custom coinbase flag this card needs. That makes capability detection and Unknown maturity a normal interoperable result. API shape alone cannot establish the backend's fork or make separately fetched snapshots consistent. [Esplora API](https://github.com/Blockstream/esplora/blob/master/API.md), checked 2026-11-01.

Blaketestnode now documents daemon address indexing and pair comparison, plus a browser node that keeps a snapshot/index locally and validates later blocks. Its README reports roughly 1.1 GB of browser storage and environment-specific timings; those are upstream measurements, not measurements of the forum. This provides a concrete alternative to trusting a remote balance, but not a free drop-in replacement. Test address-query coverage, cold-start cost and recovery before proposing browser validation here. [Blaketestnode](https://github.com/bitcoin-blake/blaketestnode), checked 2026-11-01.

Bitcoin Core distinguishes `rawtr(KEY)`, where the key is already the output key, from `tr(KEY)`, where it is the internal key. That distinction matches the parent's bare-key address path and explains why an ordinary wallet's default Taproot receive address need not match the forum identity address. An external-wallet handoff should identify the required account/output-key convention without asking members to paste secrets into the forum. [Bitcoin Core descriptors](https://github.com/bitcoin/bitcoin/blob/master/doc/descriptors.md), checked 2026-11-01.

A useful product test is whether a member can recognise a contribution, inspect the exact transaction they approve and understand a stale or uncertain balance. A second balance card adds little if it can show the previous account's response or overstate spendability. Prioritise F1–F4 and transaction preview, then verify contribution attribution. These are recommendations for a future authorised implementation; the staged/parked activation decisions remain intact. No demand study or adoption claim follows from this technical comparison.

The 725-test full client baseline belongs to the preceding batch at the same consumed pin. This run does not repeat that broader claim as a fresh result. Native tests do not exercise fetch timing, browser account changes, storage failures, WASM behaviour, actual node policy or an external wallet handoff.
