# SideStr EVM withdrawal accounting and snapshot trust

A synthetic block containing two equal withdrawals passed the complete Rust follower while paying their recipient only once. The spare withdrawal allowance paid the signer. Separately, snapshot restore accepted changed contract bytecode under the original account root, changing a read-only call from 42 to 43. These are material gaps in accounting and restored-state integrity despite the existing fixture suite passing.

This component review covers `sidestr-evm` at **sidestr-rs `9c6de86c657a25ec2f2a189baf63db7dedad40eb`** and all four SR-03 panels. [Source fingerprints](evidence/2026-11-01/evm/sources.json) bind the implementation, fixtures and pinned JavaScript predicate. The report adds no whole-ADR assessment, runtime activation or complete repository assurance. Product source and live services remain unchanged, including VisionClaw springs.

All probes use deterministic synthetic keys and isolated in-memory chains. E1 requires a signer to construct the block; it is not a demonstration that an unsigned outsider can modify history. The ordinary producer emits one output for each withdrawal, so the probe targets validator protection against a different signed construction. E2/E3 assume the restore API receives altered snapshot data; this review does not establish a network snapshot-ingestion route or operational compromise.

## Withdrawal accounting and reference compatibility

The [first probe](evidence/2026-11-01/evm/probe.json) creates two valid carried Ethereum withdrawals of **10,000 sats each** to the same script. A control with no recipient output is rejected. A control with two separate 10,000-sat outputs passes. The adversarial block pays the recipient once, pays the signer **15,000 sats** against an ordinary transaction fee of **5,000 sats**, and still passes `State::add_block`. Both withdrawal receipts are successful and the sender nonce advances twice. The complete host validator was exercised, not merely the overlay helper.

The baked reference `siding/lib/overlays/evm.mjs` has SHA-256 `d526495d008a2f94b2d7060585ce6f7c89810d52b46d14883719fee5161aa58d`, exactly the module pin in the fixture generator. Its line 102 also tests each withdrawal with `outputs.some`, and lines 120-122 sum every withdrawal into the coinbase allowance. This is a source comparison with the pinned module, not fresh JavaScript execution. It establishes that the problematic predicate is shared with the compatibility target; passing the current oracle does not distinguish it from the intended implementation.

A correction changes which signed blocks are accepted. The estate needs an explicit rule/version transition and updated differential expectations, rather than a Rust-only change that leaves validators disagreeing. No consensus implementation was changed in this audit.

## Restore and execution boundaries

A normal snapshot round-trip preserves the selected root and a contract call returning 42. The wrong-root control is rejected. Changing only that contract's stored bytecode to return 43 then restores successfully under the same root and changes execution. This is possible because the trie contains `Account.code_hash`, while the code map is separately deserialised and read without checking its bytes against that key. The probe uses the existing serialization/API surface; it does not bypass Rust privacy with unsafe code.

Receipt/time changes also pass because those fields are not committed by the account trie. The snapshot's block record contains an EVM root and Ethereum transaction hashes, not a signed sidechain header or a receipt-root proof. Even correcting the code-map check would leave E3's trust decision necessary. The previous diagram's “root and time agree” wording hid the distinction between a time entry being present and its value being independently authenticated.

The selected-height API retains all source histories by design of its copy operation. At height zero, the probe sees zero account balance and the empty root, but still retrieves a future deployment receipt and block record. Whether callers want an archive or a rewound active view must be explicit. A subsequent branch, consumer presentation and RPC response policy remain to be audited; current evidence proves the library behaviour only.

Preparation still protects the *applied* world: failed block checks do not promote speculative balances. However, an EVM-valid candidate has a pending world even if the enclosing block fails. The 64-candidate scenario rejects excessive ordinary coinbase payouts while the EVM rule passes. Later application clears pending worlds; `verdict(hash)` still returns every prior candidate verdict. This extends the [lightweight overlay cache finding](2026-11-01-sidestr-overlays-and-eviction.md) with a distinct post-commit retention path. Committed worlds are also retained per height; their intentional archive cost needs separate capacity planning.

## Comparison and useful next steps

Ethereum's account model stores a code hash and retrieves code from the state database under that hash. This makes hash-to-byte consistency a concrete comparison for E2: accepting a matching account trie while executing different bytes breaks the intended relationship. [Ethereum account model](https://ethereum.org/developers/docs/accounts/).

Ethereum also constrains block execution by a gas limit and adjusts its base fee with demand. This SideStr profile deliberately fixes the base fee at one gwei and disables block-gas validation. The gas probe confirms that distinction without running a stress test. Compatibility documentation should describe these choices before applications assume Ethereum's resource or fee behaviour. [Ethereum gas and fees](https://ethereum.org/developers/docs/gas/).

For users, an acceptance demonstration should show two identical withdrawal requests receiving two complete payments, then restart from a verified snapshot and reproduce the same contract result and receipt history. Those observable outcomes are more useful than an undifferentiated “EVM compatible” label. Industrial applications that need contract execution should name the exact profile, its signer trust and recovery path; the audit does not establish a need to activate EVM for the broader VisionFlow walkthrough.
