# Solid federation, notifications, forge and MCP surfaces

I assessed all 17 panels of SP-08 (`docs/diagrams/solid-pod-rs/08-federation-notifications-forge-mcp.md`) against solid-pod-rs `9b6143ce55b2` and agentbox `c57d9c0508f4`. Two panels are accurate, two are accurate with limits, 13 were corrected, and none is left inaccurate. I restamped the topic from `09ec90f` and re-resolved all its citations at the pinned revisions. The topic was failing its gate before this work, because the agentbox source did not resolve from the worktree. The most important finding is that agentbox still pins solid-pod-rs `76ab7aab` with `forge-full` on. That revision predates both the hidden-tip repair and today's SP-GIT-02 store isolation, so a shipped agentbox build carries the pre-repair mirror. It is inert only while no follow entries are configured. The other substantive findings are as follows. The reference server advertises a notifications WebSocket it never mounts. Once tripped, the shared webhook circuit breaker blocks every subscriber and cannot close by itself. The legacy notifications driver never re-checks access after `ack`. Several panel claims about forge authentication and ownership described a design, not the code.

## Findings

**SP-FED-01: the agentbox consumer pin predates the mirror repairs.** Trigger: an agentbox build from `c57d9c0` with a manifest that names mirror relays and follows. Consequence: the pod runs mirror code from before the hidden-tip repair (`1a66c2d`) and before store isolation (`30135fec` to `9b6143c`), so held objects can be served as SP-GIT-02 describes. Evidence: `lib/solid-pod-rs.nix:18` enables `forge-full`; `lib/solid-pod-rs.nix:58` pins `76ab7aab3e88`, dated 2026-10-30, which is an ancestor of `9b6143c`. `1a66c2d` is not an ancestor of it (`git merge-base --is-ancestor` exit 1). At `76ab7aab` the mirror fetches `+refs/heads/*:refs/mirror/*` (`solid-pod-rs-forge/src/mirror.rs:1442`) into the store Forge serves, and `lib.rs` has no `unpublished_mirror` gate. ADR-2010 still reads accepted / complete / staged (`ADR-2010-…:5-7`). To close it: bump the agentbox pin to a release that contains `9b6143c`, or keep the mirror follow list empty in shipped manifests until it does. Source tracing only; I did not inspect a running agentbox or its manifest.

**SP-FED-02: Updates-Via advertises an endpoint the server does not serve.** Trigger: a client follows `Updates-Via` from any GET, HEAD or OPTIONS response. Consequence: `wss://<base>/.notifications` reaches the LDP catch-all GET handler, not a WebSocket channel, so notifications silently never arrive. Evidence: `solid-pod-rs-server/src/lib.rs:1335` builds the header. It is set in `handle_get` (`lib.rs:1493` and five more sites in that function) and in `handle_options` (`lib.rs:2329`). The route table has no `/.notifications` route, and the path falls to `lib.rs:5433`. No server code constructs `WebSocketChannelManager` or `WebhookChannelManager`. The panel's earlier claim, "every LDP response", was also wrong: PUT, POST, PATCH and DELETE do not set the header. To close it: mount a channel behind the header, or stop emitting it from the reference server.

**SP-FED-03: once open, the webhook circuit breaker never closes by itself and blocks every subscriber.** Trigger: ten consecutive exhausted deliveries across the manager (the default threshold) with no success in between, for example a correlated outage or a dead sole subscriber. A single dead target among healthy ones rarely trips it, because any 2xx or 410 from any target resets the shared counter (`mod.rs:618`, `mod.rs:624`). Consequence: delivery to every subscription on that manager stops. The open check returns before any network call, so no success can follow; only `reset_circuit` closes it. Evidence: `solid-pod-rs/src/notifications/mod.rs:398` is the one shared counter, `mod.rs:602` is the early return, `mod.rs:484` is the reset, and `deliver_all` calls `deliver_one` per subscription in turn. The comments contradict this (`mod.rs:380` says a successful delivery resets the counter), and `mod.rs:446` says "Default 5" attempts while `mod.rs:421` gives four. To close it: key the breaker by target URL, or add a half-open retry, and fix the comments.

**SP-FED-04: the legacy `solid-0.1` driver authorises once.** Trigger: a reader subscribes, then loses Read access. Consequence: through `LegacyWsDriver`, they keep receiving `pub <uri>` change lines until they disconnect. Evidence: the driver wraps `LegacyNotificationChannel` (`handlers/legacy_notifications.rs:91`). That channel checks the authoriser in `subscribe` (`notifications/legacy.rs:339`) and its fan-out arm only tests `matches_subscription` (`handlers/legacy_notifications.rs:211`). The separate `LegacyWebSocketSession` re-checks on every change (`notifications/legacy.rs:886`), but only tests use it. The default authoriser is fail-closed (`legacy.rs:255`). This needs the default-off `legacy-notifications` feature and a consumer that mounts the driver. To close it: drive the session, or re-check in the channel's fan-out.

**SP-FED-05: a public relay store bypasses the typestate.** Trigger: embedder code calls `relay.store().put(event)`. Consequence: an unverified event is stored and later returned by `REQ` history. Evidence: `solid-pod-rs-nostr/src/relay.rs:378` (`pub fn store`) and `relay.rs:227` (`fn put(&self, event: Event)`). The WebSocket path does use the typed route (`ws.rs:222`, `ws.rs:225`). Low severity: this needs code inside the process. To close it: make `store()` crate-private or read-only.

**SP-FED-06: forge push tokens renew indefinitely.** Trigger: the holder of a valid `f1.` bearer calls `POST /api/token`. Consequence: they get a fresh token. A stolen token therefore lives until the key file is replaced, and there is no revocation. Evidence: `solid-pod-rs-forge/src/lib.rs:1465` mints for any non-anonymous agent, and `auth.rs:42` resolves a bearer to that agent. **Debt:** the key is two v4 UUIDs (`lib.rs:196`) written before its mode is set to `0600` (`lib.rs:198`, `lib.rs:202`). The MAC uses RustCrypto `hmac` with constant-time verification (`token.rs:87`). To close it: require NIP-98 to mint, fill the key from `OsRng`, and create the file with mode `0600` from the start.

**SP-FED-07: forge auth and ownership panels described intent, not code.** The reference server never injects a pod-session agent. `handle_forge` always calls `resolve_agent` (`solid-pod-rs-server/src/lib.rs:5123`), and its comment says such an agent "would be" injected (`lib.rs:5122`). So "three auth schemes" was two, and `auth.rs:50` is stale. `can_write_namespace` is not "the single authorisation predicate for every mutating route". It guards push (`forge/src/lib.rs:814`) and trails (`trail.rs:921`). Other routes compare owners inline (`api.rs:515`, `labels.rs:296`) and grant issue and pull-request authors rights in foreign namespaces (`api_issues.rs:165`, `pulls.rs:765`). GitSmart paths are rebuilt (`lib.rs:798`, `lib.rs:803`), not forwarded verbatim. All three corrected in the topic.

**SP-FED-08: the MCP security warning is stale against the source.** `docs/explanation/security-model.md:108` (AUD-009) still says to keep MCP disabled because of an anonymous read path and sidecar operations without Control. The panel attributed that warning to the README, which no longer mentions MCP. At `9b6143c`, resource and skill reads go through `authorise` (`mcp/tools.rs:144`, the REST enforcement path), and the metadata gate elevates sidecars to Control (`mcp/tools.rs:111`). **Open:** closing AUD-009 needs its named regression tests run at this revision; source tracing shows the gate is wired, not that every tool reaches it. MCP stays off by default (`solid-pod-rs-server/src/lib.rs:416`, `main.rs:343`).

**SP-FED-09: the ActivityPub "verify before store" invariant is a caller contract.** `handle_inbox` does not verify signatures. It takes a `VerifiedActor` whose fields are public (`activitypub/src/http_sig.rs:76`), and its doc invites soft-logged callers (`inbox.rs:48`). What the code does enforce is the binding of claimed actor to verified actor before storing (`inbox.rs:65`, before `inbox.rs:72`). The reference server mounts only the actor document (`solid-pod-rs-server/src/lib.rs:1433`), with no inbox or outbox. `handle_outbox` fills a missing `actor` but keeps a foreign one despite its comment (`outbox.rs:57`). The outbox enqueues rows directly (`outbox.rs:83`), not through `enqueue_to_inboxes`.

**SP-FED-10: the ADRs lag the mirror repair.** ADR-2009 and ADR-2010 each gained a 2026-11-01 review qualification (`ADR-2009-…:71`, `ADR-2010-…:62`) that still treats hidden refs as the mechanism and complete withholding as open (`ADR-2010-…:69`). At `9b6143c` the boundary is store isolation plus the reader gate. This agrees with the publication report's "ADR implications" section; the ADR text is unchanged.

**Re-check of today's publication report at the pinned revision (within SP-08's scope).** These claims hold at `9b6143c`:

- Every forge repository reader resolves through `resolve_repo` (`forge/src/lib.rs:621`) or `gated_git_dir` (`lib.rs:752`), which return 503 for an unmigrated mirror (`lib.rs:651`).
- The gate covers any existing journal, an incomplete migration for 64-hex owners and forks, and a mirror record without a regular-file publication marker.
- Forge writes into a mirror's store get 409 (`lib.rs:733`), including web edits.
- An unresolvable full object id is 404 in `commit_log` (`repo/browse.rs:298`).
- `migrate` is compiled without the `mirror` feature (`lib.rs:69`).

I did not re-trace the fetch, candidate-store and publish internals; they are SP-14's panels, not SP-08's.

**Open (SP-08.17):** `matches_subscription` compares an absolute-URL subscription with the storage event's path unchanged (`notifications/legacy.rs:393`). Whether the driver ever emits `pub` depends on the path form of the consumer's storage events, which only a running consumer shows.
