# Website information identity and nightly inbox delivery

The website-information identity has real configuration, provisioning and encrypted-monitoring paths, but its public disclosure is not proof of a stored registry row. The consumed relay merges configuration into that endpoint; both the provisioner and nightly watcher mistake key presence there for registration. The watcher also accepts a monitor with admin/cohort privileges, and its capped digest retires messages it never itemises.

This pass assesses ADR-2011 section by section, adds five [DW-09 panels](../diagrams/dreamlab-ai-website/09-information-identity-and-inbox.md), corrects DW-04.9 and DW-07.8, and corrects admission/deletion claims in DW-04.5. The other panels in those older topics are not newly declared semantically complete. No identity, credential, relay, registry, live state or product implementation was changed; no message was sent to a real recipient.

Distinguish fetched, verified, itemised, acknowledged and read states. The original messages remain on the relay; this is loss of automatic digest detail, not demonstrated deletion of the originals. |
| DW-I4 — medium, probe marker suppresses user content | `inbox-watch/run.mjs:200` treats any content containing `[inbox-watch probe]` as a probe before parsing an enquiry. Test quoted documentation, forwarded messages and deliberate marker injection. This permits suppression of the sender's own submitted content; it does not by itself let one sender alter somebody else's ciphertext. |
| DW-I5 — medium, timestamp pagination can skip ties | `lib/digest.mjs:69–75` advances to oldest timestamp minus one. With 501 events in the same second and a 500-event page, the next cursor excludes the unseen event too. The scenario executes the actual cursor helper with a modelled server page, not a live relay flood. | Use a stable compound cursor or an overlap/deduplication scheme that can drain timestamp ties. | DW-I6 — medium, successful primary delivery does not guarantee monitoring | `src/lib/nostr.ts:342–368` describes and implements the monitor copy as best effort after primary acknowledgement; missing/equal key is a no-op and failures do not affect the visitor result. | DW-I8 — low, health predicates do not validate identity shape | A disclosure with the correct key, wrong name and null principal passes `disclosureProblem`. `privilegeProblem` treats a non-array cohorts value as empty. Keep “listed”, “named correctly”, “registered”, “admitted” and “unprivileged” as distinct observations. |

The watcher’s `--dry-run` still publishes a labelled probe and prints a composed digest containing excerpts (`inbox-watch/run.mjs:297–305,364–365`). The fixture confirms the probe publication reaches the fake transport while no state is written. This matches the runner's usage comment, but it means dry-run is neither read-only nor a privacy-neutral diagnostic. This audit did not invoke it against the live relay.

Other source-only limits remain: `openAuthed` resolves after sending AUTH, before receiving its acknowledgement; paging adds subscription handlers without removing them; seen-state JSON is not shape-validated; a missing or malformed file replays the current window, while valid JSON without `seen` can fail the run. The ten-page stop is logged but not carried as a structured incomplete-coverage flag. These were not separately exercised and should not be counted among the nine scenarios.

The original digest text is sanitised and bounded, and the existing tests confirm those useful controls. A rejected or unattempted alert returns `persist:false` in the tested delivery helper. A relay OK, however, acknowledges relay acceptance, not operator reading or action; the variable/comment language must not imply a stronger receipt.

## Diagram disposition and protocol correction

DW-04.9 now says monitor copying is best effort and registration is conditional on public disclosure. DW-07.8 now calls the observed object a merged disclosure entry and records digest-retirement limits. Their previous claims that row loss necessarily alarms were removed. DW-07.3's provisioning prose is qualified consistently. The five new DW-09 panels trace the merge, privilege predicates, copy/probe boundary, digest state and plaintext annotation path.

DW-04.5 now also shows the consumed kit's mode-dependent write authentication and config-or-whitelist recipient admission, replacing the operator document's unconditional no-AUTH/whitelist-only wording. Its source references are moved out of oversized node labels so the changed panels remain legible.

DW-04.5 previously called self-service deletion cryptographically impossible because outer signing keys are discarded. That overstates the protocol limitation. Current [NIP-59](https://github.com/nostr-protocol/nips/blob/master/59.md) recommends that relays honour deletion/vanish requests signed by the gift-wrap recipient. The inspected kit's deletion handler instead uses author equality unless the caller has delete-any privilege (`relay_do/nip_handlers.rs:2457–2490`); its caller permits admin or trusted moderation (`:1566–1574`). The diagram now states this implementation boundary. No deletion, reset or moderation action was executed, and the existence of a protocol recommendation does not mean deployed relays implement it.

## Comparison and user utility

[NIP-17](https://github.com/nostr-protocol/nips/blob/master/17.md) specifies separate sealed/gift-wrapped messages and seal-to-rumor author binding, and recommends timestamps randomised up to two days into the past. That supports the need for an overlapping fetch window, but does not make timestamp-only pagination complete or provide a durable business acknowledgement. The monitor's useful contribution is connecting these encrypted receipts to an operator workflow; the cryptographic envelope itself is standard protocol behaviour.

[ntfy's subscription API](https://docs.ntfy.sh/subscribe/api/) offers an instructive operational comparison: replay can resume from a message ID, and capped replay responses explicitly signal truncation. Its [publishing documentation](https://docs.ntfy.sh/publish/#message-caching) also makes the trade-off between cached recovery and missed messages with caching disabled explicit. These are useful receipt/recovery contracts to adopt, not evidence that ntfy has the same encryption or identity model or that replacing this service would fix its defects.

For the operator, the next useful outcome is a complete, recoverable enquiry queue: preserve pending items beyond the display cap; expose incomplete fetch coverage; carry stable event/submission identities into an actionable view; and keep admission, privilege, registration and delivery states distinct. Prove a real form submission reaches the primary inbox, monitor copy and operator workflow under success, rejection, backlog, restart and key rotation. Measure acknowledged enquiries and time to response, rather than interpreting an empty health-problem list as success.

This remains bespoke encrypted intake monitoring with an optional annotation feature. Its potential utility lies in integrating website enquiries with the estate's identities and operator tools. The current evidence does not establish a complete helpdesk, durable workflow queue, lossless delivery system or superior privacy to other products. Other website decisions, topic reviews and the wider estate audit remain open.
