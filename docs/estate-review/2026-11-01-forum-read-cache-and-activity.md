# Forum relay caches: cost, read authority and activity persistence

Successful cache hits remove repeated successful lookups, but ADR-2018 overstates the resulting cost and persistence bounds. Unbound channels still trigger a lookup per event, channel cardinality is not bounded per viewer, and the activity ledger has no five-minute deadline. The live dispatcher also omits kind-41 metadata from its zone-read gate. This batch documents those behaviours without changing the relay or contacting a deployed instance.

## ADR-2018 section review

| Section or decision | Assessment against source |
|---|---|
| Status and review triggers | Accepted/complete/live and `verified_commit: 7be7871` are the owner's historical record. No current deployment or analytics receipt was collected. TTL changes, new per-event lookups, changed D1 tier and faster revocation requirements remain sensible triggers; the existing lookup-failure and cost exceptions already merit revisiting the consequences. |
| Context: historical exhaustion and query counts | The described 3.3–3.6 million quiet-day rows, busy-evening exhaustion and 110-query channel opening are historical claims, not reproduced measurements. The current source explains why caching helps. Current Cloudflare documentation still lists five million daily free rows, but rows scanned and queries issued are different units. |
| Decision: channel-to-zone memo | Implemented in `nip_handlers.rs:2189–2198`: only positive results are cached for 60 seconds. The deliberate unbound-channel exception contradicts the unrestricted cost claim. Lookup failure is also represented as None (F1), not a distinct unavailable state. |
| Decision: cohorts and whitelist admin | `cached_viewer_cohorts` caches the complete tuple, including empty/false. `trust.rs:607–637` collapses missing rows, errors and malformed cohort JSON into reduced access; a transient failure can therefore remain cached for 60 seconds. This is availability degradation, unlike the channel lookup's public fallback. |
| Decision: device owner | Both outcomes are cached by `cached_device_owner`. Native fixtures confirm negative owner/cohort results cost one lookup across 50 calls at a fixed clock. Identity delegation and revocation need their own end-to-end review; no authenticated device was used here. |
| Decision: pure read membership | `zone_read_permitted` uses the resolved context; the old `has_zone_access` function is removed. Context resolves effective owner, a separate admin lookup, then cohorts. `viewer_is_admin` combines both admin signals. The shared authoriser covers kind 41, but broadcast does not call it for that kind (F2). |
| Decision: coalesced activity | First activity flushes immediately. Subsequent reads flush on a later call after 300 seconds or when pending reads reach 50; writes share that window. There is no scheduled flush. The ledger consumes its pending state before the caller attempts D1 operations (F4). |
| Decision: “posts_created stays exact” | It is unthrottled, not exact-once. `save_event` treats successful `ON CONFLICT DO NOTHING` as success; the caller increments posts for admitted qualifying kinds on that success path. Repeated admitted events can therefore increment again, and database update errors are ignored (F5). |
| Decision: TTL equals moderation window | The lookup TTL is 60 seconds. This is a cache freshness rule under normal lookup progress, not an immediate revocation or hard end-to-end response deadline. Existing in-flight contexts are snapshots. This audit does not measure every write/ban propagation path. |
| Consequences: one query per filter, at most three misses per viewer per minute | `query_events` issues a query for each processed filter, subject to its aggregate limit budget. Additional work is not capped at three: zone entries are keyed by channel; unbound channels miss repeatedly; admin status uses another cache; activity flushes perform further reads and writes. SQL LIMIT constrains returned results, not necessarily scanned rows (F3). |
| Consequences: warm live broadcasts have no D1 reads | True only for applicable cache hits and paths that need no other lookup. An unbound zone lookup stays cold. Constructor recreation resets caches; unrelated warm entries cannot make a previously unseen channel warm. |
| Consequences: 60-second changes, 300-second admin status | The latter is stale: `auth.rs:46` now uses 30 seconds. Cohort tuples separately retain `is_admin` for 60 seconds, and context ORs the two. Thus the 30-second admin cache alone does not establish a 30-second zone-read revocation bound. |
| Consequences: five-minute lag and one lost window | Five minutes is an eligibility threshold on later activity, not a persistence deadline. A retained ledger can hold 49 pending reads for a day; reconstruction loses them. Under normal positive handler counts, fewer than 50 pending reads remain between successful record calls, but that is not a bound on their age, cumulative restart losses or already-consumed failed flushes. |
| Consequences: signals rather than audit fields | Approximate signals are a defensible choice, provided promotion and inactivity behaviour tolerate the stated loss model. Historical re-reads count again; socket send success is not an acknowledged human read. The authenticated literal session key receives activity, while zone access may use the device owner; a device key absent from whitelist does not update the owner's counters. |
| Consequences: new lookups and subscription keep-warm loops | Requiring a cache or context-derived rule is helpful but insufficient without key cardinality, error semantics and hit-rate evidence. `session.rs:75–141,225–246,313–329` persists/restores subscriptions. This supports avoiding redundant REQs after healthy recovery, but persistence can fail; no recovery integration test or client-loop audit was performed here. Pings are not free if they wake the object. |
| Verification: 357 tests, clippy and WASM check | Preserved as historical verification at the declared commit. Current isolated native evidence is 20 tests; the historical full suite and WASM check were not rerun. |
| Verification: live analytics floor | The paragraph refers to evidence after deploy but supplies only a pre-change quiet-hour floor of roughly 13,500 read queries and 1,440 writes/hour. It contains no comparable post-change result, workload normalisation or rows-scanned breakdown. A measured improvement remains unestablished by that paragraph. |

## Findings and follow-up acceptance tests

| ID | Finding, confidence and useful next step |
|---|---|
| **F1 — failed zone lookup becomes public fallback** | **Source-only security finding.** `trust::get_channel_zone` (`trust.rs:584–600`) returns None on missing DB binding, bind failure, query failure or absent row. `authorize_event` (`nip_handlers.rs:2350–2372`) gates only Some(zone), otherwise eventually returns Deliver. For an event already available to the read path, a cold/expired lookup failure can therefore bypass the zone restriction. A complete database outage may prevent history retrieval first; this is not a claim that every outage leaks data. Preserve `Result<Option<Zone>, Error>`, withhold or explicitly fail unavailable protected reads, and test selective lookup failure on REQ, COUNT and live delivery. |
| **F2 — live kind-41 metadata skips the shared gate** | **Executed dispatcher counterexample plus source policy trace.** The unchanged `broadcast_event` method delivers kind 41 without calling a fixture authoriser that always withholds. Kind-40 and kind-42 controls call it and deliver nothing. Real history authorisation explicitly withholds hidden-zone kind-41 metadata from non-members. A matching broad live subscription can therefore receive metadata the history gate would withhold. This is a metadata gap, not evidence that encrypted kind-42 content is decrypted. Derive live routing from the shared read policy; add actual hidden-zone integration cases for all three kinds. |
| **F3 — query reduction lacks the claimed upper bound** | **Executed wrapper/module cases.** Fifty calls for one unbound channel produce 50 lookups; one bound channel produces one; 50 distinct bound channel IDs produce 50. Twenty 50-read activity calls at the same timestamp each return a flush. Expired keys remain in the cache: 10,000 expired entries remain allocated after all miss. These are bounded synthetic probes, not a memory-exhaustion measurement or production load test. Add capacity/expiry reclamation and metrics by lookup type/key cardinality; test cold/warm, bound/unbound, hibernating and reconnecting workloads using D1 rows-read metadata. |
| **F4 — activity has neither deadline nor durable acknowledgement** | **Executed ledger boundaries; source-only D1 failure consequence.** Forty-nine pending reads survive a simulated day of other-user activity and flush only when the original user acts again. A discarded returned Flush is not retried; reconstruction drops pending data. The wrapper's three sequential D1 operations have no transaction/requeue acknowledgement. If persistence fails, the ledger has already removed that count. Define acceptable loss explicitly; if a deadline matters, persist a pending delta and use an alarm with idempotent acknowledgement. Test restart, partial-write failure and retry without double counting. |
| **F5 — accepted duplicate events can inflate creation activity** | **Source-only.** `storage.rs:79–83,141–143` returns success for a conflict-no-op insert; `nip_handlers.rs:1546–1564` increments qualifying post counters after save success. The existing duplicate check suppresses push fan-out, not this increment. Admission/rate limits still apply. Record whether storage inserted a new event and update activity transactionally from that outcome. Exercise duplicate admitted kind-1/40/42 events and failed counter writes; no such events were sent in this audit. |
| **F6 — administrative freshness and observation gaps** | **Source-only.** Thirty-second admin checks coexist with 60-second cached cohort admin flags. The ADR's 300-second value is obsolete, and its live benefit has no after-measurement. Document the combined effective read policy, invalidate all relevant entries on observed role changes, and retain a before/after receipt with workload, deployment revision, D1 row metrics and lookup failure rates. |

F1 and F2 should precede optimisation: a cheaper private forum is useful only if read authority is consistent when data is cold, failing or pushed live. F4/F5 matter before presenting trust promotion as reliable proof of member activity. The audit records recommended changes; no relay implementation was altered.

## External comparison and member utility

Cloudflare bills D1 use by scanned/written rows; a query returning a small subset can still scan more rows. Its documentation exposes metrics through result metadata and analytics. This supports measuring actual row cost instead of treating a query-count reduction as a budget proof. [D1 pricing and metric definitions](https://developers.cloudflare.com/d1/platform/pricing/), checked 2026-11-01.

Cloudflare's hibernation documentation states that sockets can remain connected while in-memory state is discarded and the constructor runs again. Recoverable subscriptions therefore do not imply surviving cache entries or pending activity. [WebSocket hibernation](https://developers.cloudflare.com/durable-objects/best-practices/websockets/), checked 2026-11-01.

Synapse's replication architecture describes an update log that readers consume to invalidate caches and notify listeners. It offers a useful comparison for shared-state messaging: cache invalidation is part of update propagation, not solely elapsed time. This does not establish that Synapse provides zero-latency revocation, that its entire protocol should be imported, or that it has lower costs here. [Synapse replication architecture](https://element-hq.github.io/synapse/latest/replication.html), checked 2026-11-01.

For the forum, the useful distinction is a small hosted community with clear membership rules and dependable history/live behaviour. Validate that a removed member stops receiving protected metadata, a quiet member's activity is understood, and a busy evening stays within a measured operating budget. An invalidation event or versioned policy snapshot may improve that experience before a more elaborate caching layer. No demand, adoption or market-share conclusion follows from these technical comparisons.
