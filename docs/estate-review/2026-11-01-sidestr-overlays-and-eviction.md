# SideStr asset, pool, market and producer rejection boundaries

Both Rust producer paths can evict a valid transaction because the candidate block fails a clock check. Correcting the clock does not remove the exact-byte rejection remembered for that state instance. Separately, all three lightweight overlay rules retain snapshots of rejected candidates until a block is applied. Four corrected SR-02 panels distinguish these gaps from the asset, pool and market behaviour that passes the focused tests.

This is a component assessment at **sidestr-rs `9c6de86c657a25ec2f2a189baf63db7dedad40eb`**, with agentbox `9dfc27b16e82e9786535a55e790710493dd51fdf` used only for the sealed chain document. The [source manifest](evidence/2026-11-01/overlays/sources.json) fingerprints fourteen files. It adds no whole-ADR assessment or repository-completion claim. No product source, operational chain, service or VisionClaw springs work was changed.

## Findings and acceptance criteria

| ID | Finding and consequence | Evidence | Acceptance criterion |
| --- | --- | --- | --- |
| O1 — producer liveness | A future-header failure causes the fallback to evict an otherwise valid payment. Repeating its exact bytes is then refused for the lifetime of that state instance. A producer/context failure is misclassified as transaction invalidity. | `sidestr-core/src/state.rs:849-908`; composed equivalent `sidestr-evm/src/rule.rs:301-395`; two independent production-library scenarios in [probe output](evidence/2026-11-01/overlays/probe.json). | Both producers preserve admitted transactions on block-global failures. Regression cases cover a future clock, a valid payment and repaired context, while retaining transaction-specific eviction and witness-repair behaviour. Do not classify solely by whether the complete candidate verdict failed. |
| O2 — candidate lifetime | Assets, pool and markets retain a snapshot per distinct candidate hash even if a different rule rejects the block. No size, age or rejected-candidate removal is present in these caches. Continued unsuccessful validation can therefore accumulate snapshots. | `assets.rs:525-558`, `pool.rs:299-331`, `markets.rs:394-456`; one probe retains 64 rejected candidate hashes in all three rules, then observes their removal after application. | Define a bounded lifetime for candidate snapshots, with cleanup on failure and explicit ownership of simultaneous candidates. Verify repeated rejection remains bounded and an accepted candidate still commits the correct trace. Network reachability and heap consumption require separate measurement. |
| O3 — asset capability wording | The old diagram equated no optional consensus rules with no asset capability. `AssetView` expressly supports holder-side reading of the same records; invalid tallies consume input carries and leave no output assets. | `assets.rs:11-28,281-330`; existing reader tests exercise bad-tally burns. `rules_for` returns no consensus overlays for an absent rules list (`sidestr-evm/src/rule.rs:411-429`). | Documentation and any capability display distinguish client interpretation from signer-enforced rules. Confirm the host and chain configuration before showing an enforcement badge. Diagram corrected here. |
| O4 — lifecycle wording | The old refund diagram required paired outcomes. The code accepts unequal burns, including YES alone, at two burned units per refunded sat. Refunding also permits new splits and merges. | `markets.rs:260-325`; native scenario refunds 500 sats from 1,000 YES with zero NO burned, then successfully splits again in Refunding. | Present exact burn thresholds and available operations for each state. Diagram corrected; no protocol change proposed from a documentation mismatch. |

O1 changes mempool/rejection state, not committed UTXOs or collateral. The synthetic payment passes `judge` before and after the failed production when the bad clock constraint is removed. Both producers leave the chain tip unchanged but empty the mempool; resubmission reports `rejected this session: btc:rule-header-time-future`. The scenario supplies an intentionally incorrect `now`, so it establishes the error path rather than its incidence in operation. A host that always supplies `None` avoids this particular trigger; other global failures were not exercised here.

O2's probe observes derived `Debug` output of synthetic local rule objects to establish retention of every candidate hash. It does not estimate heap bytes, prove remote denial of service or read a running process. The source stores full candidate views and asset traces, so retaining hashes is evidence of retaining the corresponding cache entries. A successful application clears the pending lists; an indefinitely growing canonical applied view is not what this finding describes.

## Component review

| Component | Assessment and limits |
| --- | --- |
| Composition and validation order | `OverlayRules::boxed` installs assets, pool, markets. `validate_block_context` queries coinbase allowances before extra-rule checks, correcting SR-02.1's former arrow order. These three rules inherit zero allowance; EVM is a separate capability. Later rules consume the candidate asset trace. |
| Temporary sequencing | `OverlayRules::sequence` clones views, applies a transaction's pool/market effects locally, and promotes them only after all active overlay checks accept it. It is overlay selection, not the complete base validator. Mint policy consults the held pool/market views (`overlays.rs:34-60`); same-block opening followed by a dependent mint was not exercised, so this report does not promise arbitrary dependency closure. |
| Asset units and identity | Normal output tallies cannot exceed carried inputs; omission or under-assignment burns units. Issuance and authorised collateral mints are exceptions. A ticker is not unique: `by_ticker` chooses the earliest height/id (`assets.rs:150-158`). Applications should retain the asset ID. The parser caps each assignment at `(1 << 53) - 1` (`records.rs:38,216-221`); a hypothetical unrestricted `u64` assignment is not an accepted arithmetic counterexample. Full arithmetic fuzzing remains open. |
| Pools | A pool coin is a positive OP_TRUE output carrying exactly its underlying asset. Opening shares use integer square root. Same-share swaps enforce a fee-adjusted product; liquidity additions cap minted shares and removals cap proportional withdrawals (`pool.rs:112-189,213-246`). Existing integration covers opening and swap, including rejected opening shares; it does not exhaust liquidity, rounding or adversarial economic behaviour. |
| Markets | Opening fixes resolver/expiry/grace and creates a collateral coin. Resolution requires an input spending the resolver's script, with base validation responsible for its signature. Split and merge have no Open-only gate. Winner redemption and expired unresolved refund have distinct thresholds. The refund probe rejects a 501-sat release before accepting 500 sats from 1,000 YES, leaving NO untouched. |
| Applied-state rollback | The excessive refund leaves the chain tip, collateral and carried YES unchanged; a following valid refund succeeds. Existing integration also recovers from bad pool opening and bad split attempts. This supports these specific paths, not general transactional rollback for arbitrary external `BlockRule` implementations. Pending caches still change, as O2 shows. |
| Activation and replay | Existing integration accepts replay when markets activate exactly at opening height and rejects a one-block-late activation when later outcome minting lacks the opening. This establishes a local replay boundary, not current estate activation. |
| Producer retry classes | Composed production uses temporary overlay sequencing first. It calls `discard` for those dropped transactions, allowing another ordering to retry. After a failed final block, both producer fallbacks call `evict`, which remembers exact bytes. The previous diagram collapsed these two cases. Input-lock maturity remains an admission check. |

The [previous runtime report](2026-11-01-sidestr-crate-and-runtime-boundaries.md#runtime-observation) observed JavaScript producers and two different faucet binaries. This pass does not rerun those observations or transfer Rust findings to the baked JavaScript implementation. The sealed dreamlab chain document still has no explicit optional `rules`; holder-side asset reading remains a separate capability. No market activity, pool liquidity, grant success or deployed remediation is established.

All four SR-02 panels were corrected, rendered and visually inspected. Revision/citation and corpus checks establish resolvable source references and generated-index consistency; they do not certify all neighbouring panels or close O1/O2. No new diagram panel or whole-ADR credit is claimed.

## Comparison and user utility

Uniswap's v2 documentation describes a fixed 0.30% swap fee and reserve growth through the constant-product mechanism. SideStr's integer swap predicate uses the corresponding 1000/3 adjustment, making v2 a useful conceptual comparison for this one pool mechanism. That comparison does not establish contract compatibility, economic equivalence, liquidity or the surrounding trading product. [Uniswap fee concepts](https://developers.uniswap.org/docs/get-started/concepts/fees).

Gnosis Conditional Tokens separates an oracle-addressed question, outcome positions and a reported payout vector. SideStr's inspected market is narrower: two outcomes, a resolver input, an expiry/grace boundary and an unresolved half-value refund rule. This is a comparison of protocol responsibilities, not interoperability or a claim about dispute quality. [Conditional Tokens developer guide](https://conditional-tokens.readthedocs.io/en/latest/developer-guide.html).

For an integrator, the useful next demonstration is an isolated lifecycle with visible receipts: issue by asset ID, open a pool, reject an invalid swap, open a market, show resolver authority, exercise expiry refund, then replay from the activation height. Show whether balances come from a client reader or enforced overlay. Before making production-reliability claims, add O1/O2's regression cases and expose discarded, evicted and producer-failed outcomes separately. An industrial show-and-tell should use this only where settlement serves the scenario; source availability alone is not evidence that a deployed marketplace exists.
