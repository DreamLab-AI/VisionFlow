# Device keys: correct gates, incomplete device lifecycle

Both workers enforce ADR-2004’s exact-string, default-off policy. The shipped clients nevertheless cannot complete the current registration contract, and non-empty device lists fail their parser. Revocation changes a registry row but does not reject the raw key at AUTH or immediately invalidate cached owner scope. This continuation reviews every section of ADR-2004, adds six NF-20 panels and corrects NF-02.7 and the client-gate edge in NF-08.8. Implementation fixes, live acceptance and the wider estate audit remain open.

## Findings and acceptance work

**F1 — The two client registration producers omit the mandatory proof.** [Settings helper](../../../nostr-rust-forum/crates/nostr-bbs-forum-client/src/utils/devices.rs:144) and [recovery-sheet helper](../../../nostr-rust-forum/crates/nostr-bbs-forum-client/src/utils/devices.rs:186) send only `device_pubkey` and `label`. The [server](../../../nostr-rust-forum/crates/nostr-bbs-auth-worker/src/devices.rs:383) requires `device_proof`, signed by the device key, bound to the authenticated owner and expiring within 300 seconds. Two native probes evaluate the extracted producer expressions and deserialize with the server type: both lack the proof. Source then establishes the 400 branch after valid NIP-98 authentication. The QR is only exposed after a successful helper result; this is a blocked registration flow, not demonstrated master-key leakage. Repair both producers and test their exact request bytes through the handler, including expiry and wrong-owner rejection. Extension-backed accounts without raw master bytes also cannot use this deterministic derivation helper; explain the supported recovery/custody choices.

**F2 — Real non-empty list output fails the client parser.** Server [DeviceRow](../../../nostr-rust-forum/crates/nostr-bbs-auth-worker/src/devices.rs:320) uses `f64` for `created_at` and `revoked`; [handle_list](../../../nostr-rust-forum/crates/nostr-bbs-auth-worker/src/devices.rs:470) serialises these into JSON without numeric normalisation. Client `DeviceKey` expects `u64` and `u8`. A native round trip through the actual server row and client parser rejects floating-point values. Empty output succeeds; replacing only the timestamp with an integer still fails on `revoked`, while replacing both succeeds. Existing client tests use hand-authored integer fixtures. Repair the public wire schema and keep a producer-to-consumer round-trip test. A user must be able to see and revoke an already-registered phone even if the add-device path is broken.

**F3 — Revocation removes delegated scope eventually, not authentication immediately.** [handle_auth](../../../nostr-rust-forum/crates/nostr-bbs-relay-worker/src/relay_do/nip_handlers.rs:2057) verifies the NIP-42 event and persists its raw public key. It does not query `device_keys`. [effective_pubkey](../../../nostr-rust-forum/crates/nostr-bbs-relay-worker/src/relay_do/nip_handlers.rs:2614) later applies the worker gate and cached owner lookup. A revoked/missing/error result returns the raw identity, not a dedicated revocation-denial state. Seven native cache/authority probes include an owner cached at t=100, revoked thereafter, still returned at t=159 and refreshed away at t=160. Registration after a negative result and recovery after a lookup failure are also delayed until expiry. An existing viewer context keeps its owner-admin decision at t=500 even after a fresh lookup has lost the mapping; this models a snapshot, not a 400-second live exploit. The request loop reuses contexts across awaits. Reconnecting to the same DO does not, by source structure, force its per-key cache empty; actual reconnect/hibernation was not run. Define the revocation promise as removal of delegated access, invalidate affected caches, and bind or recheck in-flight authority. Test old and new sockets, stale negative entries and delayed request loops. Do not claim a hard end-to-end 60-second bound from cache TTL alone.

**F4 — Re-registration is also reactivation and ownership transfer.** The [upsert](../../../nostr-rust-forum/crates/nostr-bbs-auth-worker/src/devices.rs:414) replaces the owner and resets `revoked=0`; no old-owner comparison or explicit transfer intent is required. Actual SQL probes show reactivation and A→B reassignment, after which A’s owner-scoped revoke affects zero rows. Registration still requires a valid NIP-98 caller and device proof bound to that caller. This is not proof that a captured request bypasses replay protection, nor that someone lacking the device secret can hijack a key. Decide whether transfer/reactivation is intended, require explicit consent or a separate transition when appropriate, and preserve an audit history. The current row also refreshes creation time and label, losing the previous projection.

**F5 — Principal exclusion is a separate best-effort probe.** [is_known_principal](../../../nostr-rust-forum/crates/nostr-bbs-auth-worker/src/devices.rs:273) treats failed lookup branches as no match; the comment calling these branches fail-closed is inaccurate for the exclusion rule. Proof-of-possession remains an independent protection. The exclusion reads and upsert are not one atomic predicate: a SQLite interleaving lets A’s registration of B pass the owner probe, then B registers C, then A’s write makes B both owner and device. The one-hop resolver does not recursively grant C the ultimate owner’s scope, as a native control confirms. This demonstrates a registry invariant gap, not privilege escalation. Make principal status and allowed ownership transitions atomic or version-checked, distinguish lookup failure from absence, and test concurrent registration with valid proofs in the Workers environment.

**F6 — Delegation does not produce one consistent identity across features.** [Write membership](../../../nostr-rust-forum/crates/nostr-bbs-relay-worker/src/relay_do/nip_handlers.rs:1121) resolves the owner; write administration uses the raw event signer. [Read context](../../../nostr-rust-forum/crates/nostr-bbs-relay-worker/src/relay_do/nip_handlers.rs:2165) resolves admin status on the owner and permits private-zone access through that status. A fixture with an admin owner and no device cohorts confirms inherited read-admin scope. This may match the intended full read delegation, but “device keys never inherit admin powers” must be qualified by operation. Sealed-DM filters remain raw-session-key scoped, so master-addressed encrypted messages do not become readable merely through delegation. Read activity is also charged to the raw device key, unlike owner-attributed write activity; a non-whitelisted device does not automatically advance the owner’s read-based trust/activity records. Specify the read, write, moderation, messaging and activity matrix and explain it before a user enrols an admin’s phone.

**F7 — Gate agreement and UI state still need deployment acceptance.** Both workers share the exact rule, while the browser accepts boolean true and normalised strings including `1` and `TRUE`. The NF-08.8 edge previously connected the client to the shared parser; it now points to its separate rule. Stock auth `RELAY_DB` is a documented placeholder, so matching flags alone cannot establish matching rows. No live configuration was inspected. Settings loads once while its list is non-empty and does not bind asynchronous responses to an account generation in the reviewed block; after an account switch it can retain or display an earlier account’s list. This is source-only. Validate the three settings, both resolved database identities, actual producer contracts and account changes together before activation.

## External comparison and utility

[Matrix’s device-deletion API](https://spec.matrix.org/latest/client-server-api/#delete_matrixclientv3devicesdeviceid) explicitly invalidates associated access tokens and defines authentication requirements; current OAuth-aware clients use account management instead. Its value as a comparator is an explicit lifecycle contract connecting the device record and access, not evidence that every Matrix deployment revokes instantly. [Syncthing](https://docs.syncthing.net/users/security.html) checks device certificate fingerprints against configured peers at connection establishment. That illustrates an explicit connection-admission boundary, but its file synchronisation trust model differs from forum membership and encrypted messaging. [NIP-42](https://github.com/nostr-protocol/nips/blob/master/42.md) authenticates signed identities on a connection; the forum’s device-to-owner registry is additional application policy, not a Nostr revocation mechanism.

A useful product position is a community account that can enrol and retire phones without copying its master secret. The immediate priorities are working registration/list contracts and an observable delegated-access cutoff. An acceptance journey should enrol a phone, show its key and privileges, revoke it from another device, confirm that existing and new connections lose delegated private access, and separately explain which public activity and previously obtained ciphertext remain possible. This is a proposed user journey and market inference, not a claim of adoption, competitor superiority or proven deployment behaviour. Primary sources were read on 1 November 2026.
