# VisionClaw handler families, graph, state, governance and identity

Every panel in VisionClaw topics VC-04 (23 panels) and VC-05 (15 panels) was assessed against VisionClaw `86cdd7635582` and agentbox `c57d9c0508f4`. Both topics were restamped from `8692b12` (and agentbox `6500582`), and every citation was re-resolved. VC-04 has 3 panels accurate, 4 accurate-with-limits and 16 corrected. VC-05 has 3 accurate, 4 accurate-with-limits and 8 corrected. No panel is left inaccurate-unfixed.

The most important finding is about service callers that authenticate with `X-Agent-Key`: the agentbox broker bridge, the git-bridge write-back and canary reporters. These routes sit inside the `/api` RbacGate, and the gate resolves identity through `verify_access`, which has no `X-Agent-Key` path. In a release build with the gate enforcing, those callers are refused with 401 before the handlers that check the key ever run. The dev Compose profile's full bypass hides this.

The second finding is about `/api/solid/pods/init-nip98`. The NIP-98 single-use replay cache makes the route's second, independent NIP-98 verification fail as a replay, so the route refuses genuine callers.

## Findings

**F1. X-Agent-Key service callers are refused at the `/api` RbacGate (VC-05.7, VC-05.8, VC-04.17).**
- **Trigger:** the agentbox bridge calls VisionClaw, sending only `X-Agent-Key` (`agentbox/management-api/routes/broker-bridge.js:105-115`, inbox `:345`, decide `:576-579`). The git-bridge write-back sends no credential (`src/handlers/ingest_writeback_handler.rs:19-23`). Canary writers present `X-Agent-Key` (`src/handlers/liveness_harness_handler.rs:38-45`).
- **Mechanism:** all three route groups are mounted inside the `/api` scope that the RbacGate wraps (`src/main.rs:1126`, `:1137`; decide `:1224`, write-back `:1235`, broker `:1230`, canary `:1238`). A POST needs `WriteGraph` (`src/middleware/rbac_gate.rs:179-189`). `verify_access` knows only three things: the dev bypasses, NIP-98, and the legacy `X-Nostr-Pubkey`/`X-Nostr-Token` pair (`src/utils/auth.rs:211-218`, `:259-265`, `:329-353`). `RequireAuth::power_user()` on `/broker` delegates to the same function (`src/middleware/auth.rs:158-160`).
- **Consequence:** in release, the bridge's decide and inbox calls, the write-back and canary writes all get 401. The production Compose service, `visionclaw-production`, requires `VISIONCLAW_AGENT_KEY` for these callers (`docker-compose.unified.yml:288`), which suggests the deployed intent is that they work. The dev service, `visionclaw`, arms `VISIONCLAW_DEV_MODE=1` (`docker-compose.unified.yml:116`), whose bypass grants every request (`src/utils/auth.rs:211-218`).
- **Drift:** the comments at `src/handlers/broker_inbox_handler.rs:27-33` and `:246-247` claim the bridge "authenticates through the same middleware via its X-Agent-Key". It does not.
- **To close:** allowlist the service routes in the gate and keep the handler-level key checks, or have `verify_access` accept the service credential for named routes, or give the bridge a NIP-98 signer. Then test against a release build with the gate enforcing.

**F2. Second NIP-98 verification on `/api/solid` meets the single-use replay cache (VC-05.15).**
- **Mechanism:** every successful validation claims the event id process-wide (`src/utils/nip98.rs:164-168`, `:573`). The gate verifies first (`src/utils/auth.rs:291-295`, `src/services/nostr_service.rs:648-662`). The handler then calls `extract_user_identity`, which re-runs `validate_nip98_token` on the same header (`src/handlers/solid_proxy_handler.rs:188`, `:225`). That second run returns `TokenReplayed`, so the handler gets `None` and answers 401 (`src/handlers/solid_proxy_handler.rs:1332-1338`).
- **Consequence:** `init-nip98` cannot succeed for a genuine caller. Every `/api/solid/*` request the gate verifies loses its identity before the WAC check. That is all mutations, and reads too when public reads are off.
- **Contrast:** `verify_access` already reuses an outer identity for nested `RequireAuth` (`src/utils/auth.rs:266-280`). `/pay` is not affected, because it mounts at the App root and verifies once (`src/main.rs:1105`). The dev profile hides the failure: with `VISIONCLAW_DEV_MODE=1`, `verify_access` returns before any NIP-98 verification (`src/utils/auth.rs:211-218`), so the gate claims no event id and `init-nip98` works under `launch.sh up dev`.
- **To close:** have `extract_user_identity` read `get_authenticated_user` first, and add a route test through the real gate. VC-03.15 (another worker's topic) still describes this route only as "double-authenticated".

**F3. Anonymous MCP relay control (VC-04.16).**
- **Mechanism:** `/api/health/*` is public in the gate (`src/middleware/rbac_gate.rs:55-61`), and the MCP routes have no auth wrap (`src/handlers/consolidated_health_handler.rs:479-483`).
- **Consequence:** `POST /api/health/mcp/start` runs `docker exec -d multi-agent-container … npm run mcp:start` (`src/services/mcp_relay_manager.rs:171-187`), then blocks an actix worker for 2 s with `std::thread::sleep` (`:194`). `GET …/logs` returns the relay log tail (`:210-219`).
- **To close:** move both routes under an authenticated scope.

**F4. The `/api/physics` port drives a private orchestrator with no GPU (VC-04.13).**
- **Mechanism:** `ActixPhysicsAdapter::initialize` starts a `PhysicsOrchestratorActor` whose `gpu_compute_addr` is `None` (`src/adapters/actix_physics_adapter.rs:121-127`, `src/actors/physics_orchestrator_actor.rs:195-198`, `src/main.rs:855`). `layout_handler.rs:79-84` relies on this being harmless.
- **Consequence:** `/api/physics/start` reports success without moving the simulation that clients see.
- **To close:** route the port to the live GPU actors, or retire its mutating routes.

**F5. Graph-export state is per worker (VC-04.11).**
- **Mechanism:** `configure_routes` builds a fresh handler, with fresh share and rate-limit maps, on every call (`src/handlers/graph_export_handler.rs:315`, `:38-45`). It runs inside the `HttpServer::new` factory (`src/main.rs:972`, `:1196`) with four workers (`:1265`).
- **Consequence:** a share link created on one worker returns 404 on the other three, and the export limit is per worker.
- **Also:** `GET /stats` is a 501 stub (`:308-311`), not the counter read the panel described.
