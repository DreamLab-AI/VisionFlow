# Dream governance, signing and delivery audit

Dream-engine's forum path has distinct authority, state and delivery gaps. It accepts valid signatures without checking the signer's role locally, permits missing request binding and stops following decisions after resolving an item. Reopening an item can attach its new publication receipt to the closed predecessor and make the new request a deletion target. Publication acknowledgements do not establish persistence or disappearance from the operator's panel.

This pass assesses every ADR-2115 section and the ER-6 signing decision in ADR-2122. Three existing panels are corrected and one digest panel added. Six original AB-23 panels remain queued: 1, 4, 5, 8, 18 and 22. Sixteen of the original 22, plus new panels 23 and 24, are assessed. The wider estate audit remains active; production code, owner ADR statuses, keys and running services are unchanged.

## Evidence and boundaries

Agentbox is `9dfc27b16e82e9786535a55e790710493dd51fdf`; forum source is `c39f41f104b114d6a3fa29013daaf6fa58b45080`. The entrypoint and ADR-2122 changed elsewhere, but their selected registration/custody and ER-6 blocks match; diagram citations retain the older pin and corresponding line numbers. This is not a fresh blanket stamp for unassessed panels.

[Eleven probes pass](evidence/2026-11-01/dream-governance-probes-final.log), using [committed Rust source](evidence/2026-11-01/dream-governance-probes.rs) in a clean adapter export. They exercise public planners, inbox storage, digest composition, zone policy and a loopback WebSocket relay. One test runs the actual withdrawal path twice while a temporary directory obstructs its local receipt write. Another checks query behaviour after an authentication refusal and a CLOSED response. Signing uses disposable fixture keys through the existing library; no real key is read and no external relay is contacted.

Existing tests also pass: governance 19, relay 8, inbox 12, digest 7 and zone_crypto 9, totalling 55 Rust unit tests, plus [12 hook assertions](evidence/2026-11-01/dream-governance-existing-hook.log). The probes assert current defects and limits, not remediation. [Reproduction notes](evidence/2026-11-01/dream-governance-reproduction.md) distinguish executed code from source inspection. No browser, deployed relay, identity-port daemon, live inbox or night was exercised.

## Findings and acceptance work

Paths are relative to agentbox unless prefixed forum.

| Finding | Evidence and consequence | Acceptance required |
|---|---|---|
| AB-G1 / high boundary: signature validity is not decision authority or strict request binding | `governance.rs:857-862` checks kind, non-self signer and signature, without a role/delegation lookup. At `:879-880`, absent e is accepted even when the item has a current request. A second fixture key resolves a question without an e tag or role evidence. Panel acknowledgement uses action and time, ignoring other outcome fields. | Require current request identity and an explicit trusted authority basis, including delegated reviewers and panel scope. Keep provenance in the applied receipt. This is a consumer-boundary test, not a demonstrated bypass of the deployed relay: current forum admission rejects non-admin/non-delegated writers. The adapter depends on that relay policy and on which relay DREAM_RELAY selects. |
| AB-G2 / high: newest selection and local closure do not implement a decision chain | `governance.rs:864-880` selects newest by timestamp/ID before binding or mapping. A newer stale-bound decision suppresses an older valid approval; newer delegate also leaves the item open. Once answered, `:876` and `inbox.rs:167` exclude it from later application. A signed later rejection with a supersedes tag cannot revise a locally applied approval. | Select among valid, authorised decisions according to a defined supersession chain. Persist the last applied decision and reconcile later authorised changes, or explicitly declare local answers terminal. Do not imply the relay's supersession feature is automatically honoured by this consumer. Delegate behaviour itself is intentional; the unsupported older-decision fallback and terminal local state need explicit semantics. |
| AB-G3 / high: reopened identity can withdraw its new request | `inbox::add` allows a new open row after an earlier same-ID row closes. `mark_published_in:121` selects the first matching ID without checking status or request generation. The probe stores a closed row before an open row: marking new-request changes the closed row, leaving the open one unmarked. `plan_withdrawals` then targets new-request through e, even though it correctly suppresses the coordinate tag. | Give each reopening a generation identity and bind updates to the exact open record. Retain the old request identity separately. Test publish, resolution and withdrawal across reopen/retry boundaries. The probe verifies the planned deletion target, not actual removal of a live event. |
| AB-G4 / high: atomic file replacement is not transactional state | `inbox.rs:84-111` reads failures as empty and uses one fixed temporary filename; the read/modify/write operations have no lock or revision check. A deterministic stale-snapshot write restores open after a saved resolution. `send_withdrawals:687-695` increments withdrawn before local receipt persistence; the loopback test acknowledges two sends because both receipt writes fail. | Add concurrency control and corruption handling; persist exact operation identities and distinguish acknowledged from locally committed. Retry-safe delivery may resend, so replace the at-most-once claim with a tested deduplication protocol. A temporary rename prevents partial replacement in ordinary execution but does not prevent lost updates or prove crash durability. The stale-snapshot probe is an explicit interleaving, not a claimed live race. |
| AB-G5 / high qualification: ACK does not prove durable publication or live card removal | Governance marks publication from OK without read-back (`governance.rs:1029-1035`). Withdrawal likewise records OK. Forum deletion SQL ignores errors (`relay_do/nip_handlers.rs:2457-2521`); its coordinate deletion has no timestamp bound. The forum app subscribes the panel registry only to 31400–31405 (`app.rs:837-862`), and that registry ignores kind 5 (`panel_registry.rs:227-231`). | Verify publication and deletion persistence, preserve tombstones and reconcile loaded client state. A deletion ACK alone cannot certify a card has disappeared. Current source establishes that this subscription/registry path does not process withdrawals; it does not prove every browser view stays visible, since decision-state rendering may hide it independently. No deployed D1 failure or browser session was tested. |
| AB-G6 / medium: relay queries erase refusal/completeness distinctions | `relay.rs:222-224` continues after rejected AUTH. `query:317-332` accepts deserialisable events without signature/filter checks and returns collected results on CLOSED or timeout. The loopback probe returns an invalidly signed, wrong-kind event successfully, and an auth-required CLOSED becomes an empty success. Decision planning later verifies signatures, but panel equality, publication-time lookup and digest read-back do not. | Return typed outcomes for EOSE, CLOSED, timeout and transport failure; enforce event/filter validation at the appropriate boundary. Keep an unavailable/incomplete read distinct from no pending decisions. Handle later authentication challenges deliberately. The probe does not bypass the planner's signature verification. |
| AB-G7 / medium implementation gap and corrected diagram: agent signing support already exists | ACL `:75-84,294-307` permits marked agent_governance keys to receive forum_event grants for 31400/31402; its test also grants kind 5. The shipped ACL has no marked key or these grants. The engine still loads and signs with its own key. Under intended flag-on ownership, devuser cannot read the identity-owned file. | Complete the configured-key, relay-registration and client cutover; do not describe the protocol as permanently forbidden. Include NIP-42 authentication and old-key withdrawals in the design: marked keys cannot receive the separate nip42_auth operation, while this client authenticates with its publishing key. This is an unresolved integration requirement, not proof that no safe design is possible. No key generation or activation was attempted. |
| AB-G8 / high policy boundary: malformed encryption metadata selects plaintext | `parse_zones` returns empty on malformed input; `section_to_zone` falls back to the first zone; `write_plan` returns Plain unless the selected zone is known encrypted (`zone_crypto.rs:86-115,221-233`). With gate=true and malformed metadata the probe selects Plain; valid encrypted metadata with no key correctly refuses. Selection uses latest locally held epoch, not a freshly established current zone epoch. | Treat unknown/malformed policy as unavailable when encryption is required. Resolve the section unambiguously and define key-epoch freshness. Keep intentional public-zone plaintext explicit. The probe tests policy selection only; it sends no plaintext and does not establish whether the live relay would accept it. |
| AB-G9 / medium: digest language exceeds its evidence | Missing health produces Nothing was tested even when ledger inputs contain a completed result. A REJECT label with no ledger receipt produces DISPROVED. Standby entries are omitted when ordinary outcomes exist. Earlier rows are called disrupted attempts merely from their count (`digest.rs:186-217,242-354`). | Distinguish missing evidence, failed acceptance and disproved hypotheses; bind explanations to actual receipts. Render the full nominated/standby/deferred roster consistently and identify retries by run identity. Existing source can report all verdict labels without establishing the stronger narrative. |
| AB-G10 / medium: case evidence ignores configured ledger location | `case_context:274-278` hard-codes docs/dream-cycle/LEDGER.md, while config permits ledgerPath and digest collection honours it. A validated fixture config points at custom.md; the file exists but case context has no finding or PR link. | Pass the resolved ledger path into case context and bind it to the item/run. Keep missing evidence explicit rather than supplying generic assurances. The test does not claim every optional case field must always exist. |
| AB-G11 / medium: reminders advertise unpublished items as panel decisions | The hook and digest count all locally open items, without checking published_event_id or remote availability. Existing hook fixtures have no publication fields yet emit the panel pointer. Hook suppression uses a shared timestamp without locking and ignores stamp-write failure. | Show separate local, publication-pending and confirmed-visible counts. Describe the four-hour rule as best-effort unless synchronised. Avoid directing operators to a panel which cannot yet contain their pending decisions. The transcript-consumption contract itself was not retested in Claude Code. |

A separate compatibility qualification applies throughout: the adapter consumes `nostr-bbs-core =1.0.0-beta.16`, whereas the inspected forum checkout declares beta.19. Linking a shared library reduces duplicated schemas but cannot guarantee version or policy alignment across deployments. This pass does not assert a demonstrated wire incompatibility.

## Comparison and user utility

[NIP-09](https://github.com/nostr-protocol/nips/blob/master/09.md) describes deletion requests, client handling and the inability to guarantee removal everywhere; coordinate deletions should respect the request timestamp. The relay's unbounded coordinate delete and the panel's missing kind-5 ingestion deserve explicit reconciliation tests. [NIP-42](https://github.com/nostr-protocol/nips/blob/master/42.md) distinguishes authentication from subscription permission and defines auth-required/restricted responses. Treating CLOSED as an empty successful read loses that useful distinction.

[GitHub's deployment review workflow](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/review-deployments) ties approval or rejection to a pending job and can prevent self-approval. Dream's current cases instead supply future guidance; they do not approve a merge or synchronously release a blocked operation. That distinction should be visible in the product. The comparison is about understandable decision scope, not feature parity or a recommendation to replace the forum.

A useful next deliverable is a decision receipt showing case generation, exact request, authorised signer, applied decision, local persistence, publication state and withdrawal state separately. Test reopening, supersession after application, reconnect with a loaded panel, missing encryption policy and a failed local write after remote ACK. Measure whether an operator can identify what changed and whether their latest decision took effect without reading logs. These are proposed acceptance measures, not current performance claims.
