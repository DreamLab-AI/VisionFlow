# VisionClaw client transport, identity and feature panels

I assessed all 42 panels in VC-32 (client WebSocket and binary protocol, 14 panels), VC-33 (browser identity, 8 panels) and VC-34 (client feature directories, 20 panels) by tracing the source at VisionClaw `86cdd7635582`. The three topics were stamped at `8692b12`, 217 commits earlier. I restamped each one to the pin and re-resolved every citation. Of the 42 panels, 3 are accurate, 39 are corrected, 0 are accurate-with-limits and 0 are inaccurate-unfixed. Runtime limits on corrected panels are named in the evidence column. The most important finding is VC33-F1. The power-user lookup that ER-26 added asks the shared API client for `'/api/admin/rbac/whoami'`, but that client already prepends `/api`. The request therefore goes to `/api/api/admin/rbac/whoami`, a path the repository itself records as a 404. The lookup returns `null` and never lifts a real power user. The same doubled prefix affects the semantic, analytics and physics client calls. Second in weight: VC-32.10 still described the retired drag-pins-the-node model, while the pin implements ADR-2169's hold model and a client drag heartbeat.

## Findings

**VC33-F1. The ER-26 power-user lookup requests a doubled `/api` path.**
- Trigger: any non-dev sign-in. `App.tsx:53-65` calls `fetchPowerUserStatus`, which calls `unifiedApiClient.get('/api/admin/rbac/whoami')` (`client/src/services/powerUserStatus.ts:28`).
- Consequence: `UnifiedApiClient` defaults its base to `/api` and builds `${baseURL}${url}` for every relative path (`client/src/services/api/UnifiedApiClient.ts:77`, `:182`), so the request URL is `/api/api/admin/rbac/whoami`. The server mounts whoami at `/api/admin/rbac/whoami` (`src/main.rs:1126`, `src/handlers/admin_rbac_handler.rs:282-286`). The repository records this exact doubling as a 404 in `client/src/features/ontology/services/ontologyPhysicsService.ts:21` and `client/src/features/control-center/status/usePhysicsState.ts:6`. `fetchPowerUserStatus` swallows the failure and returns `null` (`powerUserStatus.ts:36-38`), so `isPowerUser` stays false and power-user-only settings stay locked. The unit test mocks the client and asserts the doubled string (`client/src/services/__tests__/powerUserStatus.test.ts:16`), so it cannot catch this.
- Same defect elsewhere: `useSemanticService.ts:100-284` (7 calls), `analyticsStore.ts:328` and `usePhysicsService.ts:101-377` (13 calls; this hook has no caller outside tests).
- To close: drop the leading `/api` from these paths, or have the client strip it as `CommandInput.executeAction` does (`CommandInput.tsx:595`). Then add one test that exercises the real `UnifiedApiClient` URL build. I traced this from source; I did not run a live request.

**VC32-F2. The drag panel described a pin model the code no longer has.**
- Trigger: the ADR-2169 commits (`37d1226b1`, `db1ab342d`) after the old stamp.
- Consequence: a drag is now a hold that releases on `nodeDragEnd`, a 2 s update gap or a disconnect (`position_updates.rs:82-85`, `:520-544`, `types.rs:23`). The desktop client re-sends `nodeDragUpdate` every 500 ms while the pointer is still (`dragHeartbeat.ts:9-16`, `useGraphEventHandlers.ts:171-184`). A lasting anchor is the separate `nodePin` / `nodeUnpin` pair (`message_routing.rs:60-65`), which the web client never sends.
- I rewrote VC-32.10. **Drift** remains in product comments: `useGraphEventHandlers.ts:151-155` and `:269-276` still say the server pins and unpins. ADR-2169 is accepted with implementation `partial` and activation `inactive`.
- To close: update the two client comments, and do the runtime activation ADR-2169 calls for.

**VC34-F3. A failed settings retry is silently dropped, and the 401 signal has no listener.**
- Trigger: a settings flush that fails (`autoSaveManager.ts:126-136`). A single-path retry then calls `updateSettingByPath` (`settingsRetryManager.ts:104-108`).
- Consequence: that function catches every error and never rethrows (`endpoints.ts:303-311`), so the retry always takes its success branch and deletes the update. On a 401 it dispatches `settings-auth-failed` (`endpoints.ts:305-306`), but nothing in `client/src` listens for that event. The topic previously drew the 401 event as the direct outcome of the flush PUT; it is not.
- To close: rethrow from `updateSettingByPath`, or return a status, and wire a UI listener.

**VC33-F4. The legacy session-bearer realm is opt-in, default off.**
- VC-33.3 and VC-33.9 said the server accepts this realm. At the pin it answers only when `VISIONCLAW_LEGACY_SESSIONS` is `1` or `true` (`nostr_service.rs:113-117`, `:174-176`, `:510-519`). ADR-2009 records the same. Corrected.
- To close: nothing further in code; consumers of the topic should treat the realm as off unless the deployment sets the flag.

**VC32/VC34-F5. Dead paths drawn as live** (each now marked **Debt:** in place):
- The `processBinaryData` framed-header switch is unreachable, because `validateBinaryData` admits only lead bytes 3, 5 and 0x23 (`store/websocket/binaryProtocol.ts:197`, `:482-504`; VC-32.3 and VC-32.8).
- No client code sends a framed message. The six `encode*` methods have no caller, and the interaction-end flush is always empty (`BinaryWebSocketProtocol.ts:136`, `:213-216`; VC-32.4).
- `JssOntologyService.patchOntology` has no caller. `OntologyContribution` POSTs proposals by plain fetch instead (`useOntologyStore.ts:322`, `:336`; VC-34.3).
- No server emits `ontology_loaded` (VC-34.5).
- `show-help` and `search-help` have no listener (VC-34.14).
- No server route serves `/ws/workspaces`, and `useWorkspaces` has no caller (VC-34.17).
- `bots-position-update` is still emitted (`binaryProtocol.ts:325`, `:380`) but its only listener was removed (VC-34.10).
- To close: delete each dead path, or wire the missing sender, listener or route, and add a test that drives it through the real entry point.

**VC34-F6. The agent-polling max-retry stop corrupts the subscriber count.**
- `handlePollingError` calls `stop()` (`AgentPollingService.ts:324-327`), which releases a subscriber slot no subscriber gave up. With two subscribers, polling dies with `isPolling` still true, and a later `start()` never restarts it (`:126-128`, `:141-143`).
- To close: use a separate halt path that does not touch `subscriberCount`.

- To close: closed by this restamp. A topic restamp should re-derive every citation, not only those in changed files.

**VC32-F8. Product comment drift.**
- `src/utils/binary_protocol.rs:476-480` says `position_updates.rs` and `actor_messages.rs` stamp class flags. Neither does since the `requestSwarmTelemetry` removal (VC-32.6).

- The VC-32.1 drift notes against `PROTOCOL-registry.md:327-330` and `BASELINE-architecture.md:320` still hold.
- To close: correct each comment or document in place. None changes behaviour.

**VC34-F9. The settings type generator is hand-maintained.**
- `generate_typescript_interfaces()` returns a raw-string TypeScript literal (`src/bin/generate_types.rs:64-568`), so it does not track `AppFullSettings`. Only the new ontology-agent output is serialised from Rust types (`:591-601`, `:768-769`).
- VC-34.2 previously drew the struct as the generator's input. Corrected.
- To close: derive the settings interfaces from `AppFullSettings` (as the ontology output already is), or add a test that compares the two field sets.
